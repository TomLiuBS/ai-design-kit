# Figma Component Description 記入フォーマット

AIがコンポーネントを正しく選び、正しく組み立てられるようにするための Description の書き方。

配置: `guidelines/rules/description-format.md`

参照元: `design-system-audit`（F1・F2の判定）、`figma-agent-skills/description-draft.md`（起案）

**このルールは複数の生成AI（Claude Code / Codex / Figma Agent）が参照する。** ランタイム側で別基準を定義しない。

関連ルール: [layer-naming-rules.md](layer-naming-rules.md)、[variant-naming-rules.md](variant-naming-rules.md)

Figma の説明欄はプレーンテキストとして読み取られる。**Markdownの装飾は意味を持たず、画像は読み取れない。** そのため「ラベル + コロン + 1行」の形式が最も確実に切り出せる。

---

## 1. なぜこの形式か

ラベルは4つだけ。**各ラベルは、AIが誤る場面を1つずつ防ぐために置いている。**

| ラベル | 防ぐAIの誤り | 具体例 |
|---|---|---|
| **用途** | 何の部品か分からず、名前から推測して選ぶ | 案内文にどの種類を使うかが、種類名だけでは決まらない。Figma と CSS で種類の名前が違うと、AIは推測で選ぶ |
| **選び分け** | 似た部品を取り違える | アイコンのみのボタンと丸ボタン付きのラベル付きアイコン、通知の種類、3択の入力部品。相手の部品名が書かれていれば、Figma と CSS で名前が違っても対応づけられる |
| **Property** | 値名が意味を表さない軸で、AIが推測して値を指定する | `size` がサイズと配置を兼ねている軸 |
| **禁止** | 操作はできるが、その部品では使ってはいけない使い方をする | 種別色の塗りを上書きする |

**長文は逆効果。** 説明が長いほど、AIが要点を取り違える。全体で4行・200字以内にする。

---

## 2. テンプレート

Component Set（Variantの親）または単体 Component の説明欄に、次のテンプレートを貼る。**説明の部分と `(必須)` `(任意)` を削除し、書く内容に置き換える。書かない行は、ラベルごと削除する。**

```
用途(必須)：何を表示・操作するかと、どんな場面で使うかを1文で書く
選び分け(任意)：似た別の Component Setがあるときに書く。相手側にも書く
Property(任意)：いずれかに当てはまるときに書く。①1つの軸が複数の意味を兼ねている②値名が番号・略語・記号③部品ごとに同じ値名が別の意味になる
禁止(任意)：操作はできるが、その部品に限って使ってはいけないルールがあるときに書く
```

### 各行の書き方

| ラベル | 必須 | 書く条件 | 内容 |
|---|---|---|---|
| **用途** | ◎ 必須 | 常に書く | 何を表示・操作するかと、どんな場面で使うかを1文で書く |
| **選び分け** | 条件付き | 同じ用途で選択肢になりうる別の Component Set があるとき。**相手側の Description にも書く** | 「〜のときは `部品名`」の形で、似た部品との判断基準を書く |
| **Property** | 条件付き | 次の①〜③のどれかに当てはまる軸があるとき。**当てはまる軸だけ**書く | `軸名=意味` の形で書く |
| **禁止** | 条件付き | 操作はできるが、その部品に限って使ってはいけないルールがあるとき | 1文で書く |

**Property を書く条件**

1. 1つの軸が複数の意味を兼ねている（例: `size` がサイズと配置を兼ねている）
2. 値名が番号・略語・記号である
3. 部品ごとに同じ値名が別の意味になる

①〜③のどれにも当たらない軸（値名が申請の種別名、`md` / `sm` など）は書かない。

**禁止に書くのは、その部品に固有のルールだけ。** 複数の部品や画面全体に当てはまるルール（例: 同じ画面に並べてはいけないボタンの組み合わせ）は、Description ではなく DESIGN.md に書く。

**類似部品がある場合、「選び分け」は用途と同じ重さで扱う。** 片方にしか書かれていないと、もう片方だけを見たAIは判断できない。

## 3. 記入ルール

### 必ず守る

- **ラベルは `用途` `選び分け` `Property` `禁止` の4つだけ。** ラベルの後ろのコロンは、全角（`：`）・半角（`:`）のどちらでもよい
- **1行1情報。** 改行で区切る。段落にしない
- **書かない行はラベルごと消す。** 空のラベルを残さない
- **具体的な部品名を書く。** 「他のコンポーネント」ではなく `badge/number` と名前で書く
- **数値・条件は具体的に。** 「小さい画面」ではなく「幅768px未満」
- **画像・スクリーンショットで説明しない。** テキストとして読み取れない
- 旧形式のラベル（`使う` `使わない` `関連`）が書かれていても、違反にしない。書き直しは任意

### 避ける

| 避ける書き方 | 理由 | 直し方 |
|---|---|---|
| 「適宜使用してください」 | 判断基準にならない | 条件を数値か場面で書く |
| 「基本的には〜」「原則として〜」 | 例外の範囲が不明 | 例外を明示するか、断言する |
| 「デザイナーに確認」 | AIが止まる | 判断できる基準を書く |
| 見た目の説明（角丸8px、影あり） | Variables/Styleを見れば分かる | 用途と条件に置き換える |
| 長い背景説明・経緯 | 要点が埋もれる | 削る |
| 装飾記号や罫線の多用 | 読み取りの邪魔になる | ラベルだけにする |

### 書く場所

| 対象 | 書く場所 |
|---|---|
| Variant を持つ部品 | **Component Set（親）に1つ** 書く。各Variantには書かない |
| Variant ごとの違い | Set の `Property` 行に集約する |
| 単体 Component | そのComponent自身に書く |

Figma には Variant プロパティ個別の説明欄がない。**Variant 値の意味は `Property` 行に書くしかない。** ここを省くとAIは値名から推測するしかなくなる。

## 4. 記入例

書き込んだ後の形式。**形式はそのまま使える。**

### tag/requestType

```
用途：一覧・カード・見出しで、申請の種別（経費・出張・休暇など）を識別させる固定ラベル。
選び分け：ルビが必要な画面は tag_ruby/requestType。件数や状態の表示は badge/number。
禁止：塗り色の上書き。種別色はSemantic tokenで固定。
```

`Property` を書いていないのは、`type` の値が申請の種別名で、`size` の値が `md` / `sm` のため。①〜③のどれにも当たらない。

### tag_ruby/requestType

```
用途：漢字にルビが必要な場面で、申請の種別を表示する固定ラベル。
選び分け：ルビ不要の画面は tag/requestType。種別の並びが異なる（本コンポーネントは19種）。
禁止：ルビのテキスト差し替え。読み仮名は固定。
```

### explainTag

```
用途：画面上の特定要素に補足説明を添える、常時表示の吹き出し型ラベル。
選び分け：一時表示の短い補足は tooltip。
Property：size=表示サイズ（md/sm）と配置（左端/右端）を兼ねる軸
禁止：長文の格納。2行以内に収める。
```

`size` が条件①に当たるので `Property` を書く。軸を分離するまでは、兼ねている事実を明記しておく。書いておけばAIの誤解は減らせる。

## 5. 記入チェックリスト

書き終わったら確認する。

- [ ] 用途が、何を表示・操作するかと使う場面を、1文で言い切っているか
- [ ] 同じ用途の別 Component Set がある場合、`選び分け` を相手側にも書いたか
- [ ] `Property` に書いたのは、条件①〜③に当たる軸だけか
- [ ] 部品名が具体的か。「適宜」「基本的に」「デザイナーに確認」、見た目の説明が入っていないか
- [ ] 4行・200字以内か。画像で説明していないか。書かない行のラベルを残していないか

## 6. 進め方

### 前提: 名前を確定してから書く

Description には Component Set 名・Variant軸名・値名が**そのまま登場する**。

```
選び分け：ルビ不要の画面は tag/requestType。      ← Component Set名
Property：size=…                                  ← Variant軸名
```

**先に Description を書くと、名前を統一した時点で全件書き直しになる。** 順序は次で固定する。

```
① Component Set 名の統一
② Variant軸名・値名の統一
③ Description の整備        ← ここから
```

名前が未確定のまま内容を先行して作る場合は、名前が登場する行（`選び分け` `Property`）に `※命名変更後に要更新` を付けて区別する。

### 着手の順序

全件を一度に埋めない。**選択を誤りやすいものから**着手する。

| 順 | 対象 | 理由 |
|---|---|---|
| 1 | **類似部品のペア** | 誤選択が最も起きる。`tag/requestType` ⇄ `tag_ruby/requestType`、`explainTag` ⇄ `tooltip` |
| 2 | **利用頻度の高い部品** | 影響範囲が広い |
| 3 | **Property の条件に当たる軸を持つ部品** | 設定を誤りやすい |
| 4 | それ以外 | `用途` だけで埋める |

1と2を終えた時点で一度再レビューすると、F1・F2 の改善が数値で確認できる。全件終わるまで待つ必要はない。

Description の追記は**Figmaの構造を変えない**ため、既存Instanceや実装への影響がない。手戻りリスクなしで着手できる。

---

## 7. 補足

- Figma の説明欄の文字数上限は環境によって挙動が異なる場合がある。**長くしすぎない**方針であれば実質問題にならない
- 改行は保持されるが、Markdownの見出し・太字・箇条書き記号は装飾として解釈されない。ラベル形式が最も安全
- 説明を更新したら**ライブラリを再公開**しないと利用側に反映されない
- 用語は組織の公式用語を優先する。一般語へ機械的に置換しない。組織固有語は `用途` 行で1度だけ噛み砕く
