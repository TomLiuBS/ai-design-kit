# Figma Component 作成ルール

Component / Component Set を**新しく作る・更新するとき**に守るルール。

命名ルール（[layer-naming-rules.md](layer-naming-rules.md) [variant-naming-rules.md](variant-naming-rules.md)）が「できたものを直す」ためのものであるのに対し、この文書は「**作る時点でカオスを生まない**」ためのもの。

配置: `guidelines/rules/component-authoring-rules.md`

参照元: UIデザイナー（作成時）、`design-system-audit`（違反の検出）

**このドキュメントは2つの読み手を想定する。** 今は①作成時に参照するUIデザイナー、将来的には②AIがUIをチェックする際の判定基準としても使う。そのため本文（CA-00〜CA-10）はデザイナーが作業しながら読める平易さを優先し、AIによるDSレビュー固有の対応表は末尾の付録にまとめる。

背景: 複数のデザイナーが各自のタイミングでコンポーネントを追加し続けた結果、同じ役割の部品が世代ごとに重複し、Variant軸が使われず名前に情報が詰め込まれる状態が発生した。これを繰り返さないための原則。

**各項目の実データ照合結果（どのDSで何件見つかったか等）はこのファイルには載せない。** 必要なら社内のWiki等にリンクを置く。

このキットの初版。導入先で合意してから正式版とする。

---

## CA-00 Componentにするかどうかの判断基準

Component化すると、CA-01（現行版の管理）・CA-09（マスター編集・承認フロー）・CA-10（ver更新時の凍結手順）のガバナンスコストが発生する。**すべてのデザインをComponent化する必要はない。** そのコストに見合うメリットがあるかどうかで判断する。

| Component化する | Component化しない |
|---|---|
| 複数の画面・複数の場所で繰り返し使われる | その画面にしか存在せず、今後も再利用・AI参照の見込みがない |
| **AIがプロトタイプ生成時に参照する可能性がある**（1回しか使われていなくても） | |
| サイズ・状態のバリエーションをPropertyで管理したい | |

- **「再利用されるかどうか」だけでなく、「AIが参照してプロトタイプを生成しやすくなるか」も判断軸に含める。** 本プロジェクトは、デザイナーの参照しやすさ・一括更新・AIプロトタイプ生成のしやすさを優先し、**最新デザインを極力デザインシステム側に置く**方針を取る
- 迷う場合は「要確認」として提示し、ユーザーの判断を仰ぐ

## CA-01 バージョンは専用の `ver` 軸でのみ管理する

**世代・期・バージョンを、Component Set名・レイヤー名・フレーム名、および`ver`軸以外のVariant軸の値に含めない。** バージョン管理は、**専用の`ver`軸（Variant Property）でのみ**行う。

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| `ポータル_2.0期/deliveryCard`（名前にバージョンを埋め込む） | Component名は`deliveryCard`。バージョンは`ver`軸の値（`1`→`🚫1`、`2`）で管理する |

### `ver` 軸のルール

| 項目 | 内容 |
|---|---|
| 軸名 | **`ver` に統一する。** `version` `バージョン` `期` 等の表記ゆれは`ver`へ寄せる |
| 値の形式 | **単位語（`ver`・`期`等）を含まない数字のみ**（❌ `ver2.1` `2期` → ✅ `2.1` `2`）。整数・小数などの数字自体の形式はアプリごとに異なってよい |
| 旧バージョンの示し方 | 値の冒頭に **`🚫`** を付ける（[variant-naming-rules.md](variant-naming-rules.md) V-08） |
| 現行バージョン | **`ver`軸を持つSetでは、常に非`🚫`の値をちょうど1つに保つ。** 複数の非`🚫`値が同時に存在する状態は違反（どちらが現行か不明になるため）。**「ちょうど1つ」は、`ver`以外の軸の値の組ごとに数える。** 例：`type=expense`の現行が`2.0`、`type=travel`の現行が`2.21`（`2.0`は`🚫2.0`）なら、組ごとに非`🚫`が1つなので適合 |

この方式がCA-10で定める「新しいverへの更新手順」の標準的な実行方法になる（詳細はCA-10参照）。

**新旧の管理方法（まとめ）**

- Component Set名・レイヤー名・フレーム名には、現行版・旧版を問わずバージョンを一切含めない
- バージョンの区別は`ver`軸の値（`🚫`の有無）だけで行う
- **同じ役割の部品を、世代ごとに新規作成しない。** 既存を更新し、`ver`軸に新しい値を追加する

### 業務ドメインの分類軸・`ver`軸以外への混入は禁止対象

禁止するのは、**バージョンを`ver`軸以外の場所（名前・他の軸の値）に混ぜること**であって、業務上の分類や、`ver`軸そのものを使うことではない。

| | 例 | 扱い |
|---|---|---|
| バージョンを他の軸の値に混ぜる | `type=card_ver2.0` | ❌ 禁止（`type=card` と `ver=2.0` に分離する） |
| バージョンを`version`等の非標準軸名で管理する | 軸名 `version` `バージョン` `期` | ❌ 禁止（軸名は`ver`に統一する） |
| バージョンを`ver`軸の値として管理する | `ver=2`、旧版は`ver=🚫1` | ✅ 可 |
| **業務ドメインの分類** | `app=expense/attendance/workflow`（社内ポータル＝各アプリの情報をまとめて表示するアプリ） | ✅ 可 |

**見分け方**：新しいバージョンが出ると古いものは使われなくなる → バージョン（`ver`軸でのみ管理）。複数が同時に使われ続ける → 分類（`ver`軸とは別の軸でOK）。迷う場合は「要確認」とする。

### 既存コンポーネントの段階的な解消（現実的な運用）

**実データでは、多くのComponentに表記ゆれのあるバージョンが既に入っている。** 全件を一度にルールどおりへ直す前提は取らない。影響度で3段階に振り分け、段階的に解消する。**「除去」ではなく「標準化（`ver`軸・単位語なしの数字・`🚫`）への移行」が目標である。**

| 段階 | 対象 | 対応 |
|---|---|---|
| 1. 新規作成分 | これから作るComponent | **例外なく即時適用**（バージョン管理は`ver`軸のみで行う）。ここで新たな負債を増やさない |
| 2. 既存・単独版 | 対になる旧版が存在しない | 判断不要。**名前からバージョン文字列を除去し、`ver`軸へ単位語なしの数字として移す**だけで即修正可 |
| 3. 既存・複数版が共存 | 同じ役割の部品が世代違いで複数存在する | 一度に全部は解決しない。**利用状況（Library Analyticsのインスタンス数等）で優先順位をつけ**、現行の1つを除き`ver`軸の値に`🚫`を付けながら、**定期的な棚卸し（例：四半期に一度）**で`ver`軸・数値形式への標準化を計画的に進める |

- 段階3が未確定の間は、既存のバージョン付き名前のまま残してよい（無理に急がせない）。ただし**新規Instanceの複製元にはさせない**
- リネーム自体（Component Set名・Variant軸/値）はFigma上で低リスク（既存Instanceは追随し、表示・構造は変わらない）。ボトルネックは技術的リスクではなく「どれを現行にするか」の判断コスト
- **どちらを正本とするかは、AIが自己判断しない。** AIは利用状況（Library Analyticsのインスタンス数等）を証拠として提示するところまでを行い、最終判断は必ずユーザーが行う（詳細はCA-10参照）

## CA-02 分類は Variant軸で表す。名前に詰め込まない

**サイズ・状態・種別・真偽などの違いは、Variant軸で表現する。** `/` 区切りやアンダースコアで名前に埋め込まない。

| ❌ 悪い例 | ✅ あるべき姿 |
|---|---|
| `ポータル_1期/sm_list(選択ボタンあり)/Unselected/共通` | Component `deliveryCard` の Variant軸：`size=small` `selectable=true` `state=unselected` |

**判定の目安**

- 名前に `/` やアンダースコアで区切られた要素が複数あり、それぞれが「サイズ」「状態」「種類」を表しているなら、**Variant軸に分けるべき**
- 名前に埋め込まれた分類は、AIが軸として扱えない

**注意**：`/` によるカテゴリ階層（[variant-naming-rules.md](variant-naming-rules.md) V-06）は許容される。禁止するのは「Variantで表すべき差分を名前に入れること」。

## CA-03 同じ役割の重複を作らない

**同用途のComponentが既にないか、作る前に確認する。**

| ❌ 悪い例 | ✅ あるべき姿 |
|---|---|
| 同じ「モーダル」を指す`modal`という名前で、構造の異なる2つのComponent Setが別々に存在する | 検索して既存の`modal`を見つけ、新規作成せず既存を更新する。派生が必要なら`modal/confirm`のように役割が分かる名前で分ける |

- 検索して同名・類似名がないか確認する
- あれば**新規作成せず既存を更新**する
- 世代・期・チーム都合で別Componentを立てない

既に重複がある場合は、現行を1つに定め、他を Deprecated 化する。

### 役割が同じ部品を複数のSetに分ける場合

**原則は「1つの役割＝1つのSet」にする。** Setを分けると、AIが名前で探すときに複数のSetを見ることになり、軸で表せる差を名前に入れることにもなる（CA-02）。

**分けるのは、ファイルが重くなるときに限った例外（イレギュラー）として許容する。** ファイルが重くなること以外の理由では分けない。分けるかどうか、何Variantで分けるかは、人が個別に判断して決める（基準の数は定めない）。

分けるときは次に従う。

- 分ける軸は、**1つのInstanceの中で切り替わらない軸**にする（例：`app`）
- Set名は「基本名＋分けた軸の値」にする（例：`card` → `cardExpense`）。V-06に従い、略語・記号は使わない
- 分けたSetの、残りの軸の名前と値は、すべてのSetで同じにする
- 各SetのDescriptionに、「同じ役割の分割Set」であることと、分割したすべてのSet名を書く
- **既存の分割Setは対象外。** 統合を求めない（既存のInstanceに影響するため）。名前が「基本名＋軸の値」の形でなくても違反にしない

- ✅ `app` で分け、残りの軸（`size` `state`）が全Setで同じ ／ ❌ 同じ役割のSetが、軸の構成も名前の規則もばらばらに複数ある（新規作成分）

## CA-04 軸名・値・Property名はルールに従う

作成時点から次に従う。後から直す手間をなくす。

| 対象 | 要点（詳細は各ルールを参照） | ルール |
|---|---|---|
| Variant軸名・値 | 状態を表す軸は `state` に統一する。size は7段階の規定値（`xxlarge`〜`xxsmall`）を使う | [variant-naming-rules.md](variant-naming-rules.md)（V-04・V-05・V-01） |
| Property名 | ASCII英語の lowerCamelCase にする（例：`isOpen`）。真偽の名前は `is〜` `has〜` `show〜` だけ | [variant-naming-rules.md](variant-naming-rules.md)（V-07） |
| レイヤー名 | 英語の lowerCamelCase にする。Figmaのデフォルト名（`Frame 1` 等）を残さない | [layer-naming-rules.md](layer-naming-rules.md) |
| Component Set 名 | lowerCamelCase・略語禁止・機能語を先に置く（例：`closeButton`） | [variant-naming-rules.md](variant-naming-rules.md)（V-06） |

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| 軸名 `Property 1`、値 `Variant2` | 軸名 `direction`、値 `horizontal` / `vertical` |

- **単一値の軸を作らない**（`option=modal` の1値のみ等）。軸にする意味がない
- **1つの軸に複数の概念を混ぜない**（`size` にサイズと配置を入れない）

## CA-05 Description を書く

Component Set を作ったら、[description-format.md](description-format.md) の形式で説明を書く。

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| Description欄が空のまま公開する | `用途：`から始まる形式で、用途（必須）を書き、条件に当たる場合は選び分け・Property・禁止も書いてから公開する |

- 空のまま公開しない
- 名前が確定してから書く（後で名前を変えると書き直しになる）

## CA-06 作ったら状態を明示する

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| 非推奨の識別に`_old`のような独自の接尾辞を使う | 非推奨は`🚫`（または Figma の Deprecated 機能）に統一する |

- 正式版・試験版・非推奨を、Figma の機能または `🚫` で識別できるようにする
- どれが正本か、名前と状態から判断できるようにする
- **非推奨の識別は `🚫` に統一する。** `_old` 等の独自の接尾辞を使わない
- **`🚫`を付けるのはComponent Set名か`ver`軸の値とする**（Setに属さない単体Componentは名前）。新しいデザインで`ver`を追加したら、そのたびに旧`ver`に付ける（CA-10）。`ver`以外の軸の値には付けない（[variant-naming-rules.md](variant-naming-rules.md) V-08）

## CA-07 軸の意味を取り違えない

軸名は人によって解釈がぶれる。主要な軸の意味を固定する。

| 軸 | 表すもの | 表さないもの |
|---|---|---|
| **`state`** | **パーツの状態**（`normal` / `hover` / `disabled` / `focused` / `pressed` / `selected` / `unselected` など。値は [variant-naming-rules.md](variant-naming-rules.md) V-05-2 の一覧から選ぶ。`default` `on` `off` は使わない） | 表示内容の切替、種別、サイズ、世代。これらを `state` に入れない |
| `type` | 種別・種類。1つのComponent Setに1つだけ（V-04-5） | 状態、サイズ |
| `size` | サイズ（[variant-naming-rules.md](variant-naming-rules.md) V-05-1 の7値） | 用途、レイアウト、配置 |

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| `state=カード` `state=フォルダ`（種別を`state`に入れている） | `type=カード` `type=フォルダ`（種別は`type`で表す） |

- 1つの軸に複数の概念を混ぜない（CA-04）。特に `state` は状態だけに使う
- 選択・オン/オフを持つ部品は、選択状態を `state`、操作状態を `isHover` `isDisabled` `isFocused` `isPressed`（値が `true` / `false` の真偽の軸）に分ける（[variant-naming-rules.md](variant-naming-rules.md) V-05-2）
- 選択中は `selected`、非選択は `unselected`。`current` は「いま表示している位置」を示すセグメント・タブ・ページ送り・ナビゲーション項目だけに使う（V-05-2）

## CA-08 Variables の適用（余白は必須）

Component 内の余白（Padding・Gap）・角丸・色・文字は Variables / Style で指定する。対象・除外するもの・判定の条件・どのコレクションから選ぶか・直し方は [variables-rules.md](variables-rules.md) に従う。

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| Paddingに生値（`16`）を入れる | Paddingに `Spacing/16` を付ける |

## CA-09 インスタンスは編集しない

配置したインスタンスで直接変えてよいのは、**基本テキスト・アイコンと、次の例外の一覧にあるものだけ。**

| 区分 | 内容 |
|---|---|
| **上書きしてよい** | ①色（Variable を適用する）②余白（Padding・Gap）③Auto Layout の並びと間隔 ④サイズ |
| **上書きしてはいけない** | レイヤーの追加・削除・並べ替え。Detach（切り離し）。生値の直指定（CA-08・[variables-rules.md](variables-rules.md) に従う。色・余白の上書きでも Variable を使う） |

- 上の「上書きしてよい」一覧にない項目は、上書きしない。一覧への追加は人が判断する
- **上書きは一時的なものとする。マスターを更新したときは、上書きを「リセット」してマスターを反映する。** 上書きが必要なら、リセットのあとにもう一度行う
- 同じ上書きを繰り返し使う場合（例：少し変えたプライマリーカラーが何画面にも出る）は、Variant かマスターへの昇格を人が判断する
- 上書きしてよい項目で表せない違いは、ガイドライン側のマスターコンポーネントを修正し、承認を経て反映する（`apply-fixes` 相当の手順）

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| インスタンスの色を生値で上書きする。レイヤーを追加・削除する。Detach する（Detached copy＝Figma上でマスターとの紐付けが切れた複製と同じ状態になる） | 色に Variable を適用して上書きし、マスター更新時にリセットしてから必要なら上書きし直す |

- 一覧の外の上書きや Detach をすると、マスターとの連携が壊れる。一覧の中の上書きも、リセットしないとマスターの更新がインスタンスへ波及しない

## CA-10 新しいverへの更新手順（過去のデザインを凍結する場合）

Componentを新しいデザイン（新ver）に更新したいが、**過去のデザインを参照しているファイル・画面は変更したくない**場合の手順。

### 背景：なぜ「直接編集」だけでは解決しないか

FigmaのInstanceは、マスターComponent（または特定のVariant）の定義を共有している。**マスターを直接編集すると、それを参照している全てのInstance（過去のファイルも含む）が同時に新しいデザインに変わる。** 「この画面だけ古いままにする」という指定はできない。過去のデザインを凍結する必要がある場合は、次の方法から選ぶ。

### 既定の方法：`ver` 軸 + `🚫`

**Component・Component Setの標準的な更新方法は、CA-01で定めた`ver`軸を使う方法である。** 他の方法（①〜④）は、`ver`軸が使えない場合（Component化されていない一回限りの画面など）の代替手段として位置づける。

1. 対象のVariantを**Set内で複製**する
2. 複製元（旧デザインのまま）の`ver`軸の値に `🚫` を付ける（例：`2` → `🚫2`）。ジオメトリは変更しない。既存Instanceはこのリネームに追随するだけなので、見た目は変わらず凍結される
3. 複製した方（新しいデザインに編集する方）の`ver`軸の値を、次の番号にする（例：`3`）
4. 今後新しく配置するInstanceは非`🚫`の値（最新の`ver`）を選ぶので、自動的に新デザインになる
5. 旧デザインを見たいInstanceは、Property操作で`🚫`付きの`ver`値に手動で切り替えられる（可逆）

| 観点 | 内容 |
|---|---|
| Component数 | 増えない（Set内で完結） |
| 可逆性 | 可逆（Propertyの値を切り替えるだけ） |
| 前提条件 | 対象がVariantを持つComponent/Component Setであること |
| 一括更新 | ライブラリの一括更新をそのまま使える（①のような保留は不要） |
| 注意点 | 更新を繰り返すと`🚫`付きの値が蓄積する。CA-01の段階的な解消に従い、利用がゼロになった値は定期的に削除する |

### `ver`軸が使えない場合の代替手段（①〜④）

Component化されていない一回限りの画面（作業用ファイル／納品用ファイルの運用）や、Variant軸では表現できない構造変更の場合は、次の方法から選ぶ。

| 方法 | Component数 | 可逆性 | 前提条件 | Property操作の継続 |
|---|---|---|---|---|
| ①ライブラリ更新の保留 | 増えない | 可逆 | Componentが**別ファイルの公開ライブラリ**から読み込まれていること | 可能 |
| ②インスタンスのデタッチ（切り離し） | 増えない | **不可逆** | なし（ローカルComponentでも可） | 不可（通常レイヤーになる） |
| ③Component/Component Setの複製（フォーク） | 増える | 可逆に近い | なし | 可能 |
| ④ライブラリ化への移行 | （移行後）増えない | — | ローカル運用かつ更新頻度が高い場合の恒久対策 | — |

### 判断フロー

```
Variantを持つComponent/Component Setの更新か？
├─ Yes → 既定の方法（ver軸＋🚫）を使う
└─ No（Component化されていない一回限りの画面、または構造自体の変更）
    └─ Componentがライブラリ経由で読み込まれているか？
        ├─ Yes → ①を基本とする
        │         過去verを永久凍結したい場合は、運用ミス対策として②も併用する
        └─ No（ローカルComponent）
            └─ 更新頻度は高いか？
                ├─ Yes → まず④（ライブラリ化）を検討する。移行までの応急処置は過去verの扱いに応じて②/③
                └─ No（低頻度・一度きり等）
                    └─ 過去verの今後の扱いは？
                        ├─ 永久凍結でよい → ②デタッチ
                        └─ 段階的に移行したい（Propertyで運用し続けたい） → ③フォーク
```

#### ①ライブラリ更新の保留

- マスターを編集し、ライブラリを新バージョンとして再公開する
- 過去のデザインを残したいファイルでは、Assetsパネルの「更新」を**押さない**
- **自動では強制されない。** 該当ファイルに「このファイルは意図的に更新を保留している」ことを明記する運用を徹底する（Description・ファイル名・ページ名等）。他の人が誤って「すべて更新」を押すと、過去のデザインも書き換わる

#### ②インスタンスのデタッチ（切り離し）

- 凍結したいInstanceを選択し、「インスタンスの切り離し」を実行する
- 切り離し後は通常レイヤーになり、マスターとの連携が完全に切れる
- **不可逆。** Componentに戻すことはできない。やり直すには新規Instanceを作り直すか、Figmaのバージョン履歴から復元する
- 実行前に、ページの複製やバージョン履歴への名前付き保存で保険をかけておく

#### ③Component/Component Setの複製（フォーク）

- 現行のComponent（またはComponent Set）を複製し、複製した方を新しいデザインに編集する。これが新しい「現行版」になる
- 元のComponentには一切触らない。過去のファイルはそのまま元を参照し続ける
- 今後新しく作る画面・更新したい画面だけ、Instanceの参照先を新しいComponentへ手動で差し替える（Swap instance）
- 移行が落ち着いたら、元のComponentに`🚫`（非推奨マーカー）を付ける（CA-06・[variant-naming-rules.md](variant-naming-rules.md) V-08）
- **デメリット：Component数が増える。** ③を繰り返す運用が続く場合は④（ライブラリ化）を検討する

#### ④ライブラリ化への移行

- ローカルComponentで更新頻度が高い場合、③を繰り返すとComponent数が際限なく増え続ける
- 恒久対策として、該当Componentを別ファイルの公開ライブラリへ切り出し、①の運用に移行することを検討する

### Component化していない一回限りの画面にも同じ原則が適用される

Component化の有無に関わらず、**「常に最新であるべき場所」と「特定時点で凍結する場所」を分ける**という原則は共通する。

- 作業用ファイル：常に最新の設計意図を反映する場所
- 納品用ファイル：ある時点でコピーして固定した記録。納品後は編集しない

納品後に変更が必要になった場合は、作業用ファイルを更新し、改めて新しい納品版としてコピーし直す。**納品用ファイルを直接編集しない。**

### 複数版が共存している場合、AIは正本を自己判断しない

CA-01の「既存コンポーネントの段階的な解消」（段階3）で複数版が共存していることが分かった場合、**AIは利用状況（Library Analyticsのインスタンス数等）を証拠として提示するところまでを行い、どちらを正本とするかの最終判断はユーザーが行う。** 使用頻度等から仮の正本案を提示することもしない。

## 付録：AIによるDSレビュー（design-system-audit）での対応表

**ここから先はUIデザイナーが作成時に読む必要はない。** AIによるDSレビュースキル（`design-system-audit`）が、どのDSレビュー項目でCA違反を検出するかの対応表。

| 違反 | DSレビュー項目 |
|---|---|
| バージョンが名前、または`ver`軸以外の値に埋め込まれている（CA-01） | B2（Variant値）／ C1（Component名） |
| 分類が名前に詰め込まれ、軸が使われていない（CA-02） | **B1（Variant軸の設計）** |
| 同役割の重複（CA-03） | A3（正本と公開状態） |
| 軸名・値・名前のルール違反（CA-04） | A5 / B1 / B2 / C1 / C4 |
| Description 空（CA-05） | F1 / F2 |
| `🚫`が`ver`の値・Component Set名・単体Component名以外にある（CA-06、V-08） | B2（値）／ C1（名前） |

**CA-02 の「軸を使わず名前に詰め込む」は、リネームで直らない構造問題である。** DSレビューでは「要判断リスト」に回し、Variant軸への作り直しとして扱う。機械的変換の対象にしない。
