# Variant・Component 命名ルール

Component Set 名、Variant 軸名、Variant 値、Property 名の形式を定めるルール。

**AIが名前を文字列で指定して部品を選び、Property を操作できること**を目的とする。1文字違えば一致しないため、意味が通っていても表記が揺れていれば違反とする。

配置: `guidelines/rules/variant-naming-rules.md`

参照元: `design-system-audit`（A5・B1・B2・C1の判定）

**このルールは複数の生成AI（Claude Code / Codex / Figma Agent）が参照する。** ランタイム側で別基準を定義しない。

> **このファイルはこのキットの初版です。** 導入先で合意してから正式版とします。実データ照合の詳細（日付・DS名・件数）はこのファイルには載せません（必要なら社内のWiki等にリンクを置く）。

## 「軸」と「Property」の関係

Figma の Component Property には5種類ある（Variant／Boolean／Instance Swap／Text／**Slot**）。このうち本文書で**「軸」と呼ぶのは Variant 型の Property だけ**を指す。

| 章 | 対象 | 内容 |
|---|---|---|
| V-04・V-05 | **Variant型のProperty（＝軸）のみ** | 軸の意味・共通軸リスト・size/状態などの値の表記 |
| V-07 | **すべてのProperty型に共通** | lowerCamelCase・Boolean接頭辞など、名前の表記ルール |

**Slot型について**：メインコンポーネント内に「自由に内容を追加・入れ替えできる領域」を作る機能。Instanceとは別物で、レイヤー自体はInstanceではない（[layer-naming-rules.md](layer-naming-rules.md) R-01〜R-10の対象に含まれる）。SlotにもPropertyとして独自の名前があり、V-07（lowerCamelCase等）が適用される。Slot固有の命名はV-07-4に従う

つまり「軸」は「Property」の中の1タイプであり、V-07の表記ルールはBoolean/Instance Swap/Text型のPropertyにも適用される。

## 1. ルール一覧（V-01〜V-09）

### V-01 size の値

```
xxlarge / xlarge / large / medium / small / xsmall / xxsmall
```

- コンポーネントごとの px と利用場面は、DSのガイドライン（`guidelines/kit/DESIGN.md`）で定める
- **`extralarge` `md` `sm` `lg` `S` `M` `L` `Default` `xx-small` `xx-large`（ハイフン有無の揺れ）はすべて規定外**
- 規定に合っている値を、実装の多数派でないという理由で違反にしない

### V-02 角丸の値

```
xxlarge / xlarge / large / medium / small / xsmall / xxsmall / full
```

- 出典: DSのガイドライン
- 先頭は小文字に統一する
- size（V-01）とは別の軸。`full` を除き値の語は同じだが、軸ごとに定義し、互いの値を流用しない
- 旧表記からの変換：`Small`→`small`、`Medium`→`medium`、`Large`→`large`、`Full`→`full`（先頭を小文字にするだけ）。`xxlarge` `xlarge` `xsmall` `xxsmall` は新設の値
- 各値のpx値との対応は本ルールでは定めない（Tokenの定義で管理する）

### V-03 影（Elevation）の値

```
型: [アプリ・UI名称-]影の大きさ[-影の向き]
影の大きさ: low / mid / high
影の向き:   down / left / right
例: high / high-right / 承認フロー-high / cursor-high / portal-low
```

- 出典: DSのガイドライン（値の表記は本ルールで統一する）
- **アプリ・UI名称と影の向きは任意。** 大きさだけの値（`high`）も正しい
- **先頭は小文字に統一する。** スペース・括弧 `[ ]` は使わない。区切りは `-` のみ（旧表記 `[High - right]` → `high-right`）
- **アプリ名・UI名称は英語（アプリ名はローマ字を含む）**にする。ただし**アプリ内の機能名は日本語で表記してよい**（`承認フロー-high`。layer-naming-rules R-02の機能名の例外と同じ。`-` で区切られた部品ごとに言語が分かれていても混在とみなさない）
- アプリ固有の旧表記は新しい型に置き換える（例：`カーソルhigh` → `cursor-high`、`ポータル専用 low` → `portal-low`、`ポータル専用 high` → `portal-high`）
- 影の向きの語彙は現行の3語のまま。`up` 等は実データで必要になった時点で追加する
- **ガイドライン自体がアプリ固有の例外を持つ。** 共通の値に合わないことを、確認せず違反としない
- 本変更はルールの定義のみ。Figma上の既存の値は書き換えない（ルールづくり段階）

### V-04 Variant 軸名の形式

#### V-04-1 状態を表す軸は `state` に統一する

`status` `States` `states` `Status` `プロパティ1` はすべて `state` に統一する。

**`state` は「パーツの状態」を表す軸である。** 解釈が人によりぶれるため、意味を `component-authoring-rules.md` CA-07 に明記した。用途（表示内容の切替など）を `state` で表さない。

- **軸名を`state`に統一するだけでなく、値自体が状態を表しているケース**（軸の値そのものが状態名になっている）は機械変換できないため、値の再設計を個別に「要確認」として扱う

#### V-04-2 共通軸は英語で標準化、業務固有軸は日本語を許容

複数DSで頻出する軸は**英語で標準化**する。特定アプリ・特定業務でしか使わない軸は**日本語を許容**する。

**現時点の共通軸一覧**（このリストは今後も増える前提で運用する）

| 標準軸名 | 用途 | 値 |
|---|---|---|
| `type` | 種別。primary / secondary / tertiary などの強調度合いも`type`で表す（`priority`・`hierarchy`は使わない）。1つのComponent Setに1つだけ（V-04-5） | 自由 |
| `state` | パーツの状態（V-04-1） | V-05-2 の2つの一覧から選ぶ |
| `size` | サイズ | V-01 の7値 |
| `background` | **パーツが置かれる場所の背景の明暗**（パーツ自身の背景色は表さない） | `light` / `dark` / `common`。`light`＝明るい背景の上で使う見た目、`dark`＝暗い背景の上で使う見た目、`common`＝背景によらず同じ見た目（例：destructiveButton）。❌ `dark` を「パーツ自身の背景が暗い」の意味で使う → ✅ 暗い背景の上に置くパーツの種類を `dark` にする |
| `color` | 色 | 英語の色名：`red` `orange` `yellow` `green` `blue` `purple` `pink` `black` `white` `gray`（`grey` は不可） |
| `<業務軸>`（例：`approvalStatus`） | サービスの業務ドメインで複数DSに共通する分類（導入先で定義する） | 値の言語は本節の基準に従う。日本語にする場合は [layer-naming-rules.md](layer-naming-rules.md) R-02 の許容語リストの語 |
| `direction` | 向き・角度 | `horizontal` / `vertical`、および角度（`left` または `right` ＋度数。例：`right45` `left30`）。それ以外（`0` `front` 等）は「要判断」 |
| `page` | どの画面・タブの中で使う部品か | 画面名。日本語を許容する。1つの軸の中では全て英語か全て日本語にする |
| `isHover` `isDisabled` `isOpen` `isFocused` `isPressed` | 操作状態・開閉を切り替える真偽の軸（V-07-2） | `true` / `false` のみ |
| `app` | 業務ドメインとしての対象アプリ（例：社内ポータルが表示する経費精算／勤怠／ワークフローの各アプリ）。世代・バージョンには使わない（CA-01）。`service`・`領域`・`Name` は本軸の表記ゆれ＝`app` へ寄せる | **アプリ名は日本語を許容せず、英語（ローマ字表記を含む）に統一する**（❌ `経費精算` `勤怠` `ワークフロー` → ✅ 英語コードネーム・ローマ字表記。既存の`expense` `attendance` `workflow`のような英語コードネームと表記体系を揃える。キャラクター名などアプリ名でないものは不可）。**ただし、アプリ内の機能名（例：`<機能名>`）はアプリ名ではないため、日本語で表記する** |
| `role` | 利用者ロール（管理者・メンバー・閲覧者）。`user` `Actor` `actor` は本軸の表記ゆれ＝`role` へ寄せる | `admin` / `member` / `viewer` / `common`。日本語（管理者/メンバー/閲覧者）・ローマ字（kanrisha/etsuransha）は不可 |
| `breakpoint` | 画面幅の切り替え（V-05-1）。`size`（コンポーネント自身の大きさ）とは別軸 | 値セットは未確定＝要判断 |
| `ver` | **バージョン管理専用軸**（V-04-3） | 単位語を含まない数字のみ。旧バージョンには`🚫`を付ける |

- 上記の概念には**必ずこの軸名を使う**。表記ゆれ（例：`Role`）は標準名へ寄せる
- **`isHover` `isDisabled` `isOpen` `isFocused` `isPressed` は、Variant型の軸で値が `true` / `false` の2つだけのもの**（Figma上はスイッチで指定する）。`state` のようにプルダウンで名前付きの値を選ぶ軸とは別。Boolean Property（レイヤーの表示/非表示）ではない（V-07-2）
- **同じ軸名は同じ意味で使う。** `type` のような共通軸名を複数のコンポーネントで使う場合、指す意味を統一する。コンポーネントごとに全く異なる意味（例：業務分類／表示形式／件数種別）を1つの軸名に持たせることは違反とする。意味が異なる場合は別の軸名にするか、「要確認」として報告する

**同一軸内で英語・日本語を混在させない。** 1つの軸の値は、全て英語か全て日本語かのどちらかに統一する。

| ❌ 悪い例（実例） | ✅ 修正方針 |
|---|---|
| `role`軸に`admin`/`member`/`閲覧者`が混在 | `admin`/`member`/`viewer`に統一 |
| アイコン系`プロパティ1`軸に`score`/`pencil`/`file`/`share`/`submit`（英語）と`フォルダーアイコン`（日本語）が混在 | `フォルダーアイコン`→`folderIcon`に統一 |
| ページ送りコンポーネントの`size`軸に`md`/`sm`（英語）と`左端`/`右端`（日本語）が混在 | `左端`/`右端`→`leftEdge`/`rightEdge`等に統一 |
| 1つの値の中で英語と日本語が結合（`primaryデフォルト`、`AI_承認`） | `primaryDefault`、`aiApproved`のように値自体を単一言語にする |
| `type`軸に`default` `plus`（英語の汎用値）と`承認` `却下` `差戻し` `完了`（日本語）が混在 | `default` `plus` `approved` `rejected` `returned` `done`に統一 |

**英語の汎用値と同じ軸に並ぶ場合は、許容語（業務固有語）に当たる日本語の値も英語にそろえる。** 日本語のまま残せるのは、軸の値がすべて日本語のときだけ。

**混在が見つかった場合、デフォルトでは英語への統一を提案する。** 業務固有語で英訳すると意味が伝わりにくいと判断される場合のみ、全体を日本語に統一する逆方向を検討し、「要確認」として提示する。

**類似・同系統のComponent Set間でも、同じ概念に英語と日本語を混在させない。**

| ❌ 悪い例（実例） | ✅ 修正方針 |
|---|---|
| `appIcon`配下でアプリ名が`expense`/`attendance`/`portal`（英語）と`稟議`/`ワークフロー`/`お知らせ`（日本語）に混在 | `app`軸の方針（英語に統一）に従い、日本語側を英語コードネームへ置き換える |

同じ概念を指す非標準の軸名（例：`領域`が`app`軸と同じ業務ドメインを指している）が別に存在する場合、標準軸名への統合を提案する。

**追加候補（審査待ち）** — 実データ調査で見つかった、まだ共通軸に昇格していない候補。**このリストは随時増える。** 新しい候補が見つかったらここに追記し、昇格の可否は人が判断する

| 候補軸名 | 想定用途 | 状態 |
|---|---|---|
| （現時点なし） | | |

**追加・昇格の判断基準**

| 出現状況 | 扱い |
|---|---|
| **2DS以上で同じ用途** | **共通軸に昇格**。英語 lowerCamelCase で「現時点の共通軸一覧」に追加し、更新履歴に記録 |
| 1アプリ限定・業務固有 | 日本語許容のまま。共通軸にしない |
| 1アプリだが明らかに汎用（今後も使う見込み） | 「追加候補（審査待ち）」に記録し、判断を仰いでから昇格 |

**無条件に共通軸へ足さない。** 1アプリだけの軸を昇格させると、リストが肥大化して基準にならなくなる。

**業務固有軸（日本語を許容する）** — 1アプリ・特定業務でしか使わず、英語化すると意味が伝わりにくいもの。**アプリ名（`app`軸）は対象外**（英語に統一。上記参照）。

- 例：`承認状態` `決裁区分` `緊急度`
- 導入先のDS実データで確認された例をここに記録する（随時更新。例：`approvalStatus`軸の`承認` `却下` `差戻し`）
- lowerCamelCase 化を強制しない。ただし**綴り・表記は統一する**
- コード生成時の識別子は、対応表（Claude Code版 I4）で解決する

**判断基準**：「他アプリでも使いそうか」。使いそうなら英語で標準化、その業務専用なら日本語可。迷う場合は「要確認」とする。

#### V-04-3 バージョン・世代は専用の `ver` 軸でのみ管理する

**バージョン・世代の管理は、専用の`ver`軸に限定して許容する。** それ以外の軸名（`version` `バージョン` `期` 等の表記ゆれ）や、`ver`以外の軸の値にバージョンを混ぜることは禁止（[component-authoring-rules.md](component-authoring-rules.md) CA-01）。

| 項目 | 内容 |
|---|---|
| 軸名 | **`ver` に統一する。** 既存の`version` `バージョン` `期`等の軸名は`ver`へ寄せる |
| 値の形式 | **単位語（`ver`・`期`等）を含まない数字のみ**（❌ `ver2.1` `2期` → ✅ `2.1` `2`）。整数・小数などの数字自体の形式はアプリごとに異なってよい |
| 旧バージョン | 値の冒頭に`🚫`を付ける（V-08）。**常に非`🚫`の値をちょうど1つに保つ。** 「ちょうど1つ」は、`ver`以外の軸の値の組ごとに数える（[component-authoring-rules.md](component-authoring-rules.md) CA-01）。例：`type=expense`の現行が`2.0`、`type=travel`の現行が`2.21`（`2.0`は`🚫2.0`）なら適合 |

- **`ver`軸は必須ではない。** 新しいデザインに更新するときに追加する。`ver`軸を持たないSetは「非`🚫`がちょうど1つ」の対象にならない（違反にしない）
- **既存のSetに`ver`軸を追加するのは軸の追加（構造の変更）にあたる**ため、人が判断する（第4節）。実行する場合は検証用ブランチで確認してから行う

この`ver`軸が、[component-authoring-rules.md](component-authoring-rules.md) CA-10で定める「新しいverへの更新手順」の標準的な実行方法になる。

#### V-04-4 汎用名の軸を使わない

`Property 1` `プロパティ1` は**意味を表す軸名へ個別リネーム**する。値から用途を判断して命名する（例：値が vertical/horizontal なら `direction`）。**機械変換できないため「要判断」とする。**

- 綴り違いや連番の汎用軸（`propaty` `Property 2` `プロパティ2` `プロパティ3/4/5`）も本項の対象とする
- **Variant値のFigmaデフォルト名（`Component 58` `Frame 174075` `Union`）や連番の仮値（`バリアント2` `status4`）も同様に意味を表す値へ**。命名は値から用途を判断する＝要判断

#### V-04-5 軸名のつけ方

**軸名は、意味が1つに決まる具体的な名詞にする。** AIは軸名の文字列で軸を指定するため、意味が広い語では何を切り替える軸か判別できない。

- **1つのComponent Setで、同じ軸名を2回使わない。** 大文字小文字違い（`type` と `Type`）や連番（`type2`）も重複とみなす
- **`type` は1つのComponent Setに1つだけ。** 「種類」の軸が2つ必要なときは、2つ目以降を具体的な名詞にする（❌ `type` + `type2` → ✅ `type` + `shape`）
- **次の汎用語は軸名にしない：** `style` `category` `pattern` `mode` `kind` `variant` `option` `status` `orientation`。意味が広く、`type` や既存の軸と区別できないため
- **略語は軸名にしない**（❌ `btn` `bg`）。共通軸の `app` `ver` だけが例外
- `Property 1` などの汎用名・大文字始まり・綴り誤り・記号入りは V-04-4・V-07-1 に従う

| NGの軸名 | 直し先 | 扱い |
|---|---|---|
| `status` `states` `Status` | `state` | 名前の変更のみ |
| `orientation` | `direction` | 名前の変更のみ |
| `user` `Actor` `actor` | `role` | 名前の変更のみ |
| `領域` `Name` `service` | `app` | 名前の変更のみ |
| `version` `バージョン` | `ver` | 名前の変更のみ |
| `style` `category` `pattern` `mode` `kind` `variant` `option` | `type`、または具体的な名詞の軸 | 要判断（値から用途を判断する） |

### V-05 Variant 値の表記

#### V-05-1 size の値はガイドライン規定に従う

```
xxlarge / xlarge / large / medium / small / xsmall / xxsmall
```

- `lg/md/sm`、`S/M/L`、`Default/SM/XS`、`xs/xxs/xsm/sml`、px直値（`16px` 等）は**すべて規定値へ変換**する
- 変換の対応：`lg`→`large`、`md`→`medium`、`sm`→`small`、`xl`→`xlarge`、`extralarge`→`xlarge`、`S`→`small`、`M`→`medium`、`L`→`large`、`Default`→`medium`（通常サイズ相当。実寸が異なる場合は要確認）
- `M_申請一覧` `board_icon` `sm_2rows` のような**サイズ以外の情報が混ざった値**は、size値の統一では直せない。CA-02（軸へ分離）の対象＝要判断

**画面ブレークポイントは `size` に混ぜず、別軸 `breakpoint` で許容する**

`size=1366 / 1200 / 1024` のような**画面幅の値**を、コンポーネント自身の大きさを表す `size` 軸に混ぜない。既存画面への影響が大きいため、画面幅の表現自体は禁止しない。代わりに **`breakpoint` という別軸**を使う（既存画面への影響を踏まえた現実的な運用）。

- `size` はコンポーネント自身の大きさ（上記7値）だけを表す。画面幅を表したい場合は必ず `breakpoint` 軸を使う
- **`breakpoint` の値セットは未確定**（規定する画面幅はDSのガイドラインで定める。既存の`1366/1200/1024`のような値をどう整理するかは別途要判断）。値が決まるまでは、既存の画面幅の値をそのまま`breakpoint`軸へ移す（軸名の変更のみ、値の見直しは別タスク）
- **新規コンポーネントでは、まず Auto Layout でのレスポンシブ対応を優先する。** `breakpoint` 軸は、既存資産の移行や、Auto Layoutだけでは対応できない不連続なレイアウト変化（横並び→縦積み等）がある場合に使う
- コード側ではメディアクエリ・Flex/Grid との対応関係を明確にする

#### V-05-2 状態の値もガイドラインに従う

**`state` の値は、次の2つの一覧から選ぶ。** 一覧にない状態が必要なときは「要確認」とし、一覧への追加は人が判断する。

| 一覧 | 使うパーツ | 値 |
|---|---|---|
| 選択・操作系 | ボタン・チェックボックス・タブなど | `normal` `hover` `disabled` `focused` `pressed` `selected` `unselected` `current` `notCurrent` `partiallySelected` `drag` |
| 入力欄系 | テキストフィールドなど | `empty` `filled` `inputting` `focused` `error` `disabled` |

- **`default` を値に使わない**（`Default` `デフォルト` `defualt` も同じ。すべての軸が対象）。「既定の状態」か「既定の種類」か判別できず、AIが別の値を選ぶため。選択を持たないパーツの基本状態は `normal`、選択を持つパーツの非選択は `unselected` にする。`size` の `Default` は `medium`（V-05-1）。`type` などほかの軸の `default` は、具体的な名前に直す＝要判断
- **`on` / `off` を値に使わない。** トグル・スイッチも `state` の `selected` / `unselected` にする。軸そのものがオン/オフの場合は真偽の軸（V-07-2・V-07-3）にする
- 綴り・表記を統一する：`disable`→`disabled`、`hoverd`→`hover`、`unelected`→`unselected`、`非活性`→`disabled`、`focus`→`focused`、`indeterminate`→`partiallySelected`、`placeholder`→`empty`、`draged`→`drag`、`inputing`→`inputting`
- **`active` は使わない。** 「押している」か「選択中」か判別できないため。押している状態は `pressed`、選択中は `selected` にする（どちらの意味かは要判断）
- **選択を持つ部品は、`state` に選択状態（`selected` / `unselected`）を入れ、操作状態（hover・disabled・focused・pressed）は真偽の軸 `isHover` `isDisabled` `isFocused` `isPressed` で表す**（V-07-2）。選択を持たない部品は、`state` に `normal` `hover` `disabled` などを並べる。**同じ意味を `state` と `is〜` の両方で持たない。** 選択状態と操作状態を1つの`state`に掛け合わせた値（`currentHover` 等）にしない。値の数が掛け算で増え、AIが取り違えるため。既存資産でこの形でないものは、軸の構造変更が要るため対象外とし、段階的に解消する
- **選択中を表す値は `selected`、選択されていない状態は `unselected` にする。** 選択中を `active` `checked` で表さない。同じ意味の値が部品ごとに割れると、AIが別の値を指定して一致しない。
  - ✅ `checkbox` `state=selected/unselected`
  - ❌ `checkboxLabel` `state=active`
- **`current` を使えるのは、次の3つをすべて満たす部品だけ。**
  1. 同じグループの中で、「いま表示している位置」を示す（セグメント、タブ、ページ送り、ナビゲーション項目）
  2. 選ぶと、表示や画面が切り替わる（入力値として選ぶのではない）
  3. グループ内に `current` の項目が必ず1つある（0個や複数にならない）

  当てはまらない部品（チェックボックス、ラジオボタン、選択式リストの項目など、入力として選ぶもの）は `selected` を使う。1つの部品で `selected` と `current` を併用しない。`current` を使う部品の選ばれていない状態は `notCurrent` にする（`default` は「既定で選ばれている」と読まれるため使わない）。
  - ✅ `segmentedControl/item` `state=current/notCurrent`
  - ❌ `checkbox` `state=current`
- **業務固有の状態**（`承認` `却下` `配信中` `申請完了` 等）は、V-04-2 と同じ基準で判断。他でも使う汎用状態は英語化、その業務専用は日本語を許容し表記を統一
- **数字だけの値**（`0`〜`19`）は状態値として不適切。意味のある名前にするか、そもそも Variant が不適切なら CA-02 の対象＝要判断
- **タッチ中心のアプリでも、操作可能なパーツの状態に`hover`を含める**。タッチ中心だからといって`hover`を省略しない

#### V-05-3 バージョンを`ver`軸以外の値に混ぜない

`カード_ver3.0` `ポータル_2.0期` のように、バージョン・世代を他の軸の値に混ぜ込まない（CA-01）。**バージョンの管理は専用の`ver`軸（V-04-3）でのみ行う。** `ver`軸自身の値（単位語なしの数字、旧バージョンは`🚫`）はこの禁止の対象外。

#### V-05-4 使用可能な文字

- ASCII英数字を基本とする（業務固有値の日本語は V-05-2 の範囲で許容）
- 記号（スペース・`:`・`_`・`-`・`↙️↘️`）は使わない。除去は機械変換の規則（第2章参照）に従う
- **`ver`軸の値に限り、小数点`.`を許容する**（例：`2.1`）。他の軸・値では引き続き禁止
- **ローマ字は英語とみなさない**（`kanrisha`/`etsuransha` → `admin`/`viewer`）。英訳する。業務固有で英訳が難しいものは日本語を許容（V-04-2）。個別に承認した外来語（`<承認した外来語>`）は英語として扱う（[layer-naming-rules.md](layer-naming-rules.md) R-01）
- **綴り誤りは違反**（`defualt`→`default`、`eracer`→`eraser`、`avtive`→`active`、`foucus`→`focus`）。判定は [layer-naming-rules.md](layer-naming-rules.md) R-08 に従う
- `🚫` は非推奨マーカー（V-08）として例外的に許容
- **同一軸内で値の大文字・小文字表記を統一する**（❌ 同じ`type`軸内に`Default`と`outline`が混在 → ✅ `default`と`outline`に統一）

### V-06 Component Set 名の形式

#### 原則：階層を使わない

```
closeButton / iconButton / textButton / floatingButton / favoriteButton
```

- **lowerCamelCase**
- **機能語を先、種別語を後ろに置く**（✅ `closeButton` / ❌ `buttonClose`）
- 使用可能な文字は **ASCII英数字と `/` のみ**。ただし、[layer-naming-rules.md](layer-naming-rules.md) R-02の**許容語リストの1語と完全一致する名前は日本語にできる**（例：許容語リストに登録した `稟議`）。許容語は単独で使い、2語以上つなげない（❌ `稟議差戻し`）。許容語以外を含む名前と、許容語をつなげた名前は全体を英語にし、日本語と英語を1つの名前に混在させない
- **略語は禁止。すべてフルスペル**（❌ `fav` `wtext` `btn` → ✅ `favorite` `withText` `button`）
  - レイヤー名も同じく略語は使えない（[layer-naming-rules.md](layer-naming-rules.md) 第5節）。`txt` `img` は `text` `image` にする
  - 理由: Component Set 名は検索対象であり、階層で文脈を補えないため
- 綴り誤りを含めない（❌ `card_thumnails` → ✅ `cardThumbnails`）
- **バージョン番号を含めない**（❌ `card/expense_report(ver3.0)`）。新旧の管理は V-08 の非推奨マーカーで行う
- Figmaのデフォルト名・機械的な連番を含めない
- ローマ字は英語とみなさない。判断できない場合は「要確認」とする（例: `shinseiField`）。個別に承認した外来語（`<承認した外来語>`）は英語として扱う（[layer-naming-rules.md](layer-naming-rules.md) R-01）
- **役割が同じSetを複数に分けるときは [component-authoring-rules.md](component-authoring-rules.md) CA-03 に従う**
- **Component Setに属さない単体Componentの名前も、Component Set名と同じ規則に従う**（❌ `checkboxLabel+text` → ✅ `checkboxLabelText`）。記号・空白・略語・バージョン番号をAIが一意に指定できないため

#### 例外：既存の階層は維持する

すでに `/` 階層で運用されている資産は、**そのまま維持してよい**。階層を外す大規模なリネームは行わない。

```
tag/status   badge/number   card/inbox   badge/alert
```

- **既存の階層を壊す変更は、既存デザインへの影響が読みにくいため実施しない**
- **新規作成時は原則フラット**とする

#### 階層を使う場合のルール

**階層数に上限は設けない。** 大きなコンポーネントでは5階層以上が必要な場合もある。**深さではなく、各階層が分類として機能しているかで判定する。**

| ルール | 内容 |
|---|---|
| 階層数 | **上限なし。** コンポーネントの規模に応じて必要な深さを使う |
| 各階層の意味 | **上位から下位へ絞り込みになっている**こと。各階層が何を表す分類かを説明できること |
| Variantとの切り分け | **Variantで表せる差分を階層にしない。** サイズ・状態・種別のバリエーションは Variant 軸で表す |
| 兄弟間の一貫性 | 同じカテゴリの資産は**同じ深さに揃える**。深さがばらつくと探せなくなる |
| 各階層の表記 | それぞれ lowerCamelCase |
| 重複 | 階層間で同じ語を繰り返さない（❌ `tag/tag_tooltip` → ✅ `tag/tooltip`） |
| 区切り | `/` のみ。アンダースコアと併用しない（❌ `tag_ruby/status`） |

**2階層で作る場合の目安**（既存資産の実例から整理。新規作成時の目安であり、既存の階層に合わせて変更を強制するものではない）

| 階層 | 表すもの | 実例 |
|---|---|---|
| 1階層目 | その部品が属する**機能領域・部品カテゴリ** | `modal` `sidebar` `card` `tag` `badge` |
| 2階層目 | **具体的な部品名** | `searchInputArea` `配信先` `stamp` `status` |

- **3階層目以降が必要な場合**、2階層目が実際に複数の具体的な部品を束ねる分類として説明できることを確認する。「parts」のような部品であること自体しか表さない言葉は分類として認めない＝要確認とする
- **既存の`/`階層は、この目安に合っていなくても変更しない**（V-06「例外：既存の階層は維持する」のとおり）。この目安は新規作成時と、DSレビューで階層の意味を判断するときに使う

**判定の考え方**

| 例 | 判定 |
|---|---|
| `iconButton/menuIcon/largeNumber` | `largeNumber` がサイズ差であれば**Variantで表すべき**。階層にしない |
| `card/request/home/daily` | 各階層が何の分類か説明できれば**可**。説明できなければ「要確認」として報告する |

**階層が深いこと自体を違反としない。** 深さを問題にするのは、階層の意味が説明できないとき、または Variant で表すべき差分が階層になっているときに限る。

#### コード識別子への変換

| Figma名 | コード名 |
|---|---|
| `closeButton` | `CloseButton`（先頭を大文字にするのみ） |
| `tag/status` | `TagStatus`（階層を連結して PascalCase） |

**階層ありと階層なしで変換規則が異なる。** Code Connect を設定する際は、この規則に従う。

階層が深い資産は連結名が長くなる。実装側で短縮名を使う場合は、**Code Connect のマッピングで対応付ける**（Figma側の名前を変えて短縮しない）。

#### 名前の一意性

**Component Set 名は同一ファイル内で一意にする。** 同じ名前で Variant 軸構成が異なるセットが共存してはならない（例：`modal` という名前で 7-variant 版と 3-variant 版が別物として存在する状態は違反。どちらかをリネームするか統合する）

### V-07 Property名の形式（Variant/Boolean/Instance Swap/Text 共通）

#### V-07-1 Property名は ASCII英語の lowerCamelCase

`プロパティ1` `注釈` `テキスト` `Property 1`、絵文字入り（`↙️has icon left`）、スペース入り（`has icon right`）はすべて ASCII英語の lowerCamelCase へ。

- **大文字始まりの軸名（`Type` `State` `Size` `Ver` `Role`）は lowerCamelCase へ**
- **綴り誤りの軸名・Property名も違反**（`propaty`→`property`、`hight`→`height`、`posision`→`position`、`stauts`→`status`）。判定は R-08 に従う

**Figma の Property キーは内部で `名前#1234:5` の形式を持つ。`#` 以降は内部識別子であり、表示名は `#` の前だけ。** 内部IDを命名の問題として扱わない。

#### V-07-2 Boolean の接頭辞

**真偽を表す名前の接頭辞は、`is〜` `has〜` `show〜` の3つだけにする。** 接頭辞がない名前や、これ以外の接頭辞はNG。

| 接頭辞 | 用途 | 例 |
|---|---|---|
| `show〜` | 表示の有無 | `showRuby` `showLeftIcon` |
| `has〜` | 要素・属性の有無 | `hasMargin` |
| `is〜` | 真偽の状態 | `isOpen` `isLoading` |

- すべて lowerCamelCase（`Show Ruby`→`showRuby`、`IsOpen`→`isOpen`）
- ❌ 接頭辞なし（`open` `edit` `scroll` `ruby`）、`on〜`（`onHover`）、動詞始まり（`addLastRow`） → ✅ `isOpen` `isEditing` `isHover` `showRuby`。直し先は値から用途を判断する＝要判断
- `Property 1` のような汎用名は、値から用途を判断して個別リネーム＝要判断

**この規則は、次の3種類のどれにも適用する。** 種類ごとに切り替えるものと値が違う。

| 種類 | 切り替えるもの | 名前 | 値 |
|---|---|---|---|
| 真偽の軸（Variant型。Figma上はスイッチで指定する） | 見た目の状態・開閉 | `isHover` `isDisabled` `isOpen` `isFocused` `isPressed` | `true` / `false` の2つだけ |
| `state`（Variant型。プルダウンで選ぶ） | 状態の種類 | `state` | V-05-2 の一覧の値 |
| Boolean Property | レイヤーの表示/非表示 | `show〜` `has〜` | `true` / `false` |

Boolean Property では、見た目の状態（hover・disabled など）は切り替えられない。見た目の状態は、必ず Variant型の軸で表す。

#### V-07-3 Boolean値の表記

真偽の**値**は `true` / `false`（**小文字**）に統一する。`on` / `off`、`True` / `False`、`On` / `Off` は使わない。

| 対象 | 例 | 値 |
|---|---|---|
| 真偽の軸・Boolean Property（is/has/show 接頭辞） | `isOpen` `hasMargin` `showRuby` | `true` / `false` |
| トグル・スイッチ（ユーザーが選んで保持する状態） | `switch` 等のオン/オフUI | `state` の `selected` / `unselected`（V-05-2） |

- **境界（あるUIを `state` の選択状態とみなすか、真偽の軸とみなすか）は、ユーザーが選んで保持する状態かどうかで判断する＝迷う場合は要確認**

#### V-07-4 Slot名

**Slot名は、入れるものを表す名詞の lowerCamelCase にする**。AIが「何を入れる場所か」を名前から読み取れるようにするため。

- **形式**: 名詞の lowerCamelCase（例：`leftContent` `actionButtons`）。語順は layer-naming-rules R-01の語順細則に従う（修飾語を先、名詞を後）
- **数字で区別しない**（❌ `slot1` `content2`）。区別が必要なら役割で分ける（`leftContent` `rightContent`）
- **Slotが1つなら `content`** にする
- **適用範囲**: SlotのProperty名とSlotのレイヤー名は同じ規則に従う
- **中身のレイヤー**: Slotに入るレイヤーの名前も、layer-naming-rulesの通常ルール（R-01〜R-10）に従う

### V-08 非推奨マーカー

**`🚫` は「古い資産であり、参照時点では利用していない」ことを示す運用上のマーカーである。**

| ✅ 付けてよい場所 | 例 | ❌ 付けない場所 | 例 |
|---|---|---|---|
| `ver`軸の値 | `ver=🚫2` | `ver`以外の軸の値 | `state=🚫完了` `size=🚫xs` `type=🚫フォルダ` |
| Component Set名 | `🚫deliveryCard` | | |
| Setに属さない単体Component名 | `🚫closeIcon` | | |

| 扱い | 内容 |
|---|---|
| **付ける場所** | **`🚫`を付けてよいのは、`ver`軸の値、Component Set名、Setに属さない単体Component名の3か所に限る。** 新しいデザインが増えたら、`ver`を追加して旧`ver`に付ける。`ver`以外の軸の値を`🚫`付きで複製しない（`完了`と`🚫完了`のような並存を作らない） |
| **表記** | 上記3か所にある`🚫`は**違反としない。** 絵文字混入・意図不明として指摘しない。3か所以外にある`🚫`は**V-08違反**として指摘する |
| **AIの利用** | **`🚫` が付いた資産・値は選択してはならない。** 代替となる非推奨でない資産を選ぶ |
| **A3（正本と公開状態）** | 非推奨が識別できる状態として**評価を下げない** |
| **H6（制約遵守テスト）** | AIが `🚫` 付きを回避できるかを確認する。選んだ場合は不合格 |
| **Description** | `🚫` 付きの資産には、可能であれば代替先を記載する |

**`🚫`が適合する条件（場所ごと）**

| 場所 | 適合の条件 |
|---|---|
| `ver`軸の値 | 旧バージョンにだけ付ける。値の冒頭に1つだけ付ける。非`🚫`はちょうど1つ（V-04-3。`ver`以外の軸の値の組ごとに数える）。**`🚫`を除くと同じ値になる並存（`2`と`🚫2`）は違反。** 削除・統合はせず「要判断」として人に返す |
| Component Set名 | 旧Setにだけ付ける。名前の冒頭に1つだけ付ける。同じ役割の非`🚫`のSetが存在する。代替がない場合は、Descriptionにその旨を書く |
| Setに属さない単体Component名 | 上と同じ |
| 上記以外（`ver`以外の軸の値・Property名・レイヤー名） | 付けない |

- **`🚫`付きのSetの中の`ver`軸の値に、重ねて`🚫`を付けない。** Set全体が非推奨であることは、Set名の`🚫`で示す
- ✅ `ver=🚫1` と `ver=2` の並存、`🚫deliveryCard` と `deliveryCard` の並存 ／ ❌ `ver=2` と `ver=🚫2` の並存、`state=admin` と `state=🚫admin` の並存
- **3か所以外にある既存の`🚫`の直し方**:
  - 同じ軸に同義の無印値がない場合（例：`🚫完了`のみ）は、`🚫`を外す名前変更で直せる。既存Instanceは追随する
  - 同義の無印値が並存している場合（例：`完了`と`🚫完了`）は、**削除・統合しない。** `🚫`付きの値を参照しているInstanceが変わるため。指摘は行い、直し方は「要判断」として人に返す

**注意**: `🚫仮XXS` の `仮`（暫定）は `🚫` とは別のマーカーの可能性がある。**意味が確認できていないため、`仮` を含む値は「要確認」として報告する。**

### V-09 数字の制限

[layer-naming-rules.md](layer-naming-rules.md) R-09と同じ考え方を、Variant値・Property名・Component Set名に適用する。**種類・バリエーションを表す数字を含めない。**

| 対象 | 違反例 | 修正の方針 |
|---|---|---|
| Variant値 | `type=pattern1` `type=pattern2` | 役割を表す値に置き換える（値から用途を判断する＝要判断） |
| Property名 | `icon1` `icon2`（Boolean Propertyの連番） | 用途を表す名前に置き換える |
| Component Set名 | `card1` `card2` | 役割名で区別する |

**例外（数字でしか表現しようがない値）**はR-09の例外の表に準じる：px値、倍率。表にない用途の数字は違反とし、表への追加はユーザーが判断する。

- **px値の表記はR-09と異なる。** R-09の「数字＋`px`」はレイヤー名の規則であり、Variant値では従来どおり単位を付けない数字とする（例：`fontSize=14`）。単位は軸名で分かるため。`size`軸のpx直値は規定値へ変換する（V-05-1）

- **`breakpoint`軸の画面幅の値（`1366` `1200` `1024`等）はこの例外に該当し、違反としない**（V-05-1）。画面幅という数字でしか表現しようがない値のため
- **`ver`軸の値（単位語なしの数字、旧バージョンは`🚫`付き）もこの例外に該当し、違反としない**（V-04-3・V-05-3）。バージョンという数字でしか表現しようがない値のため
- **`direction`軸の角度の値（`right45` `left30`等）もこの例外に該当し、違反としない**（V-04-2）。角度という数字でしか表現しようがない値のため
- 判定に迷う場合は「要確認」とする

## 2. 機械的変換の規則

記号や大文字を含む値・名前を lowerCamelCase へ直すときの変換規則は、**[layer-naming-rules.md](layer-naming-rules.md) 第4節「機械的変換の規則」に従う**。Variant値・Property名・Component Set名すべてに適用する。

要点は次のとおり。

- **元の区切り（`_` `-` スペース）でのみ単語を分ける。区切りのない箇所を勝手に分けない**
- 例: `large_sidepanel` → `largeSidepanel`（`largeSidePanel` にしない）
- 元の綴りを変えない。綴り誤りの修正は別途行う

**この規則により、V-05（Variant値の表記規則）が未決定でも、記号除去の修正は判断なしで実行できる。** 修正のたびに表記が揺れることを防ぐ。

ただし**言語（日本語→英語）やケース体系そのものの決定は V-05 の範囲であり、機械的変換では決められない。** 日本語値の英語化は個別に判断する。

**語順も [layer-naming-rules.md](layer-naming-rules.md) R-01の語順細則（修飾語を先、役割語を後ろ）に従う。** Variant値・Property名・Component Set名が「役割語＋修飾語」の複合語になる場合も同様に適用する。V-06の「機能語を先、種別語を後ろ」（✅ `closeButton` ❌ `buttonClose`）はこの語順細則と同じ考え方である。

## 3. 判定上の注意

- **表記の揺れは、意味が通っていても違反とする。** AIは文字列で指定するため、`state` と `status` は別物になる
- **比較の順序**: ①ガイドラインの規定 → ②共通DSの同種Component → ③対象セクション内。上位に規定があればそれが正本
- **アプリ固有DSも同じルールに従う。** ただし共通DSを Instance として参照している部分は共通DS側の問題として扱う
- ルールに定義がない事象は勝手に判断せず、「ルールに定義がない」として要確認に挙げ、本文書への追記が必要であることを報告する

## 4. 変更時の影響

| 変更の種類 | 既存の画面への影響 | このルールでの扱い |
|---|---|---|
| Component Set 名・軸名・値・Property 名の変更 | 見た目は変わらない（Figma が既存Instanceを追随させる。Property 名は表示名のみ変更され、内部キーは維持される）。Set名は、名前で参照している外部（要件書の文字列参照など）のみ要確認 | AIが提案・修正してよい |
| **Variant 軸の追加・分離** | **既存Instanceが新軸の既定値になる。自動変換されず、見た目が変わるおそれがある** | **AIは実行も提案もしない。** 変更せず「要判断」として人に返す。やるかどうか・どう行うかは人が決める |

- **既存コンポーネントに対しては、名前の変更だけをこのルールの範囲とする。** 軸の追加・分離は構造の変更であり、このルールは手順を定めない
- **新規に作るComponentは、最初からこのルールどおりに作る。**

Figma の URL は node-id ベースのため、**名前を変えても要件書のリンクは切れない**。
