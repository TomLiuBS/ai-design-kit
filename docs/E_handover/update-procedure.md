ルールと素材を更新するときの手順と担当です。決まりそのものは [maintenance.md](../B_design-rules/maintenance.md)。

## 2. ルールを足す・直す

1. 何が起きたかを書く（例：「状態の値に `loading` がなく、AIが `default` を使った」）。
2. Claude Code に「このルール案を点検して」と頼む（`design-rules-editor`）。Q1〜Q13 で点検結果が出る。
3. 「ルールを追加して」と頼み、変更案（変更箇所・既存デザインへの影響・波及・更新履歴の行）を受け取る。
4. 承認する人が変更案を確認する。
5. 承認されたら、AIが編集し、更新履歴を書く。
6. `guidelines/` の変更だけをコミットする。

## 3. 素材（部品・トークン）を足す・直す

1. Figma の **ブランチ** で部品・変数を作る・直す（`component-authoring-advisor` に相談できる）。
2. ブランチを確認して本体にマージし、ライブラリを公開する。
3. Claude Code に次の順で同期を頼む。
   1. 「Figma のガイドラインをローカルに反映して」（`figma-guideline-sync` → トークン・DESIGN.md）
   2. 「Figma のコンポーネントを components.css に反映して」（`figma-components-css-sync`）
   3. 「デザインシステムを更新して」（`design-system-generate`）
4. `component-map.md` の該当行と確認日を更新する。
5. 修正メモの該当行を「反映済み」にする（`ds-fix-memo`）。
6. コミットする。

## 4. 素材の品質を確かめて直す（定期）

1. 「DSの実測値を出して」（`design-system-measure`）。前回と同じ範囲で測る。
2. 「デザインシステムをレビューして」（`design-system-audit-skill`、推奨モデルで）。修正リストが出る。
3. 承認する人が、実行する番号と「要決定」の答えを決める。
4. Figma で検証用ブランチを作る（人）。
5. 「#3, #5 を直して」（`design-system-apply-fixes`）。全件を見せてから、承認した分だけ書き込む。
6. ブランチを確認してマージ・公開する（人）。
7. 再実測・再レビューで、解消したことを確かめる。

## 5. スキルを直す

- スキルの手順で同じ手戻りが2回起きたら、該当の `SKILL.md` を直す。
- 直したら、そのスキルで1回試し、結果を確かめてからコミットする。
- スキルの中に、最終成果物の置き場所を決め打ちで書かない（置き場所は `.claude/CLAUDE.md` だけで決める）。

## 6. 版の付け方

| 対象 | 版 | 付け方 |
|---|---|---|
| ルール文書 | 各文書の更新履歴 | 変更ごとに1行 |
| 素材 | `DESIGN.md` 冒頭の版 | 部品の追加・削除で小さい番号を上げる（v1.1 → v1.2）。トークンの体系を変えたら大きい番号 |
| キット全体 | Git のタグ | `kit-v1.0` など。PoC の検証レポートに、使った版を書く |
