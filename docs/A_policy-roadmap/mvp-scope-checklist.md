# MVP の範囲を決めるチェックリスト／導入前の確認事項

導入先とのキックオフ前後で、この表を埋めて MVP の範囲を決めます。答えが決まっていない項目は「未定」と書き、こちらから案を出します。

## 1. 導入前の確認事項（質問表のひな形）

| No | 区分 | 質問 | 伺う理由 | 回答の例 | 優先 |
|---|---|---|---|---|---|
| 1 | 検証に使う PoC | キットを当てて確かめたい画面は、何画面くらいありますか。 | 部品・テンプレートの数と検証の重さを決めるため | 一覧・詳細・入力など 5〜10画面 | ★ |
| 2 | 検証に使う PoC | 2件目の PoC で、画面づくりが始まる時期の見込みは。 | 2件目で試す時期を合わせるため | 期間の後半／未定 | |
| 3 | 画面を使う方 | 画面を使う方の種類は（例：経営層／現場の業務担当／ツールに不慣れな方／社外の方）。 | スタイルの型の数と中身を決めるため | 3種類で足りる | ★ |
| 4 | 画面を使う環境 | 主にどの機器・ブラウザで使われますか。 | レイアウトの型と、押せる大きさの基準を決めるため | PC の Chrome・Edge が中心 | ★ |
| 5 | ブランド | ブランドガイドや、UI・色の決まりはありますか。 | 色・文字をその決まりに沿って決めるため | ブランドガイドあり／特になし | ★ |
| 6 | 技術構成 | 画面を作る技術（フレームワーク・CSS・部品ライブラリ）と、その設定の置き場所は。 | トークンの書き出し方と部品の直し方を決めるため | `<フレームワーク>`・`<CSS の方式>` | ★ |
| 7 | アクセシビリティ | 目指す水準や社内の決まりはありますか。 | 最低限守る基準（WCAG 2.2 の A・AA のどこまで）を決めるため | 特になし／AA を目安 | |
| 8 | 表示の切り替え | ダークモードや多言語の画面は必要ですか。 | トークンの持ち方と文字の長さの扱いを決めるため | 不要／英語の画面もある | |
| 9 | AI の使い方 | Claude Code の利用形態、共通ルール（CLAUDE.md）、Figma MCP など外部連携の可否は。 | ルールの置き場所と、AI に読ませる方法を決めるため | MCP は申請が必要 | ★ |
| 10 | 置き場所 | キット（ルール・トークン・部品）をどこに置きますか。 | 引き継いだ後も少ないファイルで更新できる形にするため | 共通のリポジトリを新しく作る | ★ |
| 11 | 更新の担当 | 引き継いだ後、キットを更新するのはどなたですか。 | 運用ガイドをその方に合わせて書くため | エンジニア1名が兼任 | |
| 12 | これまでの指摘 | これまでのレビューで出た、見た目への指摘の記録はありますか。 | キットの前後で指摘の数を比べるため | 議事録にあり／なし | |
| 13 | 既存の素材 | Figma のデザインや画面のメモなど、すでにある素材は。 | 前の状態を記録し、使える物は活かすため | Figma はない | |
| 14 | 確認の担当 | 作った画面の見た目を確認するのは誰ですか。報告前に確認する流れは。 | レビューの手順とチェックリストを合わせるため | PM が確認 | |
| 15 | 合意の相手 | 評価指標や提出基準を最終的に決めるのは誰ですか。 | 合意までの流れを決めるため | 責任者の確認が必要 | ★ |
| 16 | 成果の確かめ方 | 期間の終わりに「うまくいった」と判断する目安は。 | 検証レポートで比べる数字を最初に決めるため | 初期画面が半日でできる | ★ |
| 17 | 外部ツール | 画面レビューに使うツール（Figma プラグイン・Web アプリ）の利用に、確認や申請は必要ですか。 | ツールの使い方をセキュリティの決まりに合わせるため | プラグインのみ可 | |
| 18 | 情報の扱い | AI に入れてよい情報の範囲や、セキュリティの決まりは。 | ルールや見本に使う情報の範囲を守るため | 個人情報は不可 | ★ |
| 19 | ツールと権限 | Figma（プラン・編集の席）、Git、チャットツールに外部メンバーが入る形は。 | 開始日から作業できるよう準備するため | Figma に3名招待 | |
| 20 | 成果物の扱い | 成果物の権利や、ほかの案件で使い回すことについての希望は。 | 引き渡しの形と契約条件を決めるため | 組織内で自由に使いたい | ★ |
| 21 | 日程 | 定例の曜日・時間、休業期間、開始日の候補は。 | キックオフの日と進め方を決めるため | 毎週水曜 15時 | |

★は範囲・見積り・契約に直接かかわる項目です。★以外は定例で口頭で聞いてもかまいません。

## 2. MVP に入れるかどうかの判断

| 問い | はい → | いいえ → |
|---|---|---|
| PoC の画面で、その部品が2画面以上に出てくるか | MVP の部品にする | 画面側で作り、「不足」として記録だけする |
| その画面テンプレートを、PoC 2件のどちらかで使うか | MVP のテンプレートにする | 次フェーズ候補 |
| そのルールがないと、AIの出力が人によって変わるか | B のルールに入れる | 入れない（例として残すだけ） |
| その確認は、ツールで実測できるか | 画面レビューの実測に任せる | 固定チェックリスト（目視）に入れる |
| 導入先の更新担当が、自分で更新できるか | 入れる | 手順を簡単にするか、次フェーズに回す |
