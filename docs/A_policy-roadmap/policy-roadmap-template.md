# A. 方針・ロードマップ（テンプレート）

AIを使った画面づくりで、**一定水準のUIを短時間で作れる状態**を、軽い仕組みで作るための方針とロードマップのひな形です。

## 1. あるべき姿

### 1-1. 考え方

1. **ルールと素材が、AIの唯一の基準**
   AIツールごとに別の基準を持たせない。Claude Code でも Figma 側のAIでも、同じファイル（`guidelines/`）を読む。
2. **推測で埋めない**
   素材にない部品が必要になったら、AIは作り込まずに「素材に不足」として報告する。推測で作ったものが品質のぶれになる。
3. **判断は人、作業はAI**
   何を素材に足すか、例外を認めるか、画面を出してよいかは人が決める。反映と再チェックはAIが行う。
4. **増やすのは、使われたものだけ**
   網羅を目指さない。PoCで繰り返し必要になった部品だけを素材に昇格させる。

### 1-2. 仕組みの全体像

```
ルール（guidelines/rules/, docs/B_design-rules/）
素材（Figma ライブラリ ⇔ guidelines/kit/）
        │ AIが読む
        ▼
AI（Claude Code ＋ .claude/skills/）── 画面骨子から生成 ──▶ PoC の画面
                                                              │
                                     自己レビュー → 画面レビュー（ツール＋人）
                                                              │
        ◀────── 見つかった不足は、人が判断して素材・ルールへ戻す ──┘
```

### 1-3. 現状と目指す状態

| 観点 | 現状 `<記入>` | 目指す状態 | このキットでの手当て |
|---|---|---|---|
| UI品質 | 例：良し悪しの判断基準がない | 最低限の原則に沿って生成・レビューできる | B-1 原則定義書、固定チェックリスト、画面レビューの点数 |
| 制作速度 | 例：案件ごとに素材を作る | 基本素材を再利用し、初期画面を素早く作る | C の素材と画面テンプレート、B-2 の生成手順 |
| 運用 | 例：大きな仕組みは維持できない | 少数のファイルと明確な更新責任 | 役割ごとに1ファイル。各ファイルに更新責任者と更新履歴（B-3） |
| 拡張性 | 例：連携を先に広げると複雑になる | 効果を確かめてから必要な連携だけ足す | D の計測値で次に足すものを判断する |

## 2. MVP と次フェーズの切り分け

MVP の範囲は [mvp-scope-checklist.md](mvp-scope-checklist.md) の問いに答えて決めます。標準的な切り分けは次のとおりです。

| 区分 | 内容 |
|---|---|
| **MVP（期間内に終える）** | B-1〜B-3 の定義書／C の3ファイル（トークン・部品CSS・部品対応表）と Figma ライブラリ／基本部品 `<8>` 種と画面テンプレート `<5>` 種／素材の実測・DSレビューの仕組み／画面レビューの仕組み／PoC `<2>` 件の検証レポート／E の運用ガイド |
| **次フェーズ候補（効果を見て判断）** | 部品の追加（「不足」報告の多い順）／プロトタイプから Figma への書き起こしの定常化／ユーザビリティテストの定常運用／利用中のコード基盤（フレームワーク）との部品対応 |
| **対象外** | 全社横断・複数ブランド統合の大規模デザインシステム／本番サービス全体を網羅する部品ライブラリ／生成UIの完全自動評価（人のレビューを不要にする仕組み）／大規模運用前提の DesignOps 組織 |

## 3. ロードマップ（標準12週）

| フェーズ | 週 | 主な活動 | 主なアウトプット |
|---|---|---|---|
| 1. 計画 | 1〜2 | 現状把握、PoC の選定、MVP 範囲・評価指標の合意 | MVP 定義、素材設計方針、実行計画（本書） |
| 2. デザインルール | 2〜4 | B-1〜B-3 の作成とレビュー、命名ルールの合意 | `docs/B_design-rules/`、`guidelines/rules/` |
| 3. デザイン素材 | 3〜9 | 色・文字 → 部品 → 画面テンプレートの順に制作、Figma と CSS の同期 | Figma ライブラリ、`guidelines/kit/` |
| PoC 1件目 | 6〜8 | 素材を当てて画面を作り、手戻りを計測、素材とルールを直す | 計測シート（D） |
| 4. 検証・引き継ぎ | 9〜12 | PoC 2件目、検証レポート、運用ガイド、次期計画の合意 | D の検証レポート、E の引き継ぎ資料 |

- 素材の制作に最も長い期間を取る。
- PoC 1件目の結果で素材とルールを直し、2件目で改善を確かめる。

## 5. 評価指標

詳しい定義は [D_poc-verification/measurement-method.md](../D_poc-verification/measurement-method.md)。

| 種類 | 指標 | 目標 `<記入>` |
|---|---|---|
| 速度 | 初期画面ができるまでの実作業時間 | 例：Before 比 50% |
| 手戻り | AIへの指示のうち手戻り（素材・ルール起因を含む）の件数 | 例：素材起因を半分に |
| 初版の品質 | 固定チェックリストの通過数、画面レビューの総合点 | 例：初版で総合80点以上 |
| 素材 | 説明文の記載率・Variant違反候補率など6指標、DSレビューの判定 | 例：AI-ready（90%以上） |
| 素材の不足 | AIが「不足」と報告した部品の数と頻度 | 次フェーズの判断材料 |

## 6. 前提と確認事項

- 開発に Claude Code などAIを使ったプロセスがあること。
- Figma で素材を共有できる権限（ライブラリの公開・ブランチ）があること。
- 画面レビューのツール（Figma プラグイン／Web アプリ）を導入先の環境で使えるかは、セキュリティ条件に合わせて決める。
- 導入前に確認する事項は [mvp-scope-checklist.md](mvp-scope-checklist.md) の「導入前の確認事項」を使う。
