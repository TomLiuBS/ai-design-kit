# B-3. 最低限のメンテナンスルール

ルールと素材を、**少ない手間で、誰が更新しても同じ形で**保つための決まりです。

---

## 1. ファイルと更新責任

| ファイル | 役割 | 更新責任者 `<記入>` | 更新のきっかけ |
|---|---|---|---|
| `guidelines/rules/*.md`（5本） | AIが○×で判定する命名・構造のルール | | ルールに定義のない事象が見つかったとき |
| `docs/B_design-rules/ux-principles.md` | UX/UI の原則と提出基準 | | 提出基準を変えるとき |
| `docs/B_design-rules/process.md`・`.claude/PROTOTYPE.md` | 生成とレビューの手順 | | 手順で同じ手戻りが2回起きたとき |
| Figma ライブラリ | 素材の正本 | | 部品・トークンを足す・直すとき |
| `guidelines/kit/`（トークン・部品CSS・DESIGN.md） | 素材のローカル版 | | Figma を更新したあと（同期） |
| `guidelines/kit/component-map.md` | 部品の索引 | | 部品を足した・直したとき。確認日が30日を過ぎたとき |
| `guidelines/design-system-map.md` | Figma の所在（ファイル・ページ） | | ファイルやページを移したとき |

- **1ファイルに更新責任者は1人**。
- 各ファイルの冒頭に「置き場所・誰が読むか」、末尾に更新履歴を置く。

---

## 2. ルールを足す前の品質基準（Q1〜Q13）

新しいルールや変更案は、次の13項目で点検してから入れます。満たさないルールは入れません。点検と編集は `design-rules-editor` スキルで行います。

| ID | 観点 | 満たしている状態 |
|---|---|---|
| Q1 | 目的 | AIのどの動作（特定・選択・操作・組み立て・回避）のどんな誤りを防ぐかを1文で書ける |
| Q2 | 判定の一意性 | 誰が判定しても同じ○×になる。文字列・列挙・正規表現・変換表で判定できる |
| Q3 | 例外が閉じている | 例外は列挙で示し、追加の手順と判断者（人）が書かれている。「〜など」で開いていない |
| Q4 | 直し方が決まる | 違反の直し方が1つに決まる。決まらないものは「要判断」と明記 |
| Q5 | 人の判断の線引き | 人が判断する部分は「要確認」と明記し、AIに委ねていない |
| Q6 | 既存資産への影響 | 既存の素材が違反になる場合、名前の変更だけで直せる。直せないものは対象外か段階的に解消すると明記 |
| Q7 | 整合 | ほかのルール・一覧・変換表と矛盾しない。同じ内容の正本は1か所 |
| Q8 | 読み手 | デザイナーが作業しながら読める。守る状態を先に、❌/✅の例を1つずつ |
| Q9 | 自己完結 | ほかのAIツールが本文だけで同じ判定ができる |
| Q10 | 形式と意味の分担 | ルールは○×で判定できる「形式」だけ。○×で書けない品質はDSレビューの基準に回す |
| Q11 | 重なりの優先順位 | 1つの対象に複数のルールが当たるとき、どちらが優先かが書かれている |
| Q12 | 境界例 | 判定が割れやすいケースに例がある |
| Q13 | 時点に依存しない | 本文は「今のルールで○か×か」だけ。決定日・経緯・件数は更新履歴にだけ書く |

---

## 3. 更新履歴の書き方

各ファイルの末尾に、次の形式の表を置きます。新しい行を上に足します。

```markdown
## 更新履歴

| 版 | 日付 | 変更内容 | 変更者 |
|---|---|---|---|
| v1.1 | 2027-02-10 | V-05-2 の状態の値に `loading` を追加 | <名前> |
| v1.0 | 2026-11-26 | 汎用キットとして初版作成 | — |
```

- 1行に1つの変更。理由が要るときは「（理由：…）」を添える。
- ルールの本文には日付・経緯を書かない（Q13）。

## 4. 素材の同期と再確認

| 決まり | 内容 |
|---|---|
| 同期は人が指示したときだけ | Figma → `guidelines/kit/` の同期（`figma-guideline-sync` → `figma-components-css-sync` → `design-system-generate`）は、画面を作るたびには行わない |
| 30日の再確認 | `component-map.md` の各行に確認日を持たせ、30日を過ぎた行は使う前に Figma と照合し直す |
| 仮の部品の記録 | 素材にない部品を `components.css` に仮で足したら、修正メモ（`generated/docs/ds-content-fix-memo.md`）に記録する（`ds-fix-memo` スキル） |
| 正本は Figma | CSS と Figma が食い違ったら Figma に合わせる。Figma 側が間違っていると思ったら、修正メモに書いて人が判断する |

---

## 5. 素材に足す・やめる判断

| 判断 | 目安 |
|---|---|
| 部品を足す | 「素材に不足」の報告が2件以上の PoC から出た、または同じ PoC で3回以上出た |
| 部品をやめる | 3か月使われていない、またはほかの部品の Variant で表せる。やめる部品には廃止の印（🚫）を付け、AIが選ばないようにする |
| ルールを足す | 同じ種類の手戻りが2回以上起きた。Q1〜Q13 を満たす |
| 提出基準を変える | PoC の結果を見て、責任者が合意したとき |

---

## 6. 定期の確認（推奨）

| 頻度 | すること | スキル |
|---|---|---|
| PoC ごと | 「素材に不足」の報告と修正メモを見て、足す・直すを決める | `ds-fix-memo` |
| 月1回 | 素材の6指標を実測し、前回と比べる | `design-system-measure` |
| 四半期ごと | 素材のDSレビューを行い、修正リストを承認・反映する | `design-system-audit-skill` → `design-system-apply-fixes` |
