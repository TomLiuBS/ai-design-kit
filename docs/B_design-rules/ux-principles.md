# B-1. UX/UI 基本原則の定義書

AIが画面を作るときと、人やツールが画面をレビューするときに使う、最低限の原則です。
**AIが○×で判定できる文**で書いています。迷う表現（「適切に」「分かりやすく」）は使いません。

- 対象：PoC で作る業務アプリの画面（PC・スマートフォン）
- 出典：WCAG 2.2（日本語訳の名称）、Nielsen のユーザビリティ10原則、デザインシステムの一貫性の観点
- 導入先で水準を変えるときは、「4. 提出基準」の表だけを書き換えます。原則の文は変えません。

---

## 1. 領域別の原則

### 1-1. 視認性

| ID | 原則（満たしている状態） | 判定方法 |
|---|---|---|
| 1.4.3 | 文字と背景のコントラスト比が 4.5:1 以上。24px 以上、または 18.66px 以上の太字は 3:1 以上 | 実測 |
| 1.4.11 | 入力欄の境界・アイコン・状態の表示など、操作や理解に必要な図形が隣の色と 3:1 以上 | 実測 |
| 1.4.1 | エラー・必須・選択中・グラフの系列などを、色だけで伝えていない | 実測・目視 |
| R5 | 注記・キャプションも含め、文字は 12px 以上 | 実測 |
| 1.4.4 / 1.4.12 | 文字を 200% にしても、行間・文字間隔を広げても、文字が切れたり重なったりしない（固定高さの箱に文字を入れない） | 実測・目視 |

### 1-2. 操作性

| ID | 原則 | 判定方法 |
|---|---|---|
| 2.5.8 | 押せる領域は 24×24px 以上。スマートフォンの画面では 44×44px 以上 | 実測 |
| 2.4.7 | キーボード操作中のフォーカス位置が見える（focused の状態のデザインがある） | 実測・目視 |
| 2.5.7 | ドラッグでしかできない操作がない（タップ・クリックでも同じことができる） | 目視 |
| 3.2.1 / 3.2.2 | 選んだ・入力しただけで、予告なく画面が移動・送信されない | 目視 |
| 2.1.2 | モーダル・メニューに入ったら、閉じるボタンかキー操作で必ず抜けられる | 目視 |

### 1-3. フィードバック

| ID | 原則 | 判定方法 |
|---|---|---|
| H1 | 保存・送信・削除のあとは、結果（成功・失敗・処理中）を画面に表示する | 目視 |
| DS4 | 部品に必要な状態（normal・hover・pressed・disabled・focused、入力は error も）がそろっている | 実測・目視 |
| 状態 | 一覧・詳細には、空・読み込み中・エラーの表示がある | 目視（[checklists/state-checklist.md](checklists/state-checklist.md)） |

### 1-4. エラー防止と回復

| ID | 原則 | 判定方法 |
|---|---|---|
| H5 / 3.3.4 | 取り消せない操作（削除・送信・申込・支払い）の前に確認を挟むか、あとで取り消せる | 目視 |
| 3.3.1 / 3.3.3 | 入力エラーは該当欄の近くに文字で表示し、直し方（例：`2027/01/31` の形式）を含める | 目視 |
| 3.3.2 | 入力欄にラベルと、必要なら入力例・形式の説明がある | 目視 |
| 3.3.7 | 同じ手続きの中で一度入力した情報を、もう一度入力させない | 目視 |
| H9 | エラーメッセージは平易な言葉で、何が起きたかと次にすることを書く。エラーコードだけにしない | 目視 |

### 1-5. 一貫性

| ID | 原則 | 判定方法 |
|---|---|---|
| H4 / 3.2.4 | 同じ機能には、同じ部品・同じアイコン・同じ文言を使う | 実測・目視 |
| 3.2.3 | ヘッダー・メニュー・タブの位置・順番・表記が、画面間で同じ | 目視 |
| DS5 | 同じ部品は素材のコンポーネント（インスタンス）を使い、切り離していない | 実測 |
| DS1 / DS2 / DS8 | 色・文字・余白は、素材のトークン（スタイル・変数）から使う | 実測 |
| 素材 | 素材にない部品を作り込まない。必要なら「素材に不足」として報告する | 目視 |
| R8 | 用語集の表記（例：ログイン／サインインのどちらか）を守り、英数字は半角、半角カタカナを使わない | 実測 |

### 1-6. 情報設計

| ID | 原則 | 判定方法 |
|---|---|---|
| H8 | 1画面の主要な操作は1つ。主ボタン（primary）は1画面に1つまで | 目視 |
| 2.4.2 / 2.4.6 | 画面ごとに、内容が分かる重複しないタイトルがある。見出し・ラベルが内容を説明している | 目視 |
| 1.3.1 / 1.3.2 | 見出し・リスト・表・入力欄とラベルの関係が構造として伝わる。左上から右下へ読んだ順番で意味が通る | 目視 |
| H6 | 覚えておく必要のある情報（前の画面の値など）を、選択肢・履歴・候補で見せる | 目視 |

### 1-7. アクセシビリティ（そのほか）

| ID | 原則 | 判定方法 |
|---|---|---|
| 1.1.1 | 意味のある画像・アイコンに、代わりになるテキスト（ラベル）がある。アイコンだけのボタンには名前がある | 実測・目視 |
| 1.3.3 | 「右の写真」「丸いボタン」など、位置・形・大きさだけに頼った指示をしない | 目視 |
| 2.4.4 | リンクの文言で行き先が分かる。「こちら」だけにしない | 目視 |
| 2.2.2 / 2.3.1 | 5秒を超えて自動で動くものは止められる。1秒に3回を超えて点滅しない | 目視 |
| 1.4.10 | 幅 320px 相当でも横スクロールなしで読める（スマートフォンの画面がある場合） | 目視 |

## 2. ユーザビリティ10原則（H1〜H10）

設計の段階（方向性のレビュー）で確認します。点数には入れません。

| ID | 原則 | 確認すること |
|---|---|---|
| H1 | システム状態の視認性 | 今何が起きているかを、適切な時間内のフィードバックで知らせている |
| H2 | 現実世界との一致 | 利用者の言葉・概念・順序に沿った用語を使っている |
| H3 | ユーザーの主導権と自由 | 誤操作からの出口、取り消し・やり直しがある |
| H4 | 一貫性と標準 | 同じ意味の操作は同じ語・同じ操作でできる。プラットフォームの標準に従う |
| H5 | エラーの予防 | エラーが起きない設計にし、曖昧な操作には確認を挟む |
| H6 | 想起より認識 | 記憶を求めず、選択肢・履歴・候補で選べる |
| H7 | 柔軟性と効率 | 初心者にも慣れた人にも対応（既定値、一括操作など） |
| H8 | 美的でミニマル | 目的に対して情報が多すぎない |
| H9 | エラーの認識・診断・回復 | エラーは平易な言葉で、問題と解決策を示す |
| H10 | ヘルプとドキュメント | 必要なときにヘルプにたどり着ける |

## 3. 指摘の重さと優先度

### 3-1. 重大度（0〜4）

| 値 | 名前 | 意味 | 対応 |
|---|---|---|---|
| 0 | 問題なし | 好みの差など、ユーザビリティの問題ではない | 対応不要 |
| 1 | 美観・些細 | 見栄え・体裁の問題（色のトーン違い、わずかなずれ） | 余裕があれば |
| 2 | 軽微 | 頻度が低い、または慣れれば避けられるが不便 | 中期的に |
| 3 | 重大 | よく起きる・避けにくい・作業の完了を妨げる（送信後に取り消せない、同じ概念の呼び方が画面で違う） | 次の版で |
| 4 | 破綻 | 作業を完了できない、重要なデータが失われる、信頼を損なう | すぐに |

### 3-2. 頻度と重み

| 頻度 | 目安 | 重み |
|---|---|---|
| 高 | 利用者の50%以上が遭遇する | 1.5 |
| 中 | 条件がそろうと遭遇する（10〜50%） | 1.0 |
| 低 | まれ（10%未満） | 0.5 |

### 3-3. 優先度

`優先度の値 = 重大度 ＋ 頻度の重み`

| 値 | 優先度 | 扱い |
|---|---|---|
| 5 以上 | P0 至急 | 提出前に必ず直す |
| 4 以上 | P1 高 | 提出前に必ず直す |
| 2.5 以上 | P2 中 | 計画して直す |
| 1 以上 | P3 低 | 余裕があれば直す |
| 1 未満 | P4 軽微 | 記録のみ |

最終判断では、指摘が長く残るか、直すのが難しいか、意図した違いかも加味します。

## 4. 画面の点数と提出基準

### 4-1. 点数のつけ方

- 画面ごとに 100点から始め、指摘の重大度で減点する：**4 → −15、3 → −8、2 → −3、1 → −1**。
- 4つの軸で点数を出し、重みをかけて総合点にする：**ユーザビリティ 40%／アクセシビリティ 20%／一貫性 20%／ルール遵守 20%**。
- 総合点の判定：**S ≥ 90、A ≥ 80、B ≥ 70、C ≥ 60、D < 60**。

### 4-2. 提出基準（導入先で書き換える欄）

| 項目 | 標準 | 導入先の値 |
|---|---|---|
| 総合点 | 80点以上 | `<…>` |
| アクセシビリティの点 | 80点以上 | `<…>` |
| 必須の基準（満たさないと提出不可） | 2.5.8（押せる領域の大きさ） | `<…>` |
| P0・P1 の指摘 | 0件 | `<…>` |

### 4-3. 意図的な例外

原則に合わない表現を意図して残すときは、**理由・承認者・範囲・期限**を記録します。例外にした指摘は点数・提出判定に数えません。必須の基準は例外にできません。

## 5. 二段階のレビュー

| 段階 | いつ | 見るもの | 点数 |
|---|---|---|---|
| 設計レビュー | 画面の方向性を決めるとき | 目的・利用者に合っているか、H1〜H10、情報の構造 | つけない |
| 仕上げレビュー | 提出前 | 1章の原則（実測＋目視）、提出基準 | つける |

点数はチームの品質改善のためのもので、個人の評価には使いません。
