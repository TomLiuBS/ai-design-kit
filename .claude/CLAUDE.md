# Project instructions

## 用語

- 決まりごとは「ルール」と書く。デザインシステムの品質を確かめる作業は「デザインシステムレビュー」（短くは「DSレビュー」）と書く。チャットの回答・レポート・スキル・ドキュメントのすべてに適用する。
- スキル名・フォルダ名などの英語の識別子（例：`design-system-audit-skill`）は、呼び出しが壊れるため対象外とし、そのまま使う。

## Generated deliverables

- 生成物はリポジトリルートの `generated/` に保存する。
- 単体で利用する画像は `generated/images/` に保存する。
- HTML、CSS、JavaScriptなどで構成される動的・対話的なデザインは `generated/prototypes/<service>/<プロト名>/<バージョンのフォルダ名>/` に保存する（定義は下記「プロトタイプの命名」）。
- 手順書などサービスに属さないHTML資料は、プロトタイプではなく `generated/docs/` に保存する。
- Word、Excel、PowerPoint、Markdownなどの非実行型ドキュメントは `generated/docs/` に保存する。
- デザインシステムのレビューレポート（`design-system-audit-skill` の出力）は `generated/docs/design-system-review/` に保存する。ファイル名は `design-system-review_<対象>_<YYYYMMDD>_<作成者>.md`（`<対象>` はFigmaの Component Set名をそのまま使う。作成者はgitのユーザー名。例: `design-system-review_button_20261126_<gitユーザー名>.md`） とする。
- デザインシステムの修正メモ（`ds-fix-memo` の出力）は `generated/docs/ds-content-fix-memo.md` に置く。
- プロトタイプ専用の画像や文書は、単体成果物として重複保存せず、そのプロトタイプのフォルダ内に置く。
- 既存ファイルは、明示的に置換を依頼されない限り上書きせず、`-v2` などの版を付ける。
- 一時ファイルや不採用案は `generated/` に残さない。
- 保存先の定義はこのファイルを唯一の基準とし、個別スキルでは最終成果物の固定パスを定義しない。
- スキルに記載された固有パスは入力参照先または一時作業先として扱い、最終成果物には使用しない。

## DSレビュー（design-system-audit-skill）実行前のモデル確認

- `design-system-audit-skill` を Skill ツールで起動する**前に**、実行モデルを確認する。推奨（標準）は Sonnet 5.5（`claude-sonnet-5-5`）。
- Sonnet 5.5 でなければ、スキルを起動せず、現在のモデル名と「Sonnet 5.5 に切り替えてから、もう一度依頼してほしい」ことをユーザーに伝えて止まる。自分でモデルは切り替えない。
- ユーザーが「今のモデルのまま続けて」と明示した場合のみ起動する。その場合はレポートのScopeに、実行モデルが標準と異なることを記録する。
- スキル側（SKILL.md「実行モデルの確認」）にも同じ確認がある。こちらはスキルが読み込まれた後の二重の確認であり、起動前の確認を省略しない。

## プロトタイプの命名

- 階層は `generated/prototypes/<service>/<プロト名>/<バージョンのフォルダ名>/` の3階層とする。例: `generated/prototypes/<service>/request-list/request-list_renewal-v1/`
  - `<service>` は、導入するチームが決めるサービス（アプリ）ごとの識別子（英小文字・数字・`-`）。ほかに `common`（複数サービスに共通の画面・部品）と `etc`（どのサービスにも属さないもの）を使う。使う識別子は導入時にここへ列挙する。依頼から分からないときは質問する。
  - プロト名は画面名（または機能名）。同じ画面の修正版はこの下にバージョンとして並べる。
  - 新規の画面・機能の作成依頼は、新しいプロト名のフォルダを作る。**既存プロトタイプの修正を依頼されたときだけ**、同じプロト名の下に新しいバージョンのフォルダを作る（既存は上書きしない）。
  - **既存プロトタイプを修正するときは、作業を始める前に「現行ファイルを上書きするか」「新しいバージョン（`-v2` など）を作るか」をユーザーに確認する。** 確認なしに版を作ったり上書きしたりしない。どちらを選ぶかは依頼者が決める。
  - 最初のバージョンも、プロト名フォルダの下に置く（バージョンが1つだけでも3階層にそろえる）。
- バージョンのフォルダ名は `<画面名>_<施策名>` に版（`-v2` など）を付けたものとする。例: `request-list_renewal-v2`
  - 画面名と施策名（または機能名）は `_` で区切る。それぞれの語の内部は `-` でつなぐ。
  - 英小文字・数字・`-`・`_` のみを使う（日本語・大文字・空白は使わない）。
  - 施策名・機能名がない画面は、`<画面名>` のみとする。
  - 日付は入れない。更新日はgitの履歴で確認する。
- プロトタイプを新規作成するときは、このフォルダも作成する。
- エントリファイルは `index.html` に固定する。CSS・JS・画像は同じフォルダ内に置く。
- 同名のフォルダが既にある場合は、上記「既存ファイルは上書きしない」に従う。
- デザインガイドラインへの相対パスは、バージョンのフォルダから `../../../../../guidelines/...` になる（例: `../../../../../guidelines/kit/design-tokens.css`）。

## プロトタイプ作業

- Epic/Feature/画面骨子からプロトタイプを作成する作業では、[PROTOTYPE.md](PROTOTYPE.md)を必ず読み込み、そのルールに従う。
