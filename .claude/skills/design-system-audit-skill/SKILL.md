# Design System AI-ready レビュー

Figma Design System（DS）が、**AIが資産を発見し、意味と制約を理解し、正しい部品・状態・トークンを選び、意図した画面をFigmaとコードの双方で再現できる形式（AI-ready）になっているか**をレビューする。見た目の good/bad やデザインの好みは評価しない。「AIが誤らずに使えるか」だけを見る。

このファイルはレビューの進行と参照順序を担う。各カテゴリの評価観点は `references/` に、**正しい形の定義（ルール）は `guidelines/rules/` に置く。スキル側でルールを再定義しない。**

## 用語

- 本スキルは「デザインシステムレビュー（DSレビュー）」と呼ぶ。正しい形の定義は「ルール」、本スキルの作業は「DSレビュー」と書き、旧来の言い方（ルールを指す古い語、レビューを指す古い語、点数付けを指す語）は使わない。点数（2/1/0）は**評価値**、レポートは**レビューレポート**と呼ぶ。
- 「評価観点（references）＝どこを見て良し悪しを判定するか」と「ルール正本（guidelines/rules）＝正しい形は何か」を区別する。前者はスキルが持ち、後者は参照する。

## 絶対原則：レビュー専用・Human-in-the-loop

標準フローは次の順序とする。

```text
レビュー → レポート → UIデザイナー承認 → 修正（別途） → 再レビュー
```

- **本スキルはレビューと改善提案までで停止する。** レポート提出後に自分から修正へ進まない。
- レビューフェーズは読み取り専用とし、Figmaファイル、ライブラリ、Variables、Components、Descriptions、Examplesを変更しない。
- レビュー依頼を修正許可と解釈しない。名前変更、構造変更、Property追加、Token置換、公開設定変更は行わない。
- **修正の実行（Figmaへの書き込み）は本スキルの対象外である（担当は未確定）。** 修正リストは「デザイナーがそのまま指示に使える下準備」として作るが、本スキル自身は実行しない。実行の担当（Claude Code / Figma Agent）は別途決める。
- 不明な設計意図を断定しない。事実、推論、提案を分け、証拠不足は「未検証」または「要確認」と記録する。

読み取り専用の対象は、A〜G および I の評価に必要なFigma資産の参照とする。AI実利用テスト（カテゴリH）はFigmaへの書き込みを伴うため、読み取り専用原則の唯一の例外として後述の条件下でのみ実施する。**Hは得点に入れない参考情報であり、実施は任意とする**（実施しなくても未検証に数えない）。

### AI実利用テストの実施条件

- **実施場所**: 事前に承認された検証用ファイル、検証用ブランチ、または本番DSの複製に限定する。承認がない場合はHを実施せず「未実施（実施場所未承認）」として報告し、代替場所を自分で選ばない。
- **書き込み範囲**: 対象DSはInstanceとして参照するだけとする。公開Componentの編集、Variablesの追加・変更、Styleの追加、ライブラリの公開・更新は行わない。
- **識別**: 生成物にレビューIDと実施日を含む名前を付け、検証用であることが第三者に判別できる状態にする。
- **後片付け**: 保持するか削除するかを承認時に決め、レポートに記録する。既定は「再レビューの証跡としてレポート提出まで保持し、承認された時点で削除」とする。
- **権限不足時**: 検証場所を用意できない場合、生成を伴わない範囲でH1・H6のみを資料上の選択テストとして実施し、H3は「未検証」とする。

## 参照する文書

レビュー中に参照する文書は4種類ある。**役割が違うので混同しない。**

| 種類 | 役割 | 所在 |
|---|---|---|
| **ルール正本** | 正しい形は何か（判定の答え） | `guidelines/rules/`（`layer-naming-rules.md` / `variant-naming-rules.md` / `description-format.md` / `component-authoring-rules.md` / `variables-rules.md`） |
| **所在マップ** | どのFigmaを読むか | `guidelines/design-system-map.md` |
| **評価観点** | どこを見て良し悪しを判定するか | 本スキルの `references/`（`ai-ready-criteria.md` ほか） |
| **Figma実データ** | 実際の値・件数 | `use_figma`（figmaRemoteMcp）で取得。実測は `design-system-measure` スキルの結果を使う（[scripts/measure-scripts.md](scripts/measure-scripts.md) に案内あり） |

**形式の判定は必ずルール正本に従い、`references/` で別基準を作らない。** `references/` は「そのルールのどこを見るか」と「ルールに書けないAI-ready品質観点」だけを持つ。

## 責務境界

本スキルの対象は **Design System本体**（ライブラリ、公開Component、Variables、ガイドライン、Pattern／Examples）とする。個別の画面ファイルの構造品質は対象外とする。

| 観点 | 担当 | 本スキルでの扱い |
|---|---|---|
| DSライブラリの設計・意味・制約・コード連携 | 本スキル | 主対象。A〜Iを担当する |
| 画面ファイルの構造品質（Instance率、Auto Layout率、ページ構成など） | `figma-ai-review` | 対象外。画面側の問題の原因がDSにある場合のみ、DS側のIssueとして扱う |
| **形式的な**Layer命名規則（ケース、記号、日本語、連番、デフォルト名・素材名、ダミーテキスト、禁止語、綴り誤り） | `guidelines/rules/layer-naming-rules.md` を基準に `figma-review-layers` が担当 | C4はDS公開資産の内部Layerに限定し、判定は同ルールに従う。本スキルで別基準を作らない |
| **意味的な**命名品質（機能の具体性、親情報の冗長性、命名の粒度） | 本スキル（C9〜C11） | DS全体の文脈がないと判定できないため委譲しない。形式違反ではないので修正を強制せず改善提案として扱う |
| 要件書のタイトル番号付与 | `figma-rename-layers` | 対象外 |
| アプリ固有のアクセシビリティ必達／推奨基準の適合判定 | `accessibility-review` | F4は「要件がガイドラインとして記述・追跡できるか」に限定する。UI個別の適合判定は委譲する |
| ラフ→本デザイン、実装前の準備状況 | `design-production-readiness` | 対象外。DS側に原因がある不足のみIssue化する |

- 委譲した観点を本スキルで再判定しない。レポートには担当と実施状況（実施済み／未実施／不明）を記録し、未実施なら「未検証」として扱う。
- 委譲先の結果が入手できる場合は証拠として引用してよい。引用時は実施日と対象を明記する。

### Figma内から判定できない項目は本スキル（Claude Code）が担う

Figma Agent版レビューは、セクション内から判定できるFigma内部の項目に限定される。**次の項目はファイル／組織／リポジトリ単位の情報が要るため、Claude Code版である本スキルが担当する。**

| 項目 | 内容 |
|---|---|
| E1 | Token階層（Primitive → Semantic → Component の参照方向）。Variables Collection全体が必要 |
| F6 / I5 | Code Connect の有無と実装照合。ファイル／組織単位の設定 |
| I2 | リポジトリ側ミラー（`guidelines/` の Markdown／CSS／JSON との整合） |
| I3 / I4 | Variable名・Component名 ⇄ コード識別子の写像、日本語名の扱い |
| I9 | 状態バリアント（Interaction state）⇄ `components.css` の状態の対応。Figmaにあってクラスにない状態・値の違いを数える（Ext） |
| H3 | 画面構築テスト（生成を伴うAI実利用テスト。承認された検証場所がある場合のみ） |

Figma Agent版のレビュー結果があれば、本スキルはそれを証拠として引用し、上記のCC固有項目を上乗せする。

## レビューモード

既定は **Core** とする。Coreは、AIの誤選択・誤構築へ直接つながる項目に絞った初回・定期レビュー用の範囲である。

| モード | 範囲 | 用途 |
|---|---|---|
| Core | `references/ai-ready-criteria.md` で `Core` と記した項目 | 初回レビュー、定期レビュー、再レビューの既定 |
| Extended | A〜Iの全項目 | Coreで低評価だった領域の深掘り、正式なAI-ready認定 |

- モードはレビュー開始時に確定してScorecardに明記する。途中で無断に広げない。
- CoreでCriticalまたはMajorが出たカテゴリは、そのカテゴリのみExtendedへ拡張してよい。
- Extended限定項目をCoreで評価しない場合、N/Aにせず「Core範囲外」として区別し、得点計算から除外する。
- 得点率はモード内で完結させ、CoreとExtendedを直接比較しない。再レビューは初回と同じモードで実施する。

## 実行モデルの確認

本キットが推奨する本スキルの実行モデルは **Sonnet 5.5**（モデルID: `claude-sonnet-5-5`）とする（以下「推奨モデル」）。判定の一貫性と根拠の正確さを揃えるため、レビューを始める前に必ず確認する。推奨モデルを変える場合は、チームで決めてから本節とC-1を書き換える。

- 自分の実行モデルIDを確認する（システムプロンプトの環境情報に記載されている）。
- `claude-sonnet-5-5` であれば、そのままレビューを開始する。
- それ以外のモデルであれば、**Figmaの読み取りもレビューも始めず**、次の旨をユーザーに伝えて停止する。
  - 現在のモデル名
  - 本キットの推奨モデルは Sonnet 5.5 であること
  - モデルを Sonnet 5.5 に切り替えてから、もう一度依頼してほしいこと
- 自分でモデルを切り替えない。切り替えはユーザーが行う。
- ユーザーが「今のモデルのまま続けて」と明示した場合のみ続行する。その場合はレポートのScopeに、実行モデルが推奨モデルと異なることを記録する。

## 前提条件

- Figma Desktop アプリが起動し、対象ファイルが開かれていること。
- figmaRemoteMcp（Remote MCP）が接続され、Figma にサインイン済みであること（手順は「開始前チェック」の「C-4 で止まったときの直し方」）。
- **`use_figma` を呼ぶ前に必ず figma-use を読み込む。** 実測スクリプトは `use_figma` で実行する。
- 環境が整わず `use_figma` が使えない場合は、下記「開始前チェック」のC-4で止まる。未検証のままレビューを進めない。

## 開始前チェック（そろわなければ始めない）

**誰が実施しても同じ得点・同じ修正リストになるよう、入力（モデル・ルール・スキルとスクリプト・Figmaの取得環境）をそろえてから始める。** 次のC-1〜C-4を順に確認し、**1つでも合わなければ、Figmaの測定もレビューも始めずに停止する。** 停止したときは、どのチェックが合わなかったか・直し方をユーザーに伝える。結果はScopeの「開始前チェック」表と付録Aに記録する。

| ID | 確認すること | 合格の条件 | 合わないとき |
|---|---|---|---|
| C-1 | 実行モデル | 上記「実行モデルの確認」のとおり `claude-sonnet-5-5` | 上記のとおり停止する |
| C-2 | ルールをリモートの最新にそろえる（`guidelines/`） | 下記の手順で**自動で** リモート（このリポジトリの `origin` の main）の最新を取り込み、`guidelines/rules/` が `origin/main` と同じになった | 次のときは停止して伝える：取り込みに失敗した（オフライン・認証エラー・手元だけのコミットがある）／リポジトリが main 以外のブランチ／`guidelines/rules/` に未コミットの変更がある（ルールを編集中の可能性があるため、消さない） |
| C-3 | スキルとスクリプトをリモートの最新にそろえる | 下記の手順で**自動で** リモート（このリポジトリの `origin` の main）の最新を取り込み、本スキルと `design-system-measure` が `origin/main` と同じになった。かつ、`design-system-measure/scripts/measure-scripts.md` の「ルールと照合する定数」の表の定数が、`guidelines/rules/` の値と一致する | 次のときは停止して伝える：取り込みに失敗した（手元の未コミットの変更と重なる等）／本スキルか `design-system-measure` に未コミットの変更がある／定数がルールと食い違う。手元でスクリプトを書き換えての実行はしない（書き換えが必要なら、`measure-scripts.md` を更新して版を上げ、リモートにプッシュする） |
| C-4 | Figmaの取得テスト | 対象の Component Set について、下記の4つがすべてエラーなく取れる | 停止し、取れなかった項目と使ったツール（`use_figma` の経路）を伝える。環境を直してからやり直してもらう |

**正本は常にリモートの main とする。** 手元のファイルが古い・新しいにかかわらず、DSレビューはリモートの main と同じ内容で行う。そのため C-2・C-3 では、ユーザーに尋ねずに最新を取り込む（取り込みは手元の変更を消さない `--ff-only` だけを使う。`reset`・`checkout --`・`stash` などで手元の変更を消さない）。

**C-3 でスキルが更新されたときは、読み直してから進む。** 起動時に読み込んだ SKILL.md と `references/` は、取り込み前の古い版である。取り込みで本スキルか `design-system-measure` のファイルが変わったら（下記の `changed` が空でなければ）、SKILL.md・`references/` の全ファイル・`measure-scripts.md` を読み直し、読み直した内容に従って C-1 からやり直す。

C-2・C-3 のコマンド（リポジトリのルートで、上から順に実行する。どこかで失敗したら停止する）:

```bash
# guidelines/ はこのリポジトリに含まれる。ルール（C-2）とスキル（C-3）を同じ取り込みでそろえる
R="guidelines/rules"
S=".claude/skills/design-system-audit-skill .claude/skills/design-system-measure"
git branch --show-current                               # 「main」でなければ停止
git status --porcelain -- $R                            # C-2: 空でなければ停止（ルールを編集中）
git status --porcelain -- $S                            # C-3: 空でなければ停止（スキルを編集中）
before=$(git rev-parse HEAD)
git pull --ff-only origin main                          # 失敗したら停止（ほかの未コミットのファイルは残る）
changed=$(git diff --name-only "$before" HEAD -- $S)    # 空でなければ、スキルを読み直して C-1 からやり直す
git rev-list --count HEAD..origin/main -- $R            # C-2: 0なら合格
git rev-list --count HEAD..origin/main -- $S            # C-3: 0なら合格
git log -1 --format='%h %ci' -- $R                      # C-2 の版としてScopeに記録する
git log -1 --format='%h %ci' -- $S                      # C-3 の版としてScopeに記録する
```

C-4 の取得テスト（`use_figma` で1回だけ実行し、件数と成否だけを持ち帰る。figma-use を先に読み込む）:

1. 対象 Component Set の名前とバリアント数
2. 対象 Component Set の `description`（空文字は「取得できた・空」として合格。エラーや `undefined` は不合格）
3. ローカル Variables のコレクション数と変数の総数（`figma.variables` が使えなければ不合格）
4. 対象 Component Set 内の最初のバリアントの `layoutMode`

**C-4 で止まったときの直し方（ユーザーに伝える）**

`use_figma` は Figma のリモート接続（`.mcp.json` の `figmaRemoteMcp`、`mcp.figma.com`）にあり、各自が1回 Figma にサインインしないと使えない。デスクトップ接続（`.mcp.json` の `Figma`、`127.0.0.1:3845`）はサインインなしでつながるが、`get_metadata` などの読み取りだけで、Description・Variables の構成・測定スクリプトは使えない。デスクトップ接続だけで代わりに進めない。

1. Claude Code をリポジトリのルートで開く（`.claude/settings.json` で `figmaRemoteMcp` は有効になっている）。
2. メッセージ欄で `/mcp` を開き、`figmaRemoteMcp` を選んで「Authenticate」を選ぶ。アプリで開けないときは、ターミナルでリポジトリのルートに移動して `claude` を起動し、そこで `/mcp` を実行する（サインインの状態は同じPCで共通）。
3. ブラウザで開いた Figma のページで、会社の Figma アカウントでログインし、アクセスを許可する。
4. もう一度 `/mcp` を開き、`figmaRemoteMcp` が「connected」で、ツールの一覧に `use_figma` があることを確かめる。
5. DSレビューを最初から依頼し直す（C-1 からやり直す）。

それでも取れないときは、そのアカウントで対象のFigmaファイルを開けるか（権限）、個人ではなく会社のアカウントでサインインしたかを確かめてもらう。サインインできてもツールが出てこないときは、Figma の管理者にプランや席の制限がないかを確かめてもらう。

- C-4 で取れた「Component Set名・バリアント数・コレクション数・変数の総数」は、**対象の指紋**としてScopeに記録する。別の人のレポートと比べるときは、指紋が一致していることを確かめてから比べる（一致しなければ、Figma側が変わっているので比べない）。
- C-2〜C-4 は「今のまま続けて」と言われても省略しない。合わないまま進めると、得点が実施者ごとに変わるためである（C-1 だけは「実行モデルの確認」の例外に従う）。

### 環境が原因の「未検証」が出たときは得点を出さない

開始前チェックに合格した後でも、レビュー中にFigmaやリポジトリから情報が取れず「未検証」になった項目（環境が原因の未検証）が1件でも出たら、**得点率と判定を出さない。** サマリには「得点率：—（暫定：環境が原因の未検証 n件）」「判定：暫定」と書き、付録Bに未検証の項目と原因を並べる。分母が縮んだ得点は、他の人の得点と比べられないためである。

- 環境が原因の未検証：ツールのエラー、取得できない値、ファイルが開けない など。
- 判断が原因の未検証：委譲先のレビューが未実施、所在マップにガイドラインのnode-idがない など（AI実利用テストは得点外のため、未実施でも未検証に数えない）。こちらは従来どおり得点計算から除外し、件数をScorecardに出す（得点は出す）。
- 2つは付録Bで分けて数える。

## 運用ルール（トークン効率）

本スキルは大量のFigmaデータを扱うため、実行時に次を守る。**新しいカスタムサブエージェントを作らず、既存の集計方針・Agentツールの範囲で実現する。**

### 集計してから持ち帰る

`use_figma` で取得したノード・Variantデータは、生の配列やツリーのままレビューの文脈に持ち帰らない。**件数・頻度・キャップ済みサンプル（20〜30件）に集計したものだけ**を返す。生データを大量に返すとトークン上限超過や通信断を招き、失敗時の再実行でかえってコストが増える。

### ルール・参照文書は1回だけ読む

`guidelines/rules/` の5本と本スキルの `references/` は、レビュー開始時に1回だけ読み込む。カテゴリ（A〜I）ごとに読み直さない。後述のサブエージェント分割を行う場合も、ファイルパスを渡すのではなく、**該当カテゴリに必要なルールの要点を要約してプロンプトに埋め込む**（サブエージェントは前の会話を引き継がないため）。

### 大規模DSの分割走査

起点直下の子（セクション等）が多い場合、まず**件数のみを数える軽量走査**でComponent Setが集中する領域を特定し、そこを測定ルートとする。一括で全階層を走査しない（通信断・タイムアウトのリスクがあり、失敗時の再走査でコストが倍加する）。領域ごとに分けて個別に測定する。詳細は [design-system-measure の measure-scripts.md](../design-system-measure/scripts/measure-scripts.md) を参照。

### カテゴリ単位のサブエージェント化（条件付き）

対象DSの規模が大きい場合（目安：Component Set数が50を超える）、カテゴリまたは領域単位で `Agent` ツール（既存の汎用サブエージェントでよく、新規のカスタムエージェント定義は不要）に分割してよい。

- 各Agent呼び出しのプロンプトは自己完結させ、ルールの要点（上記「ルール・参照文書は1回だけ読む」参照）を埋め込む。
- サブエージェントは判定結果・根拠・証拠のみを返し、生データはメインセッションへ持ち帰らない。
- **規模が小さいDS（目安50セット未満）では分割しない。** サブエージェント起動のオーバーヘッドが集約の利益を上回る。

### 難所判定のみ上位モデルへ一時エスカレーション

次の判定はルールへの機械的な当てはめでは決まらない構造判断であり、`Agent` ツールの `model` パラメータで**その呼び出しだけ**上位モデル（`opus`）へ一時的にエスカレーションしてよい。メインセッションのモデルは変更しない（ユーザーによる `/model` 切り替えは不要）。

| 判定 | 該当項目 |
|---|---|
| 軸で表すべき差分が名前に埋め込まれていないかの構造判断 | B1（CA-02） |
| 同一概念が複数の軸名に散在していないかの横断発見 | B1／新出共通軸候補（variant-naming-rules V-04-2） |
| 同一役割の世代堆積の束ね方 | A3（CA-01・CA-03） |

上記以外の項目（ルールIDへの当てはめ、Description起案、レポート整形等）はメインセッションのモデルで行う。

## 参照順序

必要な情報だけを次の順序で読む。

1. 対象アプリ、プラットフォーム、Figmaファイル／ライブラリ／ページ／ブランチ、レビュー範囲、目的を確認する。
2. **所在マップ** [guidelines/design-system-map.md](../../../guidelines/design-system-map.md) で対象DSの所在（ファイルキー・node-id）を確認する。存在しない、または情報不足ならその事実をレポートし、推測した所在を正本として保存しない。
3. 対象アプリが分かる場合は、原則 **共通（ガイドライン・共通UI・共通Token）＋ 対象アプリ固有DS** を優先して参照する。固有DSはCommonの複製ではなく差分・例外の層として扱う。
4. **評価観点** [references/ai-ready-criteria.md](references/ai-ready-criteria.md) を読む。レビューモードとCore項目の指定はこのファイルに従う。
5. 対象カテゴリに応じて次の評価観点を読む（Coreでは、Core項目を含むカテゴリだけ）。**各観点は形式判定を `guidelines/rules/` に委ねる。**
   - Component設計: [references/component-criteria.md](references/component-criteria.md)
   - Variant / State: [references/variant-criteria.md](references/variant-criteria.md)
   - Naming / Layer構造: [references/naming-criteria.md](references/naming-criteria.md)
   - Variables / Design Token: [references/variable-criteria.md](references/variable-criteria.md)
   - D・F・G・H・I: `ai-ready-criteria.md` 内の該当節
   - 判定例・改善提案の書式: [references/examples.md](references/examples.md)
   - **点・重大度・修正リストの行の決め方: [references/scoring-rules.md](references/scoring-rules.md)（必ず読む）**
6. 形式の判定に入ったら、該当するルール正本を参照する。
   - レイヤー名 → [guidelines/rules/layer-naming-rules.md](../../../guidelines/rules/layer-naming-rules.md)
   - Variant軸・値・Property名・Component Set名 → [guidelines/rules/variant-naming-rules.md](../../../guidelines/rules/variant-naming-rules.md)
   - Description → [guidelines/rules/description-format.md](../../../guidelines/rules/description-format.md)
   - Component作成ルール（CA） → [guidelines/rules/component-authoring-rules.md](../../../guidelines/rules/component-authoring-rules.md)
   - Variablesの適用（VR） → [guidelines/rules/variables-rules.md](../../../guidelines/rules/variables-rules.md)

ルール間で競合する場合は、明文化された例外規定を優先する。優先順位が不明なら勝手に解決せず、影響に応じてMajorまたはCritical候補として報告する。ルールに定義がない事象は、勝手に判断せず「ルールに定義がない」ことをIssueとして挙げ、`guidelines/rules/` への追記が必要であることを報告する。

## レビューの進め方

### 1. Scope

- 対象アプリ／プロダクト、プラットフォーム、対象Figma資産、範囲、想定利用者、主要ユースケース、レビュー日時、実行環境を記録する。
- 「開始前チェック」の結果を表で記録する（C-1 実行モデルID／C-2 `guidelines/` のコミットと日時／C-3 スキルとスクリプトのコミットと日時／C-4 取得テストの成否と使ったツール、対象の指紋）。
- レビューモード（Core／Extended）を確定して記録する。指定がなければCoreとする。
- **対象名を固定する。** 対象名は、Figmaの Component Set名（単体Componentなら Component名）をそのまま使う（例：`iconButton`。`<サービス名>-iconbutton` のように、アプリ名を足したり小文字に変えたりしない）。範囲がページやセクションのときは、所在マップに書かれた名前を使う。この対象名を、レポートのファイル名の `<対象>` と、修正リストの永続IDの `<対象>` の両方に使う。
- **前回のレポートを引用するときは、ファイルがあることを確かめる。** パスを開いて中身を読めた場合だけ「前回」として引用し、パスを付録Aに書く。見つからなければ引用せず、「前回のレポートなし（探したパス）」と書く。推測したファイル名で引用しない。
- 対象DSの層（共通DS／アプリ固有DS）を確認して記録する。アプリ固有DSの場合、共通DSを **Instance参照か複製か** を必ず区別する（修正方針が正反対になる）。
- **測定の起点がDS本体であることを確認して記録する。** 起点配下で Component Set が集中する領域を測定ルートとし、Component Set を含まない画面レイアウト用セクション（利用例・画面モック）は対象から除外する。所在マップの node-id が画面同居のページを指す場合は DS本体セクションの node-id に読み替え、除外した領域を付録Aに記録する。
- 委譲対象（`figma-ai-review`、`figma-review-layers`、`accessibility-review`）の実施状況を確認し、未実施なら該当項目を未検証として扱う旨を記録する。
- 全数かサンプルかを決める。サンプルの場合は母集団、抽出方法、件数を記録する。
- AI実利用テストを実施する場合は、実施場所の承認状況と後片付け方針を先に確認して記録する。未承認ならHを未実施とする。

### 2. 実測（数える）

A1・C4・D1・E6、F1の記載率、Variant／Property／Component Set名の違反候補率（A5・B1・B2・C1）、Property の公開・組合せの欠け・変数の参照先（A4・B5・E1・E2。Script E）は数えないと判定できない。**[design-system-measure](../design-system-measure/SKILL.md) の測定結果（走査スクリプトは同スキルの `scripts/` にある）を、測定値の証拠として記録する。測定結果がなければ、同スキルの手順で測る。本スキルの中で独自に数えない。**

- 走査範囲を固定する（起点・深さ・COMPONENT内部・INSTANCE内部・非表示レイヤーの扱い）。詳細は [references/ai-ready-criteria.md](references/ai-ready-criteria.md) の実測節に従う。
- 分母と分子の両方を記録する。比率だけを書かない。
- 再レビュー時は前回の分母を併記する。分母が変われば走査範囲が変わったことを意味し、その場合は得点を比較しない。
- 測定値は [references/scoring-rules.md](references/scoring-rules.md) の換算表（暫定値）で点にする。その場で閾値を作らない。測定値と、当てはめた表の行の両方を残す。

### 3. 評価（Score and classify）

- `references/ai-ready-criteria.md` のA〜Iのうち、レビューモードの範囲にある項目を `2 / 1 / 0 / N/A` で評価し、Critical／Major／Minorを別軸で付与する。
- **点は [references/scoring-rules.md](references/scoring-rules.md) の「項目ごとの点の決め方」で、重大度は同ファイルの「重大度の表」で決める。** 表の手順にない理由で点や重大度を上げ下げしない。表で決められないときは点を付けずに要確認に回し、表への追記を提案する。
- 形式の合否は `guidelines/rules/` のルールIDで判定する。「AIが誤る」だけを理由にしない。
- カテゴリ別・総合得点率を計算する。Criticalが1件以上なら得点にかかわらず `Not ready — Critical issue` とする。
- 「確認できなかった」を0点にしない（未検証にする）。0点は「満たさないことを確認した」ときだけ付ける。
- Core範囲外の項目は「Core範囲外」と記し、N/Aや0と混在させない。
- 複数カテゴリにまたがる同じ根本原因を統合し、改善提案を重複させない。

### 4. レポートと承認依頼

- 「出力仕様」に従い、**本体（サマリ・修正リスト・要確認）と付録**に分けてレポートを作成する。
- 修正リストはルールIDを併記し、実行欄（可／要決定／要起案）と既存デザインへの影響を書く。
- 破壊的影響がある提案には、移行順、既存Instance／実装への影響、Deprecated期間を含める。
- **要確認・ルール未定は、レポート保存後にチャットでも番号付きテキストで確認する**（下記「要確認のチャット確認」）。レポートmdだけで済ませない。
- **保存の前に、同じ名前のファイルがないかを確かめる。** あれば上書きせず、`-v2`（それもあれば `-v3`…）を付けて保存する（`.claude/CLAUDE.md` の「既存ファイルは上書きしない」）。保存したパスをチャットで伝える。
- 修正対象・方針・対象ファイルまたはブランチの承認を待つ。ここで初回レビューを「承認待ち」として完了できる。
- **本スキルはここで停止する。** 修正の実行には進まない。

#### 要確認のチャット確認

要確認・ルール未定はテキストで決められることが多い。レポートmdの表に埋もれさせず、レポート保存後にチャットへ次の形で書き出す。

- 番号はレポートの要確認事項（修正リストのNo.と対応）と同じにする。レポートと食い違わせない。
- 1項目は3〜4行で、「何が問題か／選択肢（推奨を先頭にA・B…）／ルール未定なら追記先ファイルと追記する文面」を書く。
- 末尾に答え方の例を添える（例：「7=A、15=B、19=A」）。
- 区分（ルール未定／要確認）と重大度を各項目の見出しに付ける。ルール未定を先に並べる。
- 専門用語やノードIDを裸で書かない。パーツ名と「変更前→変更後」で書く。
- 回答を受けたら、ルール未定は `design-rules-editor` への依頼として扱う（本スキルではルールを書かない）。要確認の回答は修正リストの「実行」欄（要決定→可）へ反映する。

修正の実行後も同様に、「どのパーツの何を変更した／していないか」を番号で報告する（`design-system-apply-fixes` の報告）。

### 5. 再レビュー（修正が別途行われた後）

- 承認済みIssueの受入条件を検証し、対象項目の旧評価と新評価を併記する。
- **前回と今回のIssueは、No.ではなく永続IDで対応させる。** 付録Dに「前回の永続ID／前回No.／今回の永続ID／今回No.／状態（解消・部分解消・未解消・再発・新規）」の対応表を置く。前回にない永続IDは「新規」、今回にない前回の永続IDは「解消」または「対象外」とする。前回のレポートに永続IDがない場合は、前回の行を本スキルの永続IDの形に当てはめて対応させ、当てはめた結果を表に書く。
- 変更したComponentの代表Instance、Variant、Mode、Patternを回帰確認する。
- Critical／Majorに関係するAI実利用テストを、可能な限り初回と同じ入力・条件で再実行する。
- Issueを「解消／部分解消／未解消／再発／対象外」で更新し、副作用と残存リスクを記録する。
- 分母が前回と違う場合は得点を比較しない。Criticalが残る場合はAI-readyと判定しない。

## 出力仕様

**レポートは「本体」と「付録」に分ける。** 本体はUIデザイナーが読む。付録はレビューの記録と再レビュー比較用で、UIデザイナーが読む必要はない。保存先はリポジトリの共通ルール（`.claude/CLAUDE.md`）に従い、本スキルで固定の保存先を定義しない。

### 本体（3節のみ）

1. **サマリ**: 対象、レビュー日、レビューモード、総合得点率、判定、重大度別件数（修正Issueと、ルール未定の決定事項を別枠で）、重要発見3〜5件、次に必要な判断。総合得点率は付録のスコアと一致させる。環境が原因の未検証があるときは、得点率と判定を「—（暫定）」とする（「開始前チェック」参照）。
2. **修正リスト**: 着手順に並べた1行1Issueの表。Figmaの作業単位で段階に分ける（① Component Set名 → ② Variant値 → ③ Property名 → ④ レイヤー名 →〈ここまでで再レビューできる区切り〉→ ⑤ Description → ⑥ Variant構造）。行の単位・永続ID・並び順・「提案：」の値は [references/scoring-rules.md](references/scoring-rules.md) の「修正リストの行の作り方」に従う。列は「**No.**／永続ID／重大度／パーツ（**FigmaのURLリンク**。Node IDを裸で書かない）／修正内容（**提案を含む**）／理由・根拠（**ルールIDに名前をカッコ書きで並記**）／件数／実行（可・要決定・要起案）／既存デザインへの影響」。
   - **No.は全段階を通した連番**（①から順に1,2,3…。段階ごとに振り直さない）。欠番・重複を作らない。
   - **修正内容には「提案：」を付けて、ルールに沿った具体的な名前・値・軸名の案を書く**（例：`ticket_parts`→`ticketParts`）。提案であることが分かるよう必ず「提案：」と明記する。用途を推測しないと作れない案は、確認事項に回す旨を添える。**構造の問題（sizeに別の差分が混ざった値など）は「提案：なし」で終わらせず、対象のバリアントを読み取って（寸法・色・構造の差分）、新しい軸の名前と値の具体案を出す。** 共通軸リスト（variant-naming-rules V-04-2）にある軸を優先して当てる。提案を作れない場合は「提案：なし（理由）」と書く。**「〜に置き換える（または統合）」のような抽象的な書き方だけで終わらせない。**
   - 実行欄の「要決定」は「提案を承認すればその内容で実行できる」状態を指す。
3. **要確認事項**: Issueにしないが判断が必要なもの。本文で「要確認」と書いたら必ずここに転記する。
   - **番号は修正リストのNo.と対応させる**（同じNoに複数あれば-a、-b）。修正リストの対象外（未検証・未実施など）は、修正リストの最終Noの次から続ける。
   - **ルール・ガイドラインに追記・修正しないと判断できないものは、区分を「ルール未定」とし、重大度を表記する。** 重大度は関連する修正の重大度より1段階引き上げる（🟡→🟠、🟠→🔴）。ルールが決まっていないため判断できず、決める必要があること（＝重大であること）を示すためである。DSレビューはルールづくりも兼ねる。それ以外の確認事項の重大度は「—」とする。
   - 各行に「提案（ルールの追記・修正案ほか）」を付け、追記先ファイルと追記案を書く。

**本体には根拠・測定値・評価値・自己チェックを書かない（すべて付録）。専門用語をそのまま残さない。**

### 付録

- **A. 測定条件**: 開始前チェック（C-1〜C-4）の結果と対象の指紋、走査範囲（起点・全ノード数・除外の種別別件数）、参照したルール正本と所在マップ、対象DSの層、共通DSの参照状況、B2の比較範囲、サンプリング、未検証範囲。
- **B. スコア**: カテゴリ別・総合の獲得点／最大点／得点率、重大度別件数、Core範囲外の項目数、未検証の項目数（環境が原因／判断が原因に分けて、項目IDと原因を並べる）。
- **C. 詳細評価**: 各IDの評価、重大度、根拠・証拠、影響、N/A理由または未検証に必要な情報。実測項目は測定値を併記。
- **D. Issueの根拠**: 修正リスト各行に対応する Issue ID（対応する修正リストのNo.も併記）、関連項目、事実、証拠、影響、影響範囲、受入条件、代替案、指示文。件数の突き合わせを行う。区分が「ルール未定」の要確認事項は、RULE-ID・要確認No.・重大度・追記先・現状（根拠）・提案する追記案を表にまとめる。再レビューでは、前回と今回の永続IDの対応表もここに置く（「5. 再レビュー」）。
- **E. AI実利用テスト結果（得点外・実施した場合のみ）**: 実施場所と承認状況、シナリオ、入力条件、結果、主な選択、失敗／逸脱、証拠、後片付け結果。
- **F. Figma外の引き継ぎ**: Figma Agent版レビューを引用した場合の実施日と対象、CC固有項目（E1・F6/I5・I2・I3/I4・H3）の結果。
- **G. 提出前の自己チェック結果**: 件数の突き合わせ表と数値の一致確認（[references/examples.md](references/examples.md) の書式に従う）。
- **H. 追加提案（得点外）**: ルールに違反はしていないが、構造の工夫として提案したいもの（新しい軸の追加・分離など）。実施する人によって出たり出なかったりするため、点・重大度・修正リストに入れない。採用するかは人が決める。

## 完了条件

初回レビューは、開始前チェック（C-1〜C-4）にすべて合格して結果を記録したうえで、対象と参照関係、レビューモード、範囲内項目の評価、N/A／未検証／Core範囲外の理由、得点、重大度、証拠、改善提案、受入条件、（実施した場合は）AI実利用テストの実施場所と結果、承認待ちの次アクションが記録され、承認された検証場所以外のFigmaを変更しておらず、修正の実行に進んでいないときに完了する。

再レビューは、承認済みIssueの状態、前回と今回の永続IDの対応表、旧新評価、回帰結果、残存リスク、Criticalの有無を再判定したときに完了する。

## やってはいけないこと

- 開始前チェック（C-1〜C-4）に合わないまま始める／測定スクリプトを手元で書き換えて実行する／環境が原因の未検証があるのに得点率を出す。
- 承認前にFigmaを変更する／レビューから修正へ自分で進む／レポート提出で停止しない。
- **修正を実行する（本スキルはレビューと提案まで。実行は対象外）。**
- レビュー依頼を修正許可と解釈する。範囲が確定しない指示（「全部直して」等）で着手する。
- **`references/` でルールを再定義する（形式判定は必ず `guidelines/rules/` を参照する）。**
- 「AIが誤る」だけを根拠に書く（違反したルールIDを示す）。ルールIDに名前を並記しない。
- 未観察の項目を推測で評価する／情報不足をN/Aで処理する（未検証を使う）／「確認できなかった」を0点にする。
- scoring-rules.md の表を使わずに点・重大度を決める／ルールにない構造の工夫を修正リストに入れる（付録Hに分ける）／比率だけで書く／走査の深さ・除外基準を回ごとに変える。
- 総合得点率をScorecardと別に計算する／重大度の件数を4箇所で食い違わせる。
- 本体に根拠・測定値・評価値を書く／Node IDを裸で書く／専門用語をそのまま残す。
- 規定がある値を実装の多数派に合わせて正しいと判定する（規定が正本）。
- Figmaの仕様上そうなるだけのもの（TEXTノードの自動命名、Propertyキーの内部ID）を違反として報告する。
- **`🚫`が付いた資産・値について、削除する、統合する提案をする。** `ver`の値・Component Set名・単体Component名にある`🚫`は意図的な非推奨マーカーであり、そのまま尊重し、修正リストに載せない（V-08）。それ以外の位置の`🚫`（例：`state=🚫完了`）はV-08違反として指摘してよい。ただし、同義の無印値と並存している場合（`完了`と`🚫完了`）も削除・統合は提案せず「要判断」とする。同義の無印値がない場合の直し方は、`🚫`を外す名前変更までとする。
