# 判定例と改善提案の書式

固有DSの実例がない段階の汎用例と、改善提案（修正リスト・Issue・自己チェック）の書式。実レビューでは対象の証拠に置き換え、例を事実として流用しない。

---

# 1. カテゴリ別の判定例（良い例／問題例）

## Component

- **良い例**: `button` の公開Propertyが `hierarchy=primary`、`size=medium`、`state=default`、`showLeadingIcon=false` のように意味を表し、Descriptionに採用条件と代替資産がある。
- **問題例**: `button new`、`button final 2`、`青ボタン` が同時公開され、正本や置換先が分からない（A3）。主要画面へ広く影響するならCritical候補。

## Variant / State

- **良い例**: `state` の語彙が同系Componentで統一され、無効な `state=disabled + loading` の扱いが説明される。
- **問題例**: 見た目差分ごとにVariantを追加し、`Blue / 40 / On` のような値から用途を判断できない（B2）。世代・サイズ・種別が名前に埋め込まれ軸が使われていない場合は B1（CA-02）。

## Naming / Layer

- **良い例**: `form/input/text` を業務語で検索でき、内部Layerも `label`、`input`、`caption` と役割で揃う。
- **問題例**: `Frame 12` や `Group 7` が主要Layerに残る（C4・layer-naming-rules R-05）。Propertyの `helper` がどのLayerを操作するか追跡できない（C6）。

### 意味的な命名品質（C9〜C11）— 形式は正しいがAIが役割を判断できない例

いずれもMinorが基本。修正は強制せず提案として示す。

| 観点 | 問題例 | 改善案 | 補足 |
|---|---|---|---|
| C9 機能の具体性 | `actionButton`、`dataContainer` | `updateButton`、`answerListContainer` | 位置やVariant値で用途が確定するなら満たすと判断してよい |
| C10 親情報の冗長性 | `dataTable` の中の `tableScrollBar` | `scrollBar` | Property対象Layerなど単独で識別子になる要素は一意性を優先する |
| C11 命名の粒度 | `filterControlTooltip`、`tableDataScrollBar` | `tooltip`、`scrollBar` | 概念が増える原因が階層の潰れなら、C5（Layer階層）の指摘に寄せる |

## Auto Layout / Responsive

- **良い例**: LabelはHug、入力領域はFill、補足文は複数行に対応し、狭幅・長文でも順序と余白を維持する。
- **問題例**: 固定幅とAbsolute positionに依存し、ローカライズで文言が重なる（D5）。

## Variables / Token

- **良い例**: Componentは `color.action.primary.background.default` のようなSemantic tokenを参照し、Mode切替で必要値がすべて変化する。
- **問題例**: 公開ComponentがHex値やPrimitiveへ直接依存する（E2・E6）。余白・色・文字の生値が [variables-rules.md](../../../../guidelines/rules/variables-rules.md) VR-02 の条件に当たれば違反（CA-08）。

## Documentation / Pattern

- **良い例**: 類似Componentとの選び分け、Do / Don't、Empty／Loading／Error、実装リンク、Owner、最終更新日が同じ導線で見つかる。
- **問題例**: 正しいComponentは存在するが、代表PatternがDetached copyで構築され、AIがそれを正本として模倣する（G6）。

## コード連携・機械可読性

- **良い例**: 利用条件とDo / Don'tがDescriptionとテキストレイヤーに書かれMCPで取得でき、Variable に対応するコード識別子の変換規則が明文化され、リポジトリ側の機械可読文書に同期時点付きでミラーされている。
- **問題例（画像のみ）**: ガイドラインが画像として貼られAIが取得できない（I1）。人のレビューでは現れずAI利用時のみ再現。影響に応じてMajorまたはCritical候補。
- **問題例（ミラー未整備）**: 正本TokenがFigmaにしかなくリポジトリ側にミラーがない（I2）。整備計画の有無で重大度を分ける。
- **問題例（識別子の非一意）**: 日本語のComponent名しかなく、コード生成のたびに別の英語名が割り当てられる（I3・I4）。対応表と既存実装名の優先方針を示す。

## AI実利用テスト

- **良い例**: 「長い日本語ラベルを含むエラー状態のフォーム」を要求すると、AIがCommonと対象アプリ固有DSから正本を選び、Semantic tokenと正しいPropertyで構築し根拠を説明できる。
- **問題例**: 同じ条件で `🚫` 付きやDeprecated component、生値を採用する（H6）。プロンプト・利用可能ライブラリ・権限・試行回数を記録し、モデルの偶発差かDSの発見性問題かを切り分ける。

# 2. 修正リストの書式（本体・第2節）

**Figmaの作業単位で段階に分け、段階ごとに表を作る。1行＝1つのルールID×1つの対象（軸の値・名前・レイヤー名の種類）。永続ID・並び順・「提案：」の値は [scoring-rules.md](scoring-rules.md) の「修正リストの行の作り方」に従う。** 各段階の冒頭に、Figmaのどこを触るかと既存デザインへの影響を1行で書く。

| 段階 | 見出し | 触る場所 | 既存への影響 |
|---|---|---|---|
| 準備 | 命名を決める（Figma作業なし） | — | なし |
| 1 | Component Set名を直す | Assets／レイヤーパネル | なし |
| 2 | Variant値を直す | 右パネルのバリアント欄 | なし |
| 3 | Property名を直す | 右パネルのプロパティ欄 | なし |
| 4 | レイヤー名を直す | コンポーネント内部 | なし |
| — | **ここまでで再レビューで改善を確認できる** | | |
| 5 | Description を書く | 右パネルの説明欄 | なし |
| 6 | Variant構造を変える | 右パネル（軸の追加・分離） | **あり** |

表の列と書き方:

| 列 | 内容 |
|---|---|
| No. | **全段階を通した連番**（1,2,3…）。要確認事項の番号と対応させる。表示用で、再レビューの対応は永続IDで取る |
| 永続ID | `<対象>/<ルールID>/<部位>-<現在の値>`（例：`iconButton/V-05-2/state-default`） |
| 重大度 | 🔴／🟠／🟡。[scoring-rules.md](scoring-rules.md) の「重大度の表」で決める |
| パーツ | 名前を **FigmaのURLリンク**にする（`https://www.figma.com/design/{fileKey}/{name}?node-id={nodeId}`。node-idは**ハイフン区切り**）。**Node IDを裸で書かない** |
| 修正内容（提案を含む） | 何をどう直すかを1文＋**「提案：」でルールに沿った具体的な名前・値・軸名の案**。件数が多い場合は代表例＋「ほかN件」（全件は実行時に提示）。用途の推測を含む案はその旨を添え、作れない場合は「提案：なし（理由）」 |
| 理由・根拠 | **違反したルールを示し、ルールIDに名前をカッコ書きで並記する**（`layer-naming-rules R-08（綴り誤り）`）。ルールが無い場合は「◯◯（ルール名）が未策定」 |
| 件数 | 対象数 |
| 実行 | 下表の3値 |
| 既存デザインへの影響 | `なし` または `あり`＋何が起きるか |

「実行」欄の判定:

| 値 | 意味 |
|---|---|
| **可** | 変更前後が全件確定（機械的変換の規則で一意に決まるものを含む）。番号指定でそのまま頼める |
| **要決定** | 変更後の名前・軸名を人が決める必要がある |
| **要起案** | 書く内容を先に作る必要がある（Descriptionなど） |

- 記号除去・ケース統一は「可」（layer-naming-rules 第4節の機械的変換で一意に決まる）。
- **1件でも人の判断が要る対象が混ざれば、その行全体を「要決定」にする。** 混在するなら行を分ける。
- 着手順は重大度順ではなく、段階（①〜⑥）の順 → 同じ段階の中はルールIDの昇順 → 同じルールIDの中は現在の値のアルファベット順で決める（scoring-rules.md）。

修正内容の例:

| No. | 永続ID | 重大度 | パーツ | 修正内容（提案を含む） | 理由・根拠 | 件数 | 実行 | 影響 |
|---|---|---|---|---|---|---|---|---|
| 1 | `iconButton/V-01/size-extralarge` | 🟡 | [iconButton](URL?node-id=xxx-xxx) | `size=extralarge` を直す。<br>**提案：** `xlarge` | `variant-naming-rules` V-01（sizeの値） | 20件 | 可 | なし |
| 2 | `iconButton/V-05-2/state-active` | 🟠 | [iconButton](URL?node-id=xxx-xxx) | `state=active` を直す。<br>**提案：** `pressed` または `selected`（どちらの意味かは要決定） | `variant-naming-rules` V-05-2（状態の値） | 20件 | 要決定 | なし |
| 3 | `sidebar/R-08/layer-fliter` | 🟡 | [sidebar/fliter](URL?node-id=xxx-xxx) | `fliter` を直す。<br>**提案：** `filter` | `layer-naming-rules` R-08（綴り誤り） | 1件 | 可 | なし |

要確認事項の書式（番号は修正リストのNo.と対応）:

| No. | 重大度 | 区分 | 確認したい内容 | 提案（ルールの追記・修正案ほか） |
|---|---|---|---|---|
| 2 | 🔴 | **ルール未定** | 配置を表す軸名を共通軸に加えるか | `variant-naming-rules` V-04-2に`placement`を候補として追記する案 |
| 3 | — | 判断依頼 | この部品の用途を教えてください | 用途が分かれば名前を提案します |

- 区分が「ルール未定」＝ルール・ガイドラインに追記・修正しないと判断できない項目。**関連する修正の重大度より1段階引き上げる**（🟡→🟠、🟠→🔴）。それ以外は「—」。
- ルール未定の根拠は、付録Dに RULE-ID・追記先・現状・追記案として表にまとめる。

# 3. Issueの書式（付録D）と件数の突き合わせ

## Issue記述例

```markdown
### DSR-001 — 🟠 要対応（Major） — B1, H1

- 事実: `button` と `iconButton` で同じ概念が `type=main` と `hierarchy=primary` に分かれている。合計 4件。
- 証拠: 対象ファイル、Component set名、Node ID、観察した値。
- 影響: AIが類似Component間で誤った軸を選び、画面間の優先度表現が不統一になる。N件（M Component Set）。
- 推奨変更: 語彙を公式の意味軸へ統一する（名前変更で直せるものに限る。構造変更が要るものは要判断）。旧値の非推奨化に`🚫`は使わない（`🚫`は`ver`の値・Component Set名・単体Component名のみ。V-08）。
- 代替案: すぐにRenameできない場合、Descriptionと対応表で選択条件を補足する。
- 影響範囲: 既存Instance、Code component、Code Connect、ガイドライン。
- 受入条件: 対象setで語彙が一致し、既存Instanceの見た目と実装対応を維持する。
- 次の状態: UIデザイナー承認待ち。承認前は変更しない（修正実行は本スキルの対象外）。
```

## 件数の突き合わせ（提出前に必ず作る）

- **N は常に「指示文に書く対象の数」で統一する。** 「問題が起きている件数」と「作業対象の件数」を混ぜない。
- 0点の項目は例外なくIssueにする。1点は原則Issue化し、しない場合は理由を書く。
- 同種の問題は1つのIssueにまとめ、対象を全件列挙する。
- 6件以上は代表3件を示し、全件の内訳は「事実」欄に書く。5件以下は全件列挙。

| Issue ID | 事実 N | 影響範囲 N | 指示文の最終番号 | 判定 |
|---|---|---|---|---|
| DSR-001 | 4 | 4 | 4（全件） | ✅ |
| DSR-002 | 22 | 22 | 3（代表。全22件は承認後） | ✅ |

**「指示文の最終番号」は指示文を見て転記する（事実欄の数字をコピーしない）。** 3つ以上の数字が揃わなければ提出しない。

# 4. 提出前の自己チェック

チェックボックスだけでなく、**数えた数字を書く。** 不一致を見つけたら報告で終えず、本文を直してから提出する。

- [ ] 0点の項目すべてにIssue IDが振られているか
- [ ] 重大度の件数が Issues／Detailed／Scorecard／Executive の4箇所で一致するか（4組を並べて書く）
- [ ] 総合得点率が付録スコアと一致するか（カテゴリ別を足して総合行と突き合わせる）
- [ ] 修正リストの「パーツ」がすべてURLリンクか（Node IDを裸で書いていないか）
- [ ] 「理由・根拠」にルールIDと名前が並記されているか（「AIが誤る」だけになっていないか）
- [ ] 「実行」欄がすべての行にあり、一部でも人の判断が要る行を「可」にしていないか
- [ ] 走査した全ノード数と除外の種別別件数をScopeに記録したか（再レビューは前回と分母が一致するか）
- [ ] 本文で「要確認」と書いた項目が本体3「要確認事項」に転記されているか
- [ ] 本体が「サマリ・修正リスト・要確認」の3節に収まっているか（根拠・測定値・評価値を本体に書いていないか）
- [ ] 修正リストのすべての行に永続IDがあり、`<対象>` がファイル名の対象名と同じか
- [ ] 前回のレポートを引用した場合、そのファイルを開いて確かめたか（パスを付録Aに書いたか）
- [ ] 保存先に同じ名前のファイルがないか（あれば `-v2` を付けたか）
- [ ] 修正の実行に進んでいないか（本スキルはレビューと提案まで）

# 5. 再レビューの記述

旧評価と新評価を併記し、変更した事実だけで解消としない。受入条件、代表Instance、関連Mode、AI実利用テストを確認し、`解消／部分解消／未解消／再発／対象外` のいずれかを付ける。分母が前回と違えば得点を比較しない。
