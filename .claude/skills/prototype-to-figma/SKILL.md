# プロトタイプ → Figma 書き起こしスキル

最終的にFigmaを開発へ納品するため、**pxのずれがないこと**と**既存コンポーネントとつながっていること**を両立させる。
デザイナーが手動で直す前提なので、置換できなかったものは「どこを・なぜ・何にすべきか」を一覧で渡す。

## 前提

- 対象は `generated/prototypes/<service>/<プロト名>/<バージョンのフォルダ名>/` のプロトタイプ（エントリは `index.html`）。HTMLの新規作成は `prototype-draft` の担当。
- 公式の `generate_figma_design` / `html_to_figma` は**DSのコンポーネントを使わない**（素のフレームになる）。コンポーネントへの置換はこのスキルの工程3で行う。
- Figmaへの書き込みは `use_figma` を使う。**呼ぶ前に必ず `figma-use` と `figma-generate-design` を読み込む**（`skillNames` に両方を入れる）。置換・集計・検証の書き方と落とし穴は [references/figma-recipes.md](references/figma-recipes.md) にある。
- 書き込み先のFigmaファイル（作業用ファイルの `<書き込み先のfileKey>`）は**必須の入力**。既定の書き込み先は持たない。指定がなければ工程0で質問する。**DS本体・本番ファイルには書かない**。

## 工程0: 入力の確認（不足があれば先にまとめて質問する）

1. 対象プロトタイプのフォルダ名
2. **取り込む状態**（例：初期表示／選択中／ダイアログ表示）。状態はプロトタイプを操作して作るので、状態ごとに1回キャプチャする。再現できない状態は「未対応」として報告する
3. 書き込み先のFigmaファイル（必須。作業用ファイルのURLまたはfileKey。DS本体・本番ファイルは不可）
4. **方針（決定済み）: DS優先。** 寸法・状態の見た目がDSと合わない部品も、**DSのコンポーネントに置換する**（プロトタイプの寸法には合わせない）。プロトタイプとのずれは、置換のあとに「差分一覧」として報告する。DSに該当するコンポーネントがない部品だけが、素のフレームのまま残る

## 工程1: DS差分の確認（キャプチャの前に行う）

プロトタイプはDSのCSSで作っていても、Figmaのコンポーネントとずれていることがある（例：ボタンの寸法、ラジオの未選択状態の見た目）。置換の前に差分を洗い出す。

1. プロトタイプが使っているDS部品を、`prototype.css` / `index.html` のclassから列挙する（例：`.btn--primary`、`.toggle`、`.select`、チェックボックス、ラジオ、アイコン、サムネイルカード）
2. `get_libraries` で接続済みライブラリを確認し、`search_design_system`（`includeLibraryKeys` で絞る）で、各部品に対応するコンポーネントを探す。検索は1つの意図につき1クエリ
3. 見つかった各コンポーネントについて、`use_figma`（読み取りのみ）で次を調べる:
   - variantの種類と各variantの**幅・高さ**（これは**既定サイズ**。実際の画面では、インスタンスの幅を画面に合わせて伸ばして使われていることが多い）
   - **正本のFigma（プロトタイプの NOTES.md に書かれた画面ファイル）での実使用サイズ。** 正本の特定は次の順に行う: ① プロトタイプの `NOTES.md` の「対象・正本」の記述（ファイルのキー）を読む → ② 書かれていなければユーザーに聞く（推測しない）→ ③ `use_figma`（読み取りのみ）でページ一覧を取り、画面名に近いページを探す。ページの切り替えは1回だけ。正本の画面フレームの中のインスタンスを、コンポーネント名ごとに `幅×高さ` と件数で集計する（読み取りのみ。書き方は [references/figma-recipes.md](references/figma-recipes.md)。例：`button` が `186×48` で1件、`selectField` が `172×40` で8件）。集計はページ全体で1回にし、結果を使い回す。プロトタイプの寸法が、既定サイズと違っても、正本で実際に使われているサイズなら「ずれ」ではない。正本にない寸法だけが、プロトタイプ側のずれ
   - 正本の画面で、そのDSコンポーネントを**使っていない**部品（例：カードやサムネイル）は、DSに該当がないものとして扱う
   - 状態（未選択・選択・無効など）ごとの**見た目**（枠線の色・太さ、塗り）
4. プロトタイプの実寸・見た目と比べ、次の対応表を作って**ユーザーに見せる**:

   | プロトタイプの部品 | DSのコンポーネント | 寸法（プロト/DS） | 状態の見た目 | 判定 |
   |---|---|---|---|---|
   | … | … | 28×28 / 24×24・32×32 | 枠色が違う | 置換する（差分あり） |

   - 判定は次の3つ。**DS優先なので、DSに該当があれば寸法・見た目が違っても置換する**
     - 「置換する」: 寸法・見た目が一致
     - 「置換する（差分あり）」: 該当するコンポーネントはあるが、寸法または見た目が違う。差分は工程5の差分一覧に載せる
     - 「置換しない」: DSに該当するコンポーネントがない。素のフレームのまま残し、要コンポーネント化の一覧に載せる
   - variantが複数あり、どれが近いか迷うときは、寸法が最も近いものを選び、選んだ理由を差分一覧に書く
   - 色は、DSの変数（`search_design_system` で `entity: "variable"`）で結び付けられるものを探す。見つからなければ、そのままの値を残して一覧に載せる

## 工程2: キャプチャ（寸法の確定）

pxの基準は、HTMLのレンダリング結果をそのまま取り込むキャプチャで確定する。

1. 一時サーバーを起動する（Node を使う。Windows では `python` がストアのスタブで動かないことがあるため、Pythonは使わない）:
   ```bash
   node .claude/skills/prototype-to-figma/scripts/capture-server.js . --port 8791 --width 1024 --height 768
   ```
   - サーバーは配信時にだけ、キャプチャスクリプト・画面幅の固定・アイコンの箱の固定を差し込む。**プロトタイプのHTMLは変更しない**
   - `--width` は対象画面の幅（既定1024px）。ウィンドウ幅に左右されない
   - 起動後、`http://localhost:8791/generated/prototypes/<service>/<プロト名>/<バージョンのフォルダ名>/index.html` が200で返ることを確認する
2. `generate_figma_design`（`fileKey`、`nodeId` はセクション、`sessionId`）で `captureId` を取る。**状態ごとに別の `captureId` を取る**（1回で使い切り）
3. **アプリ内ブラウザでは動かない**（キャプチャがタイムアウトする）。**通常のChromeで開く**:
   Windows（PowerShell）:
   ```powershell
   Start-Process "$env:ProgramFiles\Google\Chrome\Application\chrome.exe" -ArgumentList '--new-window','--window-size=1100,900','<URL>#figmacapture=<captureId>&figmaendpoint=<エンドポイント>&figmadelay=5000'
   ```
   macOS（ターミナル）:
   ```bash
   open -na "Google Chrome" --args --new-window --window-size=1100,900 '<URL>#figmacapture=<captureId>&figmaendpoint=<エンドポイント>&figmadelay=5000'
   ```
   - `figmadelay` は5000ms以上にする（フォントの読込を待つ）
   - エンドポイントは、`generate_figma_design` の結果に書かれたURLエンコード済みのものをそのまま使う
4. `generate_figma_design` を `captureId` つきで5秒おきに呼び、`completed` になるまで待つ（最大10回）。`pending` が続く場合は、Chromeのウィンドウが前面にあるか、サーバーが動いているかを確認する
5. 完了したら一時サーバーを停止する。**取り込んだフレームの幅が `--width` と一致していること**を `get_metadata` で確認する

## 工程3: DSコンポーネントへの置換

工程1で「置換する」「置換する（差分あり）」と判定した部品を置換する。

- **アイコン**: DSのアイコンコンポーネント（例：`arrow_back_FILL0_wght400_GRAD0_opsz24`）を使う。**サイズは、元の枠ではなくDSコンポーネントの標準サイズに合わせ、枠の中央に置く**（キャプチャの枠はフォント由来で潰れていることがあり、枠に合わせると歪む）。色はプロトタイプと比べ、DSの変数が見つかれば変数に結び付ける
- **それ以外の部品**: `setProperties()` でテキストや表示/非表示を設定し、variantはプロトタイプの状態に合わせる。透明度などプロトタイプ側の指定は引き継ぐ
- **variantの選び方（見た目で選ぶ）**: variantの名前だけで決めない。置換前のノードの塗り・枠線・アイコンの色を読み取り、候補のvariantを仮に1つインスタンス化して同じ項目を読み取り、**最も近いものを選ぶ**。近いものがなければ、最も近いものを選び、見た目の違い（例：「DSは濃い灰色の円に白いアイコン、プロトタイプは薄い灰色の円に黒いアイコン」）を差分一覧に書く。仮のインスタンスは、必ず消す
- **位置とサイズ**: 置換のたびに、置換前の `x / y / width / height` を控え、置換後と比べる。「置換する」の部品は、差が0.5px以上なら直す。「置換する（差分あり）」の部品は、**サイズはDSに従う**（プロトタイプに合わせて引き伸ばさない）。ただし、周りの部品の位置が意図せず動いていないかを確認し、差分を記録する。親が自動レイアウトのときは、インスタンスを入れると配置の設定が変わることがある。その場合は親の `counterAxisAlignItems` などを元に戻す
- **レイヤー名**: 置換のあと、**画面全体のレイヤー名を [layer-naming-rules.md](../../../guidelines/rules/layer-naming-rules.md) に沿って付け直す**（最上位のフレームは F-01、それ以外は R-01〜R-10）。キャプチャ由来の名前（`Container` `Text` `Button - …` `h2d-svg-use-0` など）をそのまま残さない。手順・対応表・検証は [references/layer-naming.md](references/layer-naming.md) に従う。ルール違反の名前が0件になるまで直す
- **やらないこと**: DSに該当がない部品を、近いだけのコンポーネントで無理に置換しない。DS本体のコンポーネントや変数を変更しない。置換したインスタンスのサイズを、プロトタイプに合わせて上書きしない

## 工程4: 検証

1. 置換した部品ごとに、置換前後の `x / y / width / height` の差を表にする。「置換する」の部品は0.5px以上の差を残さない。「置換する（差分あり）」の部品は、差を記録して工程5の差分一覧に回す。置換前の値は、置換の呼び出しの中で控えておく（[references/figma-recipes.md](references/figma-recipes.md) の `swapIn` と `rec`）
2. **画面全体の位置を、プロトタイプと突き合わせる。** プロトタイプ側は、アプリ内ブラウザで同じ幅（`--width`）に開き、`javascript_tool` で主要な要素の `getBoundingClientRect()`（x・y・幅・高さ）を取る。Figma側は `get_metadata` で同じ要素の位置・サイズを取る。**差が0.5px以上の要素を一覧にする**（置換した部品に限らず、見出し・入れ物・文字の枠も含む）。置換でDSのサイズに従った部品の隣で起きた位置のずれも、ここで見つける
3. 取り込んだ画面全体のスクリーンショット（`get_screenshot`）を、プロトタイプの画面（同じ幅でのスクリーンショット）と見比べる。**アイコンの形・大きさ・色、サムネイル、文字の欠けを1つずつ確認する**
4. 置換件数を、種類別に数える（アイコン／チェック／ボタンなど）
5. レイヤー名の違反が0件であることを確かめる（[references/layer-naming.md](references/layer-naming.md) の「検証」）
6. 検証で直した点・直せなかった点を、報告に含める

## 工程5: 引き渡し（デザイナー向け）

次の4つをユーザーに渡す。

1. **置換済み**: 種類別の件数と、使ったコンポーネント名
2. **差分一覧（プロトタイプとDSのずれ）**: DS優先で置換した結果、プロトタイプと違いが出た部品。プロトタイプ側を直す材料になる

   | nodeId | 部品 | 使ったコンポーネント（variant） | 寸法（プロト → DS） | 見た目の違い | variantの選定理由 |
   |---|---|---|---|---|---|

3. **置換しなかった部品（要コンポーネント化）**: DSに該当がない部品

   | nodeId | 部品 | 理由 | 推奨名（`component-authoring-rules.md` に沿った案） |
   |---|---|---|---|

4. **キャプチャの既知の制限**で、手作業が要るもの

## 既知の制限（キャプチャ側。スキルでは直せない）

- サムネイルのSVG（`<use>`）が**黒い矩形**になることがある。画像として入れ直すか、手作業で直す
- 縦書きの文字（`writing-mode`）が**横書きでずれる**
- 公式の `generate_figma_design` はDSのコンポーネントに解決しない（Figmaフォーラムに同じ要望あり）

## 注意

- 一時サーバー・一時ファイルは、作業が終わったら停止・削除する。`generated/` に残さない
- 工程1の対応表は、置換の前にユーザーに見せる。DSに該当がない部品を、ユーザーの了承なしにコンポーネント化・変更しない（コンポーネント化はデザイナーが手動で行う）
