# デザインルール編集スキル

`guidelines/rules/` のルール文書を、**AI駆動デザインの目的に照らして点検し、人が決めた内容を正しい書式・正しい範囲で書き込む**スキル。

**誰が使っても同じ結果になること**を最優先にする。そのため、判断が分かれうる箇所は本スキルで手順と出力形式を固定している。手順を省略・入れ替えしない。

**ルールの中身（何がOKで何がNGか）は本スキルに書かない。** 毎回ルール文書そのものを読む。本スキルが持つのは、前提・品質基準・手順・出力形式だけ。

---

## 第1部　前提

### 1-1. AI駆動デザインとは

AIがデザインシステム（DS）を読み込み、そのDSの部品を使って、品質の高いプロトタイプを作る進め方。

AIはDSを**人のように「見て察する」ことができない。** 次のように、文字列と構造でしか扱えない。

| AIの動作 | AIが頼りにするもの | 崩れるとどうなるか |
|---|---|---|
| 部品を**特定**する | Component Set名・レイヤー名の文字列 | 1文字違えば別物。`state`と`status`は一致しない |
| 部品を**選ぶ** | 名前、Description（プレーンテキスト） | 似た部品を取り違える、非推奨を選ぶ |
| 部品を**操作**する | Variant軸名・値、Property名 | 存在しない値を指定する、軸の意味を取り違える |
| 部品を**組み立てる** | Description（用途・選び分け・Propertyの意味）、Variables | 誤った組み合わせ、DSにない値の創作 |
| 使ってはいけないものを**避ける** | `🚫`マーカー、`ver`軸 | 旧版・非推奨を使う |

**ルールの役割は、この5つの動作をAIが一意に・安定して行える状態をDSに作ること。** ルールの質がそのままプロトタイプの質になる。

### 1-2. DSを育てる循環

```
ルール（guidelines/rules/）
  → DSをルールに沿って整える（DSレビュー・修正：design-system-audit-skill / design-system-apply-fixes）
  → AIがDSを使ってプロトタイプを作る（prototype-draft）
  → AIが使ってみて揺れ・不足を発見し、推測で埋めずに報告する
  → 人が判断してルールを追加・修正する ← 本スキルが担う
```

**循環を回すのは人の判断。** AIが不足を推測で埋めると、この循環は止まる。本スキルも、ルールに定義がないことを勝手に決めない。

全体像の資料（必要なときに読む。チームで用意したものがあれば、`generated/docs/` や社内のWiki等にリンクを置く）:

- プロトタイプ生成の仕組み
- DSの測定・DSレビュー・修正の流れ
- 全タスクと進捗（タスク一覧。ルール整備・社内合意の項目を含む）

### 1-3. ルール文書の所在と役割

| ファイル | 担当 | 主な読み手 |
|---|---|---|
| `guidelines/rules/layer-naming-rules.md` | レイヤー名・トップフレーム名（R-xx、F-01） | デザイナー、DSレビューAI |
| `guidelines/rules/variant-naming-rules.md` | 軸名・値・Component Set名・Property名（V-xx） | デザイナー、DSレビューAI |
| `guidelines/rules/description-format.md` | Descriptionの記載形式 | デザイナー、起案AI、DSレビューAI |
| `guidelines/rules/component-authoring-rules.md` | Componentの作り方・版の扱い（CA-xx） | デザイナー、DSレビューAI（付録） |
| `guidelines/rules/variables-rules.md` | Variablesの適用・どのコレクションから選ぶか（VR-xx） | デザイナー、DSレビューAI、測定（Script B） |

IDの範囲は増減するため、本スキルには書かない。**作業のたびに見出しを確認する**（手順2）。各文書の冒頭にある「参照元」が、読み手の正本。

文書ごとに構成が少しずつ違う（例：`description-format.md` には更新履歴の節がない）。**構成を揃える変更は、それ自体を人に確認してから行う。**

- 5本が**ルールの唯一の正本**。スキル・DSレビュー・プロトタイプ生成は参照するだけで、再定義しない。
- ルールは **Claude Code／他のAIエージェント（Codex など）／Figma Agent の複数のAIが読む。** Claude固有のスキルを読まないと意味が通らない書き方をしない。
- **`guidelines/` はこのリポジトリの一部**（正本はリモートの `main`）。**ルールの変更は、このリポジトリで guidelines/ の変更をコミットする。** スキルや生成物など、ほかの変更と同じコミットに混ぜない。
- 実データ照合の詳細（日付・件数・DS名）は本文に書かず、ルール文書の外（社内のWiki等）に一本化する運用。

### 1-4. 現在のフェーズ

- **いまはルールづくりの段階。** DS本体（Figmaの本番・ブランチとも）には反映しない。Figmaへの書き込みは、人が明示したときに別スキルで行う。
- ルール文書は「ドラフト・レビュー待ち」で、組織の正式承認は未了（承認者も未決）。未決の論点は各文書の本文・更新履歴とタスク一覧にある。**本スキルに未決事項を書き写さない**（古くなるため）。

### 1-5. 守る姿勢（例外なし）

| 姿勢 | 内容 |
|---|---|
| **ルールを決めるのは人** | AIは案と根拠を出すまで。案の採否・ルールに定義がない事象の扱いは人が決める |
| **推測で埋めない** | 資料が見つからない、件数・定義が食い違う、解釈が2つ以上成り立つ → 編集前に質問する |
| **既存デザインへの影響は絶対に避ける** | DSは多数の画面ファイルから参照されている。ルール変更により、既存資産に値の変更・構造変更（Variant軸の追加・分離・削除）・基本値→Aliasの付け替えが必要になる案は、既定では出さない。必要に見える場合は「要判断」として人に返す |
| **`🚫`は意図的な非推奨** | V-08のマーカー。`ver`の値・Component Set名・単体Component名にある`🚫`を外す・削除する・統合する案を出さない。それ以外の位置の`🚫`はV-08違反として指摘してよいが、並存値の削除・統合は案に出さず「要判断」とする |
| **ルールが正本** | 実データの多数派や過去の慣習に合わせてルールを解釈・変更しない。実データはルールを見直す材料であり、ルールを決めるのは人 |
| **参照側は勝手に直さない** | ルールを参照するスキル・文書は、編集せず「変更提案」として報告する |

## 第2部　ルールの品質基準

ルールの点検・変更案の作成では、次の13項目を**すべて**確認する。いずれも1-1の「AIの5つの動作」から導いたもの。既存ルールの書き方（「AIが連番と判別できないため」など理由を添える、例外は許容語リストで閉じる、等）もこの基準に沿っている。

| # | 観点 | 満たす状態 | 満たさない例 |
|---|---|---|---|
| Q1 | **目的** | AIのどの動作（特定・選択・操作・組み立て・回避）のどんな誤りを防ぐかを1文で書ける。本文に理由が書かれている | 「見栄えが良いから」「統一感のため」だけが理由 |
| Q2 | **判定の一意性** | 誰が（どのAIが）判定しても同じ○×になる。文字列・列挙・正規表現・変換表で判定できる。数え方の単位（Component単位かSet単位か等）、日本語の表記（漢字／かな、全角／半角）も決まっている | 「適切に」「分かりやすく」「なるべく」「必要に応じて」、品詞や意味の判断が要る条件 |
| Q3 | **例外が閉じている** | 例外は列挙リストで示し、リストへの追加手順と判断者（人）が書かれている | 「〜など」で例外が開いている |
| Q4 | **直し方が決まる** | 違反の直し方が機械的変換の規則で1つに決まる。決まらない場合は「要判断」と明記されている | 直し方が複数ありうるのに、どれを選ぶか書いていない |
| Q5 | **人の判断の線引き** | 人が判断する部分は「要確認」「ユーザーが判断」と明記され、AIに委ねていない | AIが正本・訳語・共通軸への昇格を自己判断できる書き方 |
| Q6 | **既存資産への影響** | 新ルールで既存資産が違反になる場合、名前の変更だけで直せる。直せないもの（構造・値の変更）は対象外または段階的解消と明記。`🚫`付きは対象外 | 既存Instanceが変わる修正を前提にしている |
| Q7 | **整合** | 他のID・共通軸一覧・許容語リスト・機械的変換の規則・報告優先順位・適用範囲の表・付録の対応表と矛盾しない。同じ内容（リスト・例を含む）の正本は1か所で、二重管理になっていない | 2つの文書で同じリストを別々に持っている。見出しや適用範囲の表がIDの追加に追随していない |
| Q8 | **読み手** | デザイナーが作業しながら読める。守る状態を先に書き、❌/✅の例を1つずつ。AIによるDSレビュー専用の情報は付録 | 違反の診断口調だけで、何をすべきかが分からない |
| Q9 | **自己完結** | 他のAI（他のAIエージェント・Figma Agent）が本文だけで同じ判定ができる。実データの件数・日付は本文にない | 特定スキルの手順を読まないと判定できない |
| Q10 | **形式と意味の分担** | ルールは○×で判定できる「形式」だけを持つ。○×で書けない品質（命名の具体性・粒度など）は、ルールではなくDSレビュー基準（`design-system-audit-skill/references/`）側の扱いとして提案する | 「具体的な名前にする」を○×のルールとして書く |
| Q11 | **重なりの優先順位** | 1つの対象に複数のルールが当たる場合（例：Slotのレイヤー名にR-xxとV-xxの両方）、どちらが優先かが書かれている | 「同じ規則に従う」とだけ書かれ、例外の扱いが食い違う |
| Q12 | **境界例** | 判定が割れやすい境界のケース（例外の際、似た語、数字の扱い等）に例がある | ❌/✅が典型例だけで、迷うケースに例がない |
| Q13 | **時点に依存しない** | 本文は「今のルールでOKかNGか」だけを書く。決定日・改訂の経緯・以前のルール・レビュー状態・件数などの過去の情報は、更新履歴にだけ書く | 「（2026-10-14決定）」「旧regexから外した」「〇〇の改訂で許容に変更した」「要確認・レビュー待ち」「（84件）」、一覧の「追加日」列 |

**判定の付け方**: 各項目を `OK／NG／要確認／該当なし` で判定し、根拠（該当箇所の引用か、行番号）を必ず添える。

- 根拠のない `OK` を付けない
- 確認できなかった項目は `要確認` とし、`OK` にしない
- `該当なし` は、その変更・ルールの性質上その観点が当てはまらないときだけ使い、理由を書く（例：リストに語を1つ足すだけなのでQ8は該当なし）

## 第3部　手順

依頼を次のどちらかに分類する。両方を含む場合は、点検を先に行う。

- **A. 点検**：ルール案・既存ルールが品質基準を満たすか、ルール同士が矛盾しないかを確認する。**ファイルは編集しない**
- **B. 編集**：人が決めた内容をルール文書に書き込む

### 作業環境の前提

- 作業ディレクトリはリポジトリのルート。以下のコマンドはこの前提で書いている
- ファイル内容の検索は Grep ツールを優先する。シェルで行う場合は Git Bash で実行する（PowerShell には `grep` がない）
- 対象のURLがこのリポジトリの `guidelines/`（`.../blob/main/guidelines/...`）を指すなら、ローカルの `guidelines/` の同じパスとして扱う

### 手順1　依頼を確定する

依頼の種類（点検／編集）を決め、**読み取り（手順2・3）を先に済ませてから**、次の項目のうち不明なものを**まとめて1回**質問する。読み取り以外の作業（編集・コミット）は、回答が揃うまで行わない。

| 項目 | 確認する内容 |
|---|---|
| 種類 | 点検か編集か。編集なら、追記・修正・新設・廃止・整理のどれか |
| 決定の有無 | 人が決めた内容か、AIに案を求めているか。**案を求めている場合は手順4の変更案を出して止まる**（編集しない） |
| 決定の根拠 | どのレビュー・合意で決まったか（更新履歴に書くため） |
| 対象範囲 | どの文書・どのIDか。新設なら、どの文書に置くか |

決定内容が既存ルールと矛盾する、またはどう書くか解釈が2つ以上ある場合も、決め打ちせず質問する。

### 手順2　最新化して読む

1. `guidelines/` の状態を確認する。
   ```bash
   git status -sb -- guidelines/
   git fetch
   ```
   - `fetch` はリモートの参照を更新するだけで作業ツリーを変えないため、点検でも実行してよい
   - **点検（A）の場合**：`pull` しない。ローカルが `origin/main` と違えば、`git show origin/main:guidelines/rules/<対象>.md` で main の内容を読み、ローカルとの差を報告に書く。未コミットの変更があっても点検は続け、その旨を報告に書く
   - **編集（B）の場合**：未コミットの変更があれば、触らずに人へ報告して指示を待つ（他の人の作業中かもしれない）。`origin/main` より遅れていれば `git pull --ff-only` で最新化する。fast-forwardできなければ止めて報告する
2. 対象文書の**見出し一覧**を取り、IDの範囲と構成を確認する（枝番IDは `####` 見出しにあるため4階層まで取る）。
   ```bash
   grep -nE '^#{1,4} ' guidelines/rules/<対象>.md
   ```
3. 対象文書の**冒頭（目的・参照元・関連ルール）、該当節の全文、更新履歴の全文**を読む。新設・整理・文書全体の点検の場合は文書全体を読む。
4. 同じ論点の過去の決定を確認する。**更新履歴の表を全行読む**ことを基本とし、該当IDの変更理由が履歴で分からない場合だけ差分を見る。
   ```bash
   git log --oneline -- guidelines/rules/<対象>.md
   git log -p -S "<ID>" -- guidelines/rules/<対象>.md
   ```

記憶や本スキルの要約で判定しない。

### 手順3　波及を洗い出す

**検索するキーワード**は、次の3種類を必ずすべて使う（人によって検索語が変わらないようにするため）。

1. 変更する**ID**と、その親ID（例：`V-07-4` と `V-07`）
2. 追加・変更・削除する**文字列そのもの**（語、軸名、値、正規表現の一部）
3. その規定が属する**リスト・概念の名前**（例：`許容語`、`共通軸`、`機械的変換`、`報告の優先順位`）

**検索範囲**は次のすべて。省略しない。

```bash
grep -rn "<キーワード>" guidelines/ .claude/skills/ .claude/PROTOTYPE.md .claude/CLAUDE.md generated/docs/ --include=*.md
```

他のAIエージェント用の指示ファイルやスキル（例：`AGENTS.md`、`.agents/skills/`）や、Figma Agent 用のスキル置き場があるリポジトリでは、それらも検索範囲に加える。ルールはそれらのAIも読むため、あれば必ず含める。

文書全体の点検（A）では、文書が持つ全IDのうち、他ファイルから参照されているもの（冒頭の「参照元」に書かれたスキル、付録の対応表）を対象に検索する。

ヒットしたものを次の2つに分ける。

| 区分 | 対象 | 扱い |
|---|---|---|
| **同時に直すもの** | `guidelines/rules/` の5本（同じ文書内の他の節、連動する他文書のID・例・一覧・変換規則・報告優先順位・付録・冒頭の参照元） | 同じ変更で整合させる |
| **変更提案にするもの** | 上記以外のすべて：`.claude/skills/`・他のAIエージェント用のスキル（DSレビュー基準・測定スクリプトの正規表現など。両方にある場合は両方を挙げる）、他のAIエージェント用の指示ファイル、Figma Agent 用のスキル、`guidelines/` の rules 以外（`README.md`・`design-system-map.md`・`kit/`・`<service>/` 等）、`generated/docs/` | 編集しない。手順9で一覧にして報告する |

特に、**測定・DSレビュースクリプトの正規表現や判定条件**がルールと一致しているかは、測定値の再現性に直結するため必ず確認する。

### 手順4　点検する／変更案を作る

- **点検（A）**：対象のルール（または案）を第2部の Q1〜Q13 で判定し、**出力形式1**で報告して終わる。文書全体の点検では、IDごと（R-01、R-02…）に判定し、文書全体に関わる観点（Q7・Q9など）は最後にまとめて判定する
- **編集（B）**：変更案を作り、第2部の Q1〜Q13 で自己点検したうえで、**出力形式2**で提示し、承認を待つ

承認を省略してよいのは、**判定結果（何がOKで何がNGか）が変わらない修正だけ**：誤字、リンク切れ、表記の体裁、見出し番号のずれ、本文の時点情報を更新履歴へ移すこと（Q13）。迷ったら承認を取る。

品質基準で `NG` が出た場合は、決定内容を勝手に書き換えない。`NG` の理由と直し方の案を示し、人に判断を求める。

### 手順5　編集する

承認された内容だけを書き込む。

- **既存の書式に合わせる**：守る状態を先に書く（「〜にする」）。❌/✅の例は既存の項目と同じ粒度で1行ずつ。理由（AIの何を防ぐか）を添える
- **IDを振り直さない**（他文書・スキルが参照している）。新設は次の番号、細則は枝番（例：`V-04-3`）。廃止は欠番にし、理由を本文に残す
- **正本は1か所**。連動する他文書には要点と「〜参照」のリンクを書き、本文を複製しない
- **連動する他文書も同じ変更で整合させる**（見出し・例・一覧・付録・報告優先順位）
- **本文には今のルールだけを書く（Q13）。** 決定日（`（YYYY-MM-DD決定）`）、改訂の経緯（「旧〜」「〜に変更した」）、レビュー状態、実データの件数・DS名は本文に書かず、更新履歴に書く。既存の本文にこれらを見つけたら、変更箇所の近くであっても勝手に消さず、点検の指摘として報告する
- 変更しない部分の文言を、ついでに直さない

### 手順6　更新履歴を書く

変更した各文書の末尾の更新履歴の表に**1行追加**する。既存の行は消さない・書き換えない。更新履歴の節がない文書（現時点では `description-format.md`）は、節を新設してよいかを手順4の変更案で人に確認する。

- 日付：当日（`YYYY-MM-DD`）
- 書き出し：**太字で、何を決めたか**（例：`**R-10（単独Image）を新設。**`）
- 続けて：変更の要点と理由。決定の根拠（どのレビュー・合意か）
- 判定基準が変わらない整理なら「判定基準は変更なし」と書く
- ドラフト扱いなら「ドラフト案・レビュー待ち」と書く
- 連動した文書には「〇〇.md の X-XX と連動」と書く

### 手順7　検証する

次をすべて確認し、結果を出力形式3に書く。

- [ ] `git diff -- guidelines/` で、承認した箇所だけが変わっている
- [ ] 追加・変更したIDが、冒頭・一覧・付録・報告優先順位・他文書の参照と食い違っていない
- [ ] 文書内リンク（`[...](....md)`）の先が存在する
- [ ] 変更後の本文を Q1〜Q13 でもう一度確認した

### 手順8　コミット・プッシュ（依頼があったときだけ）

- **コミットもプッシュも、人の依頼があったときだけ行う。** 依頼がなければ、出力形式3で報告して終わる
- コミットはこのリポジトリで行い、guidelines/ の変更をコミットする。対象は今回の変更ファイルだけ（`git add guidelines/rules/<ファイル>`。`add -A` を使わない）。ほかの変更と同じコミットに混ぜない
- メッセージは既存の履歴に合わせた英語の1行（例：`Add R-10 for standalone Image`、`Clarify that ...`）。1コミット＝1論点
- **プッシュは毎回確認を取る。** `main` へ直接プッシュするか、ブランチ＋PRにするかも確認する（過去の許可を次回に流用しない）

### 手順9　報告する

出力形式3で報告する。

## このスキルでやらないこと

- ルールの内容を人に代わって決める（案と根拠の提示まで）
- Figmaの変更（リネーム・構造変更）。実行は `design-system-apply-fixes` など
- DSレビュー・実測（`design-system-audit-skill`／`design-system-measure`）
- 参照側スキル・文書の書き換え（変更提案まで）
- 未決事項・ルールの中身を本スキルへ書き写す

## 関連スキル

- `component-authoring-advisor`：Componentの作り方の相談（ルールを読んで答える側）。本スキルはルールを書く側
- `design-system-audit-skill`：ルールに照らしたDSの評価。○×で書けない品質観点（Q10）はこちらの基準が持つ
