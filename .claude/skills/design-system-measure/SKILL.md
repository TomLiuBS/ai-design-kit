# Design System 実測（AI-ready構築期間の一時評価）

DSの**数値指標だけ**を、毎回同じ条件で測る。**判定も評価も修正リストも作らない。** Figmaも変更しない。

## 位置づけ：一時的な評価である

このスキルは、**AI-readyなデザインシステムをつくる期間のための、一時的な評価**として作っている。

- 目的は、DSの整備（命名・Description・Variant整理）の前後を、同じ物差しで比べること。複数人で検証するため、**実行者が変わっても同じ値が出る**ことを優先する。
- 恒常的な品質保証やKPIとして設計していない。AI-ready化の整備が一段落し、運用が安定したら、このスキルを残すか、`design-system-audit-skill` に統合するか、廃止するかを人が決める。
- 閾値（Tier1→2の暫定値など）との合否比較は、このスキルでは行わない。値を出して、閾値との比較は人が行う。
- 結果を報告するときは、冒頭に「AI-ready構築期間の一時評価」であることを書く。

## やること／やらないこと

| やる | やらない |
|---|---|
| 固定した走査範囲での実測（Script A〜E）と、分母・分子つきの集計 | 良い・悪いの判定、得点化、改善提案、修正リストの作成（→ `design-system-audit-skill`） |
| 固定フォーマットでの報告と、測定条件の記録 | Figmaの変更（→ `design-system-apply-fixes`） |
| 「要確認」（日本語の業務固有語など）の件数と内訳の記録 | 正本の一意性・H3構築テストの評価（判定が入るため、DSレビュースキルの担当） |
| 同じ測定を再実行して値が再現するかの確認 | スクリプトの書き換え、手で数えた値の混入、サンプル抽出による推定 |

## 測れる指標

| 指標 | 内容 | スクリプト | DSレビュースキル上のID |
|---|---|---|---|
| Component化率 | INSTANCE ÷（INSTANCE + FRAME + GROUP） | Script A | A1 |
| レイヤー名の違反候補率 | 形式違反のレイヤー ÷ 評価対象レイヤー | Script A | C4 |
| Auto Layout適用率 | Auto Layout適用FRAME ÷ 全FRAME | Script A | D1 |
| Variables適用率 | 余白・Gap・色・文字ごとに、適用済み ÷（適用済み＋[variables-rules.md](../../../guidelines/rules/variables-rules.md) VR-02 の違反）。従来の塗り・テキスト適用率も併記 | Script B | E6 |
| Description記載率 | Descriptionが空でないComponent Set・単体Component ÷ 評価対象 | Script C | F1 |
| Variant違反候補率 | 違反候補を含むComponent ÷ 評価対象Component（軸名・値・Property名・Component Set名の内訳つき） | Script D | A5・B1・B2・C1 |
| Property・組合せ・変数の参照先 | Property が付いていない TEXT・INSTANCE ÷ 先頭バリアント直下の TEXT・INSTANCE／欠けた組合せ ÷ 軸の値の掛け合わせ／値を直接持つ変数の直接参照・Alias の階層 | Script E | A4・B5・E2・E1 |

「違反候補」は、スクリプトが機械的に拾った候補。最終判定ではない。最終判定が必要なときは、`design-system-audit-skill` がルール（`guidelines/rules/`）に照らして行う。

## 前提

- **`use_figma` を呼ぶ前に必ず figma-use を読み込む。** `use_figma` の引数に `skillNames: "design-system-audit"` を含める。
- Figma Desktopアプリが起動し、対象ファイルが開かれていること。figmaRemoteMcpが接続されていること。
- `use_figma` が使えない場合は、**値を推測せず**「未測定」と報告して止まる。直し方（`/mcp` で figmaRemoteMcp に Figma でサインインする）は、design-system-audit-skill の SKILL.md「C-4 で止まったときの直し方」をユーザーに伝える。

## 手順

### 1. 測定条件を確認する（実行前に必ず）

次を確認して、報告に記録する。**指定がなければ質問する。推測で決めない。**

| 項目 | 確認内容 |
|---|---|
| 対象DS | 共通DS／アプリ固有DS（アプリ名）。アプリ固有DSは、共通DSをInstance参照しているか複製しているかも確認する |
| 測定の起点 | [所在マップ](../../../guidelines/design-system-map.md)のnode-id（コロン区切り）。所在マップにない、または画面同居のページを指す場合は、その事実を報告し、DS本体セクションのnode-idに読み替える（読み替えを記録する） |
| 本体かブランチか | どちらを測るか。ブランチなら、ブランチ名も記録する |
| 測定の目的 | ベースライン（Before）か、修正後（After）か、再現性の確認か |
| 比較する前回値 | After測定なら前回の測定結果（分母つき）を受け取る |

### 2. 起点がDS本体であることを確認する

- Component Setが集中する領域を測定ルートにする。画面レイアウト・利用例・画面モックの領域は除外し、除外した領域を記録する。
- Script Aの診断（COMPONENT／COMPONENT_SET の内部／外部の比率）で、外部が支配的なら、起点が画面領域に及んでいる疑いがあるので、起点を見直す。

### 3. 走査する（スクリプトは書き換えない）

- **走査の前に、ルール（`guidelines/`）と本スキルをリモートの main の最新にそろえる。** 手順は design-system-audit-skill の SKILL.md「開始前チェック」の C-2・C-3 と同じ（`--ff-only` で自動で取り込み、手元の変更は消さない。取り込みに失敗したら停止。本スキルが更新されたら読み直してから進む）。
- **走査の前に、[measure-scripts.md](scripts/measure-scripts.md) の「ルールと照合する定数」の表に従い、スクリプトの定数（`SIZE_OK`・`STATE_OK` など）と `guidelines/rules/` の値を見比べる。** 食い違えば測定せずに停止し、食い違いをユーザーに伝える（手元で書き換えて測らない）。

- 走査範囲は固定: 起点配下を全階層／COMPONENT・COMPONENT_SET内部は走査する／INSTANCE内部は走査しない／非表示レイヤーは走査する。
- **起点直下の子が多い場合は、一括で走査しない。** まず件数だけを数える軽量走査で、Component Setが集中する領域を特定し、領域ごとに測る。
- スクリプトは [scripts/measure-scripts.md](scripts/measure-scripts.md) の Script A〜E を**そのまま**使う。`NODE_ID` だけを差し替える。
- **生データを返さない。** スクリプトが返す集計（件数・頻度・上限つきサンプル）だけを使う。
- エラー時は、即リトライせず、メッセージを読んで原因を確認する。タイムアウトで起点を絞った場合は、走査範囲が変わったことを記録し、前回値と比較しない。

### 4. 集計する

- **率は、分子と分母を足してから割る。** 領域ごとに測った場合、領域ごとの率を平均しない（例: 領域1が 10/40、領域2が 5/10 なら、全体は 15/50 = 30.0%）。
- 同名のComponent Setの重複（Script Dの `duplicateNames`）は、領域をまたぐと数え漏れが出る。領域ごとの `componentSetNames` を突き合わせて数え直す。
- 率は小数第1位まで（四捨五入）。分母・分子は必ず整数で併記する。
- `review`（日本語の業務固有語・要確認）は、違反に数えない。件数と内訳を別に記録する。

報告は次の形に**統一する**。実行者によって書き方を変えない。

## ぶれを防ぐ規則

| 規則 | 理由 |
|---|---|
| スクリプトを書き換えない。変えたいときはスキル（measure-scripts.md）を更新する | 実行者ごとに数え方が変わるため |
| 測定条件（起点・本体／ブランチ・走査範囲）を必ず記録する | 後で同じ条件で再現できるようにするため |
| 分母が前回と変わったら、値を比較しない。理由（走査範囲の変更など）を記録する | 範囲が違う値は比べられないため |
| 手で数えた値・サンプルからの推定値を混ぜない | 再現できないため |
| 判定・得点化をしない | 判定はルールに照らして `design-system-audit-skill` が行うため |
| 前回値と比べるときは、同じ起点・同じ範囲であることを確認する | Before/Afterの比較が成り立つため |

## 再現性の確認（立ち上げ時・実行者が変わるとき）

複数人で使い始めるときに一度、次を行う。

1. 2人が、同じ対象・同じ起点・同じ時点（本体は変更しない）で、それぞれ測定する。
2. 分子・分母がすべて一致するかを確認する。
3. 一致しなければ、測定条件（起点・分割の仕方・除外）を突き合わせ、原因を特定して、このスキルの手順に反映する。

## 関連スキルとの関係

| スキル | 関係 |
|---|---|
| design-system-audit-skill | 実測が必要な項目では、本スキルの結果を証拠として引用する。判定・評価・修正リストはDSレビュースキルが行う |
| design-system-apply-fixes | 修正後の軽量確認で、本スキルのスクリプトを、変更対象だけに絞って使う |
| figma-ai-review | 画面ファイルの構造品質を見るスキル。本スキルは画面ファイルを対象にしない |

## 今は測れない指標

- **アプリ間のUIコンポーネント・パターンの共通化率**: 定義が未確定（画面ファイルのInstanceのうち共通DS由来の割合にするのか、アプリDSのうち共通DSを複製している割合にするのか）。定義が決まれば、スクリプトの追加で測れる見込み。
- **UI操作起因の問い合わせ・ヘルプデスク件数**: Figmaからは取得できない。外部データが必要。
