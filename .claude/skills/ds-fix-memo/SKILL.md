# DS内容の修正メモ スキル

`generated/docs/ds-content-fix-memo.md` に、**ルールには合っているが、内容や意味が実態とずれているもの**を貯めるスキル。貯めるだけで、Figma やコードの修正は行わない。

**誰が使っても同じ結果になること**を最優先にする。基準と書式は、このスキルとメモ冒頭で固定している。

## 大原則

- **ユーザーが「メモに追加して」と言ったときだけ追加する。** 作業中に見つけても、勝手に足さない。
- **1項目ずつ、基準に合うか確かめてから追加する。** まとめて流し込まない。
- 基準に合わないものは断り、行き先を案内する。
- 推測で埋めない。分からない列は「要確認」に書く（空欄にしない）。

## 手順

### 1. 追加（「メモに追加して」）

1. メモ `generated/docs/ds-content-fix-memo.md` を読む（冒頭の基準・書き方、既存のIDを確認）。
2. 項目ごとに、次の3つを確かめる。**1つでも欠けたら追加しない。**
   - ルールには違反していない（`guidelines/rules/` の該当ルールを読んで確認する。違反なら「DSレビューの修正リスト」へ）。
   - 内容や意味が実態とずれている。
   - 根拠を示せる（Figma のノード、値、実際の使われ方）。根拠がなければ、ユーザーに聞く。
   - **例外（FigmaのDSに無く、CSSへ暫定追加した部品）**は、上の3つに代えて次を確かめる: ①FigmaのDS（共通DS・対象サービスの固有DS）に無いこと ②CSSの暫定区画の場所（ファイルと見出し） ③元にしたFigmaのノード。「現状」に「Figma未定義・CSSに暫定追加」、「修正案」に「FigmaのDSに登録 → CSSをFigmaに合わせて直し、暫定の注記を外す」と書く
3. 行き先が別のものは、追加せずに案内する。

   | 内容 | 行き先 |
   |---|---|
   | ルール違反 | DSレビュー（design-system-audit）の修正リスト |
   | ルールが未定 | ルールの未決一覧 |
   | そのプロトタイプだけの仮・要確認（CSSに暫定追加した部品は除く） | そのプロトタイプの `NOTES.md` |
   | 好みや感想 | 入れない |

4. 重複を確かめる（同じ対象・同じ内容の行がすでにないか）。あれば、追加せずに既存のIDを示す。
5. 影響範囲を、リポジトリで検索して書く（検索した語と、見つかったファイルを示す）。Figma 側の使用数など、調べられなかったものは「未集計」と書く。
6. **追加する前に、行の案をチャットで見せ、承認を得る。**（列ごとに、何を書くかを示す）
7. 承認後、表の末尾に追記する。IDは最大のIDの次（`FX-nnn`）。状態は「未着手」。要確認があれば「確認中」。
8. 追加した行のIDと、要約を1行ずつ報告する。

### 2. 更新（状態の変更・内容の追記）

- 行は消さない。状態を「修正済み」「見送り」などに変え、「見つけた経緯」の列に日付と理由を足す。
- 要確認が解消したら、その内容を「修正案」に反映し、「要確認」から外す。

### 3. 一覧

- 状態ごと（未着手・確認中・修正済み・見送り）に、ID・対象・修正案を表にして見せる。
- 「要確認」が残っている行を先に示す。

## 書式（メモの列）

ID／状態／対象／現状／修正案／影響範囲／要確認／見つけた経緯（日付）

- 対象には、Figma のノード・変数名・ファイルなど、場所が分かるものを書く（URL があればリンクにする）。
- 日付は絶対日付（例：2026-11-11）。
- 表記は日本語。

## やらないこと

- Figma の変数名やコードの変更（修正は別の作業。検証用ブランチで行う）。
- ルールの追加や変更（`design-rules-editor` の担当）。
- 基準に合わないものの追加。
- ユーザーの承認なしの追記。
