# Component作成・更新 相談スキル

Figma Componentの作成・更新にあたり、[component-authoring-rules.md](../../../guidelines/rules/component-authoring-rules.md)（CA-00〜CA-10）と、関連する[variant-naming-rules.md](../../../guidelines/rules/variant-naming-rules.md)・[layer-naming-rules.md](../../../guidelines/rules/layer-naming-rules.md)に基づいて相談に乗り、ルールに沿った提案を行う。

**本スキルは相談専用。** Figmaへの書き込み（Componentの作成・リネーム・構造変更の実行）は行わない。実行が必要な場合は、対象に応じた別スキル（`figma-use`、`design-system-apply-fixes`等）に委ねる。

---

## 絶対原則

- **判定基準は本スキルに書かない。** 毎回、上記3ファイルを読み込んでから回答する。記憶やこのファイルの要約で判定しない
- ルールに書かれていない基準を、本スキルで補わない。ルールに定義がない事象を見つけた場合は「ルールに定義がない」として報告し、ルール文書への追記が必要かどうかをユーザーに確認する
- **ルールが「要確認」「ユーザーが判断する」としている項目は、AIが代わりに決めない。** 推測で答えを埋めず、必要な情報が不明な場合は質問する

---

## 相談内容別フロー

相談内容を次のいずれかに分類し、対応するCA項目を踏まえて回答する。複数にまたがる相談はそれぞれの該当箇所を順に扱う。

### 1. これはComponent化すべきか

**CA-00**に従う。

- 「複数の画面・場所で再利用されるか」「AIがプロトタイプ生成時に参照する可能性があるか」を確認する。本プロジェクトは最新デザインを極力デザインシステム側に置く方針（CA-00）を取っているため、再利用の有無だけで機械的に判断しない
- 判断材料が不明な場合は、再利用の見込み・AI参照の見込みをユーザーに確認する

### 2. 新しくComponentを作りたい（作成方針の相談）

Component化すべきと判断された場合、次を踏まえて作成方針を提案する。

| 観点 | 参照ルール |
|---|---|
| バージョンを名前・値に入れない | CA-01 |
| サイズ・状態・種別はVariant軸で表す | CA-02 |
| 同じ役割の重複がないか | CA-03（可能であれば既存Componentの検索を促す） |
| 軸名・値・Property名・レイヤー名の形式 | CA-04、variant-naming-rules.md、layer-naming-rules.md |
| Descriptionを書く | CA-05 |
| 正式版・試験版・非推奨の明示 | CA-06 |
| 軸の意味の取り違え防止 | CA-07 |
| Variables（余白は必須） | CA-08、[variables-rules.md](../../../guidelines/rules/variables-rules.md) |

### 3. 既存Componentの構造を変えたい（軸の追加・分離など）

CA-04付録「軸の追加・分離は既存Instanceが新軸の既定値になる」を踏まえ、影響範囲を確認してから提案する。機械的に進めず、既存Instanceへの影響を必ず一言添える。

### 4. 新しいver・Slotの中身を更新したい（過去のデザインをどう扱うか）

**CA-10**に従う。判断フローには複数の分岐軸があるため、**次の情報が揃っていなければ先に質問する**（推測で進めない）。

- Componentがライブラリ経由（別ファイルの公開ライブラリ）か、ローカルか
- 更新頻度は高いか、低い（一度きり）か
- 過去のデザインを永久凍結したいのか、段階的に移行したいのか

揃った情報をもとに、CA-10の判断フロー（①ライブラリ更新の保留／②インスタンスのデタッチ／③Component複製／④ライブラリ化）のどれに該当するかを提案し、各方法のメリット・デメリット（Component数の増減、可逆性、前提条件）を併記する。

Component化していない一回限りの画面についての相談（作業用ファイルと納品用ファイルの扱い）も、CA-10の該当節に従って回答する。

### 5. 複数版が共存している。どちらが正本か

**CA-01（段階3）・CA-10**に従い、**AIはどちらが正本かを自己判断しない。**

- 可能であれば利用状況（Library Analyticsのインスタンス数等。Figmaファイルが指定されていれば`figma-use`経由での確認を提案してよいが、本スキル自身では書き込み・分析の実行はしない）を証拠として整理する
- 最終判断は必ずユーザーに委ね、「こちらが正本です」と断定しない

---

## ルール文書が見つからない場合

推測で回答を始めない。ルール文書の所在をユーザーに確認し、見つからない場合は「ルールが参照できないため提案できない」と報告する。

## ルールと実例が食い違った場合

ルール文書が正本である。実装側の多数派や過去の慣習に合わせて解釈しない。

## 実行前チェックリスト

- [ ] `component-authoring-rules.md`・`variant-naming-rules.md`・`layer-naming-rules.md`（Variablesの相談では`variables-rules.md`も）を今回読み直したか（記憶で判定していないか）
- [ ] 相談内容をどのシナリオ（1〜5）に分類したか特定したか
- [ ] CA-10など判断フローが必要な項目で、分岐に必要な情報が不明な場合、推測せずユーザーに質問したか
- [ ] 複数版の正本判定など「要確認」項目を、AIが代わりに断定していないか
- [ ] 回答にルールID（CA-XX・V-XX・R-XX）を明記したか
- [ ] Figmaへの書き込み（作成・リネーム・構造変更）を提案の範囲外とし、実行は別スキルに委ねる旨を伝えたか
