# Design System 修正実行

`design-system-audit-skill` が出した**修正リストの、指定された番号だけ**を実際にFigmaへ反映する。**DSレビューは行わない。判定も行わない。** 指定された修正を、指定された範囲だけ実行する。

Figma Agent版の修正実行スキル（試作）の原則を引き継ぎ、Claude Code（`use_figma`）向けに再設計したもの。両者の役割分担は未定のため、本スキルは独立して動作する。

## 絶対原則

### 2段階の承認を必ず経る

```
番号の指定 → ① 全件を提示 → ② 承認（＋要決定の確定を同時に受領可） → ③ 実行 → ④ 報告
```

- **①で提示しただけで実行しない。** 明示的な承認を待って止まる。
- 「直して」の一言で①と③を続けて行わない。**必ず一度止まる。**
- 承認が「#8だけ」なら**#8だけ実行する。** ついでに他を直さない。

### 範囲が確定しない指示では着手しない

- 「全部直して」「よしなに」では動かない。対象の番号を列挙して選んでもらう。
- **段階をまたいで同時に実行しない**（Variant値とProperty名を同時に変えない）。原因の切り分けができなくなる。

### 実行できないものの扱い（修正リストの「実行」欄）

| 実行欄 | 動き |
|---|---|
| **可** | ①〜④を実行する |
| **要決定** | **①の提示時に決定案（選択肢）を添えて出す。** ②の承認と同時に決定を受け取ってよい（決定内容自体を勝手に選ばない。案を出すのはよいが確定は人の返信を待つ） |
| **要起案** | ①〜②で完結させない。Description等の**内容起案**は決定と性質が違う（文章を作る作業）ため、起案→提示→承認の別ステップを経てから「可」として扱う |

### 構造変更は本スキルの対象外

**段階6（Variantの構造を変える）は実行しない。** 軸の追加・分離・削除、Variantの増減、Component Setへの統合は既存Instanceの選択値が失われるため扱わない。指示された場合は次を伝えて止まる。

- 既存Instanceへの影響を先に調査する必要があること
- 段階的な移行計画が必要であること（新軸を追加 → 移行 → 旧値を削除）
- 検証用ブランチで確認してから本体へ反映する判断が人に必要であること

### CA-09（マスターのみ編集。Instanceは編集しない）

編集対象は常に**マスターComponent／Component Set**。配置されたInstanceは編集しない（`component-authoring-rules.md` CA-09）。Instance内部はFigma Plugin API上リネーム不可であり、そもそも対象にならない。

### そのほか継承する原則

- **既存のDescriptionがある場合は上書きしない。** 既存内容を活かして統合し、変更点を報告する。
- **日本語の訳語を確認なしに確定しない。** 訳案を提示し、承認を求める。
- 変更後の名前を決めるとき、区切りのない箇所を勝手に単語分割しない（`layer-naming-rules.md` 第4節の機械的変換の規則に従う）。

## 責務境界

| 観点 | 担当 |
|---|---|
| 何を直すべきかの判定・優先順位・ルールIDの特定 | `design-system-audit-skill`（本スキルの対象外） |
| 承認された修正の実際の書き込み | 本スキル |
| Description の内容起案 | Figma Agent版の Description 起案スキル相当（起案スキル。未移植の場合は本スキル内で最小限起案し、要確認として明示） |
| 修正後の正式な再レビュー・Issueステータス確定 | `design-system-audit-skill` の再レビュー手順 |

本スキルが行うのは「実行が意図通り反映されたかの即時確認」（後述の軽量再測定）までであり、正式な合否判定はしない。

## 前提条件

- Figma Desktopアプリが起動し、対象ファイル（既定は検証用ブランチ）が開かれていること。
- figmaRemoteMcp（Remote MCP）が接続されていること。
- **`use_figma` を呼ぶ前に必ず figma-use を読み込む。**
- **`design-system-audit-skill` のレポート（修正リスト）が存在し、実行する番号／Issue IDが指定されていること。** 指定がなければ着手しない。

## 実行対象の既定 — 検証用ブランチ

- **既定は検証用ブランチに対して実行する。本体への反映（マージ）は本スキルの対象外とし、人が判断する。**
- Scope確認時に「対象は検証用ブランチか、本体か」を必ず確認する。指定がなければブランチを使うことを前提に、ブランチキーの提供を求める。
- **技術的制約**: Figma Plugin APIには「ブランチを新規作成する」操作がない（Figma UI操作のみ）。ブランチが未作成なら、人にUI上での作成を依頼して**停止する**（自動生成しない・本体を代わりに使わない）。
- ブランチ実行時は [design-system-map.md](../../../guidelines/design-system-map.md) の規則どおり、**ブランチキーを `fileKey` として使う**。
- **ライブラリの公開（本体への反映を利用側に届ける操作）はFigma Plugin APIで実行不可。** ブランチから本体へのマージ、および本体ライブラリの再公開は必ず人が行う。報告で必ず伝える。

## 運用ルール（トークン効率）

`design-system-audit-skill` と平仄を合わせる。**新しいカスタムサブエージェントは作らない。**

- **集計してから返す。** `use_figma` の実行結果（変更前後の値、mutated node ID）はそのまま生データで持ち帰らず、対象一覧の形に整えて返す。
- **ルール・レポートは1回だけ読む。** カテゴリ・段階ごとに読み直さない。
- **大量修正はバッチに分割する。** 1回の `use_figma` で全件を処理しようとせず、小さいバッチに分けて実行し、都度 mutated node ID を `return` する（figma-use の絶対原則）。
- **難所は上位モデルへ一時エスカレーション可。** 日本語訳語の候補案作成など判断の質が要る作業は、`Agent` ツールの `model` パラメータで一時的に `opus` を使ってよい。**ただし確定は人の承認を経る**（エスカレーションは案を作る作業のみに適用し、承認プロセスを省略しない）。

## 進め方

### 0. Scope

- 対象アプリ／DS、対象ブランチ（キー）、実行する番号／Issue ID、参照するDSレビューレポートを確認して記録する。
- 対象ブランチの存在を確認する。未作成なら人にUI上での作成を依頼して停止する。
- 修正リストの各対象について「実行」欄（可／要決定／要起案）を確認する。

### 1. 全件を提示する

指定された番号の対象を、**変更前 → 変更後**の形で全件示す。要決定の項目は決定案（選択肢）を添える。

```
#8 は8件です。以下の内容で修正します（対象ブランチ: <ブランチキー>）。

対象: systemDialog/confirm [<nodeId>]

1. desscription        → description
2. Show important_icon → showImportantIcon
...
8. main action         → mainAction

以上 8件

この内容でよろしいですか？
```

**守ること**

- レポートで「ほかN件」と省略されていても、ここでは省略しない。全件を出す。
- リストが途中で切れてはならない。切れそうな場合は分割して提示し、すべて出しきる。
- 連番を振り、末尾に `以上 N件` を書く。Nは最終番号と一致させる。
- 提示件数がレポートの件数と違う場合は、その差を説明する（対象が増減している可能性がある）。

**変更後の名前の決め方**

`layer-naming-rules.md` 第4節「機械的変換の規則」に従う。元の区切り（`_` `-` スペース）でのみ単語を分け、元の綴りは変えない（綴り誤りの修正は別途、同時に行ってよい）。素材名・CSSユーティリティ風名・デフォルト名にはこの規則を適用せず、役割名への置き換えが必要なため「要決定」として提示する。

### 2. 承認を待つ

**ここで必ず停止する。** 自分から進まない。承認の範囲が曖昧な場合（「だいたいOK」等）は、どの番号を実行するかを確認してから進む。要決定の項目は、この返信で決定が来ればそのまま③へ進んでよい。決定が来なければ、その項目だけ保留し、残りを先に進めるか確認する。

### 3. 実行する

#### 3-0. 実行直前の現在値確認（他者の同時変更の検知）

承認から実行までの間に、他のデザイナーが同じ対象を変更している可能性がある。**書き込み直前に、承認済みの対象ノードだけを読み、現在値が提示時の「変更前」と一致するか確認する。** DS全体は読まない（トークン消費を避けるため）。

- 読む範囲は、承認済み番号の対象ノードのみ。`use_figma` の読み取り（名前・Property名・Variant値・Descriptionのみ返す）で取得し、結果は「ノードID／提示時の変更前／現在値／一致○×」の一覧に整えて持ち帰る。ツリー全体のメタデータは取得しない。
- **一致した対象だけ**書き込む。1件でも不一致なら、その対象は書き込まずに保留し、不一致の内容（提示時の値→現在値）を人に報告して判断を仰ぐ。他の一致した対象を先に進めてよいかも確認する。
- 現在値で上書きせず、現在値に合わせて変更後の名前を勝手に作り直さない（修正案の再提示は人の承認を経る）。
- この確認は「確認した時点」の保証であり、確認後の変更は防げない。報告でその旨を一言添える。

#### 3-1. 書き込み

`use_figma`（figma-use 準拠）で、マスターComponent／Component Setに対して書き込む。変更の種類ごとに注意点が異なる。

| 対象 | 注意点 |
|---|---|
| **Component Set名** | Instanceは維持され表示も変わらない。ただし名前で参照している要件書・ドキュメントが切れる可能性があるため、実行前に確認済みか尋ねる |
| **Variant値／Variant軸名** | 既存Instanceの選択は自動で追随する |
| **Property名** | 表示名のみが変わる。内部キー（`#`以降）は維持される |
| **レイヤー名** | overrideは通常保持される。**TEXTノードをリネームすると本文の自動命名が解除される**（以後、本文を変えても名前に反映されない）。初回はこの点を伝える |
| **Description** | 表示にも構造にも影響しない。既存内容の上書き禁止（絶対原則） |

**守ること**

- 指定された番号の分だけ実行する。
- 小さいバッチに分割し、バッチごとに変更ノードIDを確認する（figma-use の絶対原則）。
- 実行中にエラーが出たら即リトライしない。エラー内容を読み、対象と理由を記録して次へ進む。

### 4. 軽量再測定

報告の前に、**変更対象だけに絞った再測定**を行う。`design-system-audit-skill` の `scripts/measure-scripts.md`（Script A/B）を、走査範囲を今回変更したComponent Setのみに絞って流用し、対象のルール違反件数がBefore→Afterでどう変わったかを確認する。

- これは「実行が意図通り反映されたか」の即時確認であり、**正式な合否判定・Issueステータス確定ではない。** 正式な再レビューは `design-system-audit-skill` の再レビュー手順に委ねる。
- 対象が少数（数件程度）の場合は、再測定の代わりに `get_metadata` 等で直接確認してもよい。

### 5. 報告する

```
#8 の修正が完了しました（対象ブランチ: <ブランチキー>）。

変更した項目（8件）:
1. desscription        → description        ✅
...
8. main action         → mainAction         ✅

失敗: 0件

軽量再測定: C4違反 8件 → 0件（対象Component Setのみ）

■ 次に必要なこと（人による判断・実行）
- ブランチの内容を確認し、表示崩れがないか確認してください。
- 本体への反映（マージ）と、ライブラリの再公開は本スキルでは実行できません。人が判断・実行してください。
- マージ前に、今回変更した対象について本体側の現在値とブランチの値を比較した一覧（ノードID／ブランチ／本体／一致○×）を添える。本体側が更新されている対象があれば、マージ前にブランチへ本体の更新を取り込む（Figma UI上の人の操作）よう伝える。対象ノードのみを読み、DS全体は読まない。
- 正式な再レビューは design-system-audit-skill に依頼してください。
```

**守ること**

- 報告は修正リストのNo.に合わせた番号で、「変更した番号（パーツ名・変更前→変更後）」と「変更していない番号（理由つき）」を分けて書く。表やmd風の専門用語に頼らない。
- 変更前と変更後を全件一覧で報告する。
- 失敗した対象は、対象と理由を必ず報告する。件数だけで済ませない。
- **本体への反映（マージ）とライブラリ公開が人の作業として必要であることを必ず伝える。**
- 一度に大量の変更を溜めない（レビュー・マージの負担が増える）。

### 5-2. 対応表の同期（報告の前に必ず確認する）

変更した対象が [component-map.md](../../../guidelines/kit/component-map.md) にあるか、node-id で検索する。

- **名前の変更だけ**（リネーム）: 表は node-id が正なので更新不要。報告に「対応表: 更新不要（node-idが同じ）」と書く
- **部品の追加・削除、CSSクラス・動きに関わる変更**: 該当行の案（追加・変更・削除）を報告に載せ、承認を得てから `component-map.md` を直し、確認日を更新する
- 本スキルはFigmaのブランチに書くので、**本体へのマージ前は確認日を更新しない**（本体の状態ではないため）。表の更新案だけを報告に載せ、マージ後に反映する

## 実行後に残ること

| 実行した内容 | 残る作業 |
|---|---|
| Component Set名・Variant値・Property名の変更 | 既存のDescriptionに旧名が書かれていれば更新が必要。該当箇所を一覧で示す |
| 名前の変更全般 | ブランチの内容を本体にマージするかの判断。マージ後は再レビューで改善を確認 |
| Descriptionの追記 | マージ・ライブラリ公開後、利用側で内容が読めるか確認 |

## やってはいけないこと

- 提示しただけで承認を待たずに実行する。
- 「全部直して」「よしなに」など範囲が確定しない指示で着手する。
- 指定された番号以外を、ついでに直す。
- 段階をまたいで同時に実行する（Variant値とProperty名を同時に変える等）。
- 「要決定」の行で、変更後の名前を勝手に決める（案を出すことと確定することを混同しない）。
- 「要起案」の行で、Descriptionの内容を勝手に書いて実行まで進める。
- 構造変更（軸の追加・分離・削除、Variantの増減、Component Setへの統合）を実行する。
- Instance内部を編集する、またはマスター以外を対象にする。
- **検証用ブランチが未作成のとき、本体に直接書き込む、またはブランチを自分で作成しようとする**（Plugin APIでは不可）。
- **本体へのマージ・ライブラリ公開を自動化しようとする、または「実行した」と報告する**（人の作業であり本スキルの対象外）。
- 実行直前の現在値確認（3-0）を省略する、または不一致の対象を現在値のまま上書きする。
- 現在値の確認のために、DS全体のメタデータを取得する（対象ノードのみ読む）。
- 提示のリストを途中で切る。
- 日本語の訳語を確認なしに確定する。
- 既存のDescriptionを確認せず上書きする。
- 失敗した対象を件数だけで報告し、理由を書かない。
- エラー時に内容を読まず即リトライする。
